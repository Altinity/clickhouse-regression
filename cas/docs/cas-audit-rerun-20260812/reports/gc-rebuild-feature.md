## Rebuild path as implemented

There are exactly two entry points, and they demand **opposite** disk postures.

1. CLI, `clickhouse-disks cas-gc-rebuild [--force]` (`programs/disks/CommandCaGcRebuild.cpp:18-63`). It **requires a read-only-opened CA disk** (`:43-47`) and its shipped description says the tool is for the state where "the GC guard has refused every round (see CORRUPTED_DATA in the gc log)" and "never run against a disk a live server has mounted" (`:24-26`). It mints a random `gc_id` and calls `Gc::rebuildBaseline(force)` (`:49-51`), printing the report and rethrowing the refusal as `BAD_ARGUMENTS` (`:53-62`).

2. SQL, `SYSTEM CAS GC REBUILD [FORCE] <disk>` (`src/Parsers/ParserSystemQuery.cpp:473-478` → `src/Interpreters/InterpreterSystemQuery.cpp:2488-2522` → `ContentAddressedMetadataStorage::runGcRebuildNow`, `ContentAddressedMetadataStorage.cpp:489-505`). This path begins with `checkNotReadOnly("GC rebuild")` (`:491`), i.e. it **requires a writable disk** — the live, mounted, GC-scheduling disk of a running server.

Inside `rebuildBaseline`:

- Health gate (`CasGc.cpp:2632-2721`): decode `gc/state`; if `snap_generation > 0`, read the named fold seal and fail closed if it is missing or undecodable (`:2662-2675`, both messages end "this pool must be recreated"); mark unhealthy if any `blob_target_runs` object is absent (`:2676-2678`). If `snap_generation == 0` or `gc/state` is unreadable, adopt `newestFoldSealRef()` (`:2684-2714`, definition `:1074-1153`). If everything looks healthy and `force` was not passed, refuse (`:2716-2721`).
- Lease (`:2725-2729`): `acquireOrRenewLease(state, state_token, /*allow_steal=*/false)`. This is the **only** mutual exclusion the rebuild takes.
- Pre-work drain (`:2731-2736`) then universe discovery: `enumerateRefPrefix()` — a full LIST of the pool's refs prefix (`:2737`, `:2561-2593`) — and one `CasRefCatalog::read` cut (`:2738`). `buildRefWalkPlan` (`:2743-2744`, `:180-256`) turns catalog entries plus the listing into the walk universe; the prior seal's `ref_lives` are supplied as parent state (`:2741-2742`).
- Optional generation-0 validation (`:2748-2782`): per-life LIST of the namespace stream prefix plus `groupRefKeys`, used only to decide healthy/unhealthy.
- Generation choice (`:2784-2803`): LIST of the gc generations prefix, `generation = max_gen + 1`.
- Per-life edge derivation (`:2848-2928`): for each life, `recoverRefTableDetailedFromAuthority(backend, layout, catalog_entry, checkpoint)` (`Pool/CasRefProtocol.cpp:811-866`) replays the ref log **bounded by the `_ckpt` frontier** read once at `CasGc.cpp:2746`; every committed ref folds `+1` for its manifest's blobs, and a committed ref naming a missing/invalid manifest is a hard refusal (`:2883-2889`); precommits fold `+1` or mint a `ManifestBodyMissing` hold (`:2893-2910`); `cov.last_folded_ref_id` is set from the same recovery (`:2874`); prior-seal holds override minted ones (`:2913-2922`).
- Unowned-manifest pass (`:2931-2952`): per namespace, LIST the manifest prefix and fold `+1` for any manifest not owned by a ref whose build prefix is **not** `prefixEligible` (`:2943`, `Gc/CasOrphanManifestSweep.cpp:373-387`) — i.e. in-flight builds of a live mount are protected.
- Persistence (`:2961-2992`): flush each shard's deltas into `(generation, attempt, shard)` run objects (`:2811-2824` → `Gc/CasBlobInDegree.cpp:551-554`), reset every shard's condemned summary (`:2973-2974`), `validateFoldSealForWrite`, write the fold seal (`:2979-2980`), then a single `casPut` on `gc/state` guarded by the lease token (`:2987`). Only on a committed `casPut` is `performed` set and a `GcRebuild` event emitted (`:2994-3013`).

`Gc::previewDeletes` (`:3017-3080`), reachable only from `cas-gc-dryrun` (which requires a read-only-opened disk, `programs/disks/CommandCaGcDryRun.cpp:38-39`), reads the adopted seal and lists zero-in-degree candidates plus every condemned row. It performs no writes.

`cas-fsck`, `cas-inspect`, `cas-drop-member` all require a read-only-opened disk (`CommandFsck.cpp:51-54`, `CommandCaInspect.cpp:44-45`, `CommandCaDropMember.cpp:43-46`). `SYSTEM CAS FSCK` (`InterpreterSystemQuery.cpp:2524-2548`) does not require read-only and takes no deadline. Each `SYSTEM CAS` verb has its own `GLOBAL SYSTEM` privilege (`src/Access/Common/AccessType.h:351-357`, checked at `InterpreterSystemQuery.cpp:1012-1033` and declared at `:3161-3183`).

## Findings

### gc-rebuild-feature-1 -- no writer/mount interlock exists; the two entry points require opposite read-only postures and "read-only" does not gate writes (High)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:491` (`checkNotReadOnly("GC rebuild")`) vs `programs/disks/CommandCaGcRebuild.cpp:26,43-47`; the only exclusion taken is `CasGc.cpp:2725`; the mount census at `CasGc.cpp:2968-2971` discards its result; `ContentAddressedMetadataStorage.h:110` and `.cpp:582` (`read_only = object_storage->isReadOnly()`); `Pool/CasPool.cpp:299,364` (the only two places `PoolConfig::read_only` is consulted).
- **Trigger**: on a running server with a writable CA disk, `SYSTEM CAS GC REBUILD FORCE <disk>` while inserts are in flight. It is accepted; nothing in the path examines mount leases, mount slots, or writer epochs to decide whether to proceed.
- **Evidence**: the SQL path *requires* `read_only == false`, which is precisely the live-mounted disk the CLI's own shipped string forbids ("never run against a disk a live server has mounted"). Asked whether a real interlock exists: it does not. `acquireOrRenewLease` (`CasGc.cpp:3105-3190`) arbitrates only between GC leaders — it reads and CASes `gc/state`, nothing else. `read_only` is an in-process flag: it is set from `object_storage->isReadOnly()` and inside the pool it only suppresses bootstrap and the `mountWritable` claim (`CasPool.cpp:299,364`); no CAS backend write path consults it, which is why the "read-only" CLI rebuild can still write run objects, a fold seal and `gc/state`. The one point where the rebuild touches live-writer state, `computeHeartbeatFloor` (`CasGc.cpp:2971`, definition `Pool/CasServerRoot.cpp:455-549`), has its returned `HeartbeatFloor` dropped on the floor — and because `mount_obs` is a fresh empty map for this `Gc` instance and the call happens exactly once, the token-stability test at `CasServerRoot.cpp:506-507` can never be satisfied, so the call cannot even fence. The rebuild pays a pool-wide LIST plus a GET per mount slot and derives zero protection from it.
- **Notes**: I could not construct a *confirmed* permanent-edge-loss trigger from a live rebuild, and the reason is worth stating because it is the load-bearing safety property of this path: the per-life edge derivation is anchored to the immutable `_ckpt` frontier (`CasRefProtocol.cpp:811-866`, grounding at `Pool/CasRefCkpt.cpp:86-127`) and the persisted cursor is taken from *that same* recovery (`CasGc.cpp:2874`), so every ref a concurrent writer commits lands above the cursor and is folded by a later round; re-folding an already-folded `+1` is idempotent and an unmatched `-1` is counted, not applied (`CasBlobInDegree.cpp:514-537`). A rewound cursor is therefore safe. That makes this finding a missing-interlock/uncontrolled-concurrency finding rather than a proven data-loss finding — but it is the substrate for finding 2, which *is* reachable, and it means the safety of the DR path rests entirely on an invariant no code in this path checks.

### gc-rebuild-feature-2 -- the rebuild never renews its lease across an unbounded scan, and the in-process scheduler steals it; the mitigation is unreachable while the rebuild runs (High)

- **Anchor**: lease taken at `CasGc.cpp:2725` and used at `:2987`; no `pulseHeartbeat` or re-`acquireOrRenewLease` anywhere between. Steal test: `CasGc.cpp:3157-3172`. Background rounds pass `allow_steal = true` by default (`Gc/CasGcScheduler.h:94-95`, background loop at `Gc/CasGcScheduler.cpp:245-247` omits the argument; `runOneRoundNow` explicitly passes `false`, `:213`). Mutex disjointness: `runGcRebuildNow` holds only `gc_scheduler_mutex` (`ContentAddressedMetadataStorage.cpp:496`), while the scheduler thread serialises on its own `gc_round_mutex`.
- **Trigger**: `SYSTEM CAS GC REBUILD FORCE <disk>` on a pool whose scan takes longer than ~2 GC intervals. Tick 1: the scheduler sees a lease owner different from its last observation, so `incumbent_renewed` is true, it declines and records the observation. Tick 2: the owner and `lease.seq` are unchanged (the rebuild never renews) and the GC heartbeat is unchanged (the rebuild never pulses), so `hb_alive` is false and the steal at `:3177-3186` commits. A normal round now runs concurrently with the in-flight rebuild.
- **Evidence**: consequences are all reachable from code. (a) The rebuild's terminal `casPut` fails and returns `refusal = "gc/state changed under the rebuild (a competing writer) — re-run"` (`:2990-2992`), discarding the entire scan; since nothing is resumable (finding 3), a re-run hits the same wall. (b) The stolen-lease round runs `cleanupRefObjects` and the namespace janitor, which delete ref-log/snapshot objects; the rebuild's still-running checkpoint-bounded walk then reads a legitimately deleted log and throws `CORRUPTED_DATA` "committed log id {}-{} is absent under the supplied immutable checkpoint frontier" (`CasRefProtocol.cpp:839-843`) or, from `readCheckpointSnapshotBase`, "checkpoint-named base snapshot ... is absent" (`:798-804`) — a *false corruption verdict* produced by ordinary concurrency, on the one tool an operator reaches for when they already believe the pool is corrupt. (c) Both writers are now emitting into fold generations chosen by different rules (see finding 4).
- **Notes**: the obvious operator mitigation — stop GC, then rebuild — is not available *during* a rebuild: `gcStop()` acquires `lifecycle_mutex` then `gc_scheduler_mutex` (`ContentAddressedMetadataStorage.cpp:691-692`) and therefore blocks behind the rebuild's `gc_scheduler_mutex` for the rebuild's whole duration. Doing it in the right order beforehand works, but nothing in the code or in any shipped string on this path tells the operator to, and `runGcRebuildNow` does not stop or quiesce the scheduler itself. Lock ordering is consistent (`lifecycle_mutex` before `gc_scheduler_mutex` everywhere it is taken), so this is a liveness/usability defect, not a deadlock.

### gc-rebuild-feature-3 -- the scan is O(all refs + all manifests) with a synchronous round trip each, no deadline, no budget, and no resumability (Medium)

- **Anchor**: `CasGc.cpp:2737` (`enumerateRefPrefix`, `:2561-2593`), `:2752-2754` (per-life stream LIST), `:2788-2801` (generations LIST), `:2868` (per-life log replay, `CasRefProtocol.cpp:834-858` — one `backend.get` per log id), `:2935-2951` (per-namespace manifest LIST plus one `foldManifestEdges` body GET per manifest). Budget: `:2804-2805` and its use at `:2832`.
- **Trigger**: any pool with a non-trivial manifest count. Run either entry point and there is no parameter that bounds the work or the wall time.
- **Evidence**: `rebuild_edge_budget` bounds only how many `BlobDelta`s accumulate in RAM before a shard flush (`:2832`) — it does not bound LISTs, GETs, or elapsed time, and no code path passes a deadline into the rebuild. Compare the sibling read-only tool, which *does* have both a deadline and a partial-result mode: `cas-fsck --timeout` / `--partial` (`programs/disks/CommandFsck.cpp:28-32,60-64`) with the shipped rationale "abort the scan after N seconds with a clear error instead of hanging". Nothing about the rebuild's progress is persisted: on any failure or refusal the next attempt restarts from zero, and `next.manifest_sweep_cursor = ""` (`CasGc.cpp:2986`) additionally rewinds the orphan-sweep cursor, so a successful rebuild also re-does the pool-wide manifest sweep from the beginning. There is also no progress callback (`cas-fsck` has `FsckProgress`, `CommandFsck.cpp:56-59`), so a multi-hour rebuild is indistinguishable from a hang.
- **Notes**: this compounds finding 2 — the larger the pool, the more certainly the lease is stolen before the scan ends, i.e. the DR path is least likely to work on exactly the pools that need it.

### gc-rebuild-feature-4 -- refusals and failures are not side-effect free, and the residue is adoptable and can trip a fail-closed "impossible" check (Medium)

- **Anchor**: `CasGc.cpp:2811-2824` (`flush_shard` writes run objects mid-scan), `:2832` (flush triggered by budget), refusal returns at `:2885-2888` and `:2990-2992`, seal write at `:2980` ordered *before* the `gc/state` CAS at `:2987`; attempt numbering at `:2810,2816,2976-2978` vs the normal round's `attempt = state.lease.seq` (`:1375`); `putDeterministicArtifact` at `Gc/CasBlobInDegree.cpp:300-310` and the run key at `:551`; adoption of an unreferenced seal at `CasGc.cpp:2686-2713` (`newestFoldSealRef`, `:1074-1153`).
- **Trigger**: run a rebuild on a pool large enough that at least one shard bucket reaches the budget, and let it hit either refusal — e.g. a committed ref naming a missing manifest (`:2885`), or a concurrent lease steal (finding 2). The tool reports `performed=0` and a refusal, but a complete-looking fold seal at generation `G` plus its source-edge runs are already durable and unreferenced by `gc/state`.
- **Evidence**: `pruneSupersededGenerations` prunes relative to the *adopted* generation, so an unadopted generation `G` is not cleaned up by it. Worse, `newestFoldSealRef()` is exactly the adoption source used when `gc/state` names no baseline (`:2684-2713`), so a later rebuild can adopt a *failed* rebuild's seal as `prior_seal` and take its holds from there — and the surrounding shipped strings state the standard this violates: "A rebuild that dropped them would bless a baseline whose frontier is unproven" (`:2664-2666`). Separately, the two producers number `attempt` differently: a rebuild uses a per-shard flush counter starting at 1 (`:2810,2816`) while a normal round uses the lease sequence (`:1375`). On a young pool (fresh `gc/state`, `lease.seq == 1`, `snap_generation == 0`) both resolve to generation 1 / attempt 1, and two divergent writes to `blobTargetRunKey(1,1,shard,0)` or `foldSealKey(1,1)` make `putDeterministicArtifact` throw `CORRUPTED_DATA` "occupied by divergent bytes (impossible under correct operation; refusing to proceed)" — a fail-closed check firing on a state that concurrency, not corruption, produced.
- **Notes**: the fail-closed direction is the right one; the defect is that the rebuild can manufacture the precondition. Nothing here deletes blobs — the rebuild's `foldDeltasIntoGeneration` calls pass no `head_blob`/`peek_head`/`confirm_condemned_marker`, `current_round = 0`, `suppress_destructive = false` with a null retired-merge sink (`:2816-2821`), so the rebuild neither condemns nor retires.

### gc-rebuild-feature-5 -- `cas-gc-dryrun` is not a preview of the next round, is silently empty in the disaster state, and one bad run suppresses the whole output (Medium)

- **Anchor**: `CasGc.cpp:3017-3080`; empty return at `:3021-3023`; checksum verification at `:3076`; shipped description "Preview the next GC round's deletes for a content-addressed pool (read-only, no deletes)" at `programs/disks/CommandCaGcDryRun.cpp:23`; printing at `:44-46`.
- **Trigger**: run `cas-gc-dryrun` on a pool whose `gc/state` object is absent or unreadable — the exact state `cas-gc-rebuild`'s own description names as its reason to exist. Output is `preview_deletes=0`, indistinguishable from "the next round will delete nothing".
- **Evidence**: `previewDeletes` reads only the *adopted* seal's runs. It does not run a fold, so it cannot show anything the next round would newly condemn or newly spare; it applies none of the round's gates (`suppress_destructive`, graduation timing, the per-round budgets in `runRegularRound`); and it covers only blobs — no manifest bodies, ref objects, superseded generations, or namespace-janitor deletes, all of which a real round can remove. So the number it prints is neither an upper nor a lower bound on the next round's deletes, while the shipped description presents it as the next round's deletes. Additionally `reader.verifyAgainst(run.checksum)` (`:3076`) throws while building the result vector, and the caller prints only after the call returns (`CommandCaGcDryRun.cpp:42-46`), so a single corrupted run means the operator sees *no* preview rows at all rather than the rows already decoded — the opposite of the `--partial` posture the sibling `cas-fsck` ships (`CommandFsck.cpp:32`).
- **Notes**: `previewDeletes` itself performs no writes, so the "read-only, no deletes" half of the description holds.

### gc-rebuild-feature-6 -- `SYSTEM CAS FSCK` holds `lifecycle_mutex` across an unbounded scan, blocking `SYSTEM CAS GC STOP`/`START`/`FORGET` (Medium)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:739-745` (`std::lock_guard lifecycle(lifecycle_mutex)` then `Cas::runFsck(*store(), detail)`), the same mutex in `gcStop` (`:691`), `gcStart` (`:711`) and `forgetDisk` (`:663`); `Tools/CasFsck.h:114-116` shows the deadline/progress/partial/namespace-prefix parameters the SQL path declines to pass; the CLI passes all of them (`programs/disks/CommandFsck.cpp:56-64`).
- **Trigger**: `SYSTEM CAS FSCK <disk>` on a large pool, then `SYSTEM CAS GC STOP <disk>` from another session. The second statement blocks until the scan finishes.
- **Evidence**: the SQL verb calls `runFsck` with default arguments — no deadline, no progress sink, no partial mode, no namespace scoping — so it is an O(all objects) synchronous scan with no bound, and it holds the lifecycle mutex for its entire duration. The operator therefore cannot quiesce GC while diagnosing, which is the natural first step before a rebuild. The CLI verb is fully parameterised, so the gap is specific to the SQL surface.
- **Notes**: `runFsck` performs no writes (no `putIfAbsent`/`putOverwrite`/`casPut`/`deleteExact` in `Tools/CasFsck.cpp`), so its read-only claim holds; this is a liveness and operability finding, not a correctness one.

### gc-rebuild-feature-7 -- the rebuild reports almost nothing about the quality of the baseline it blesses (Low)

- **Anchor**: `RebuildReport` fields at `Gc/CasGc.h:48-63`; dropped-row counters computed at `Gc/CasGc.cpp:208,219,229,240,250` and exposed by `RefPlan::droppedParentRows()`/`droppedHolds()` (`CasGc.h:188-192`) but never read on the rebuild path; the normal round does surface them (`CasGc.cpp:529-531`). `clamped_shards` incremented per precommit at `:2908`. Refusal handling at `programs/disks/CommandCaGcRebuild.cpp:53-62` and `InterpreterSystemQuery.cpp:2499-2501`. Skipped reconcile: `listRefPrefix` calls `store->reconcileRefCatalogCut(catalog_cut)` (`CasGc.cpp:2606`); the rebuild's own catalog read at `:2738` does not.
- **Trigger**: rebuild a pool where the prior seal carries a hold for a life that is no longer in the catalog cut. `buildRefWalkPlan` drops that parent row and its hold (`:202-213`), the successor seal never carries it, and `RebuildReport` has no field in which that appears — the report says `performed=1` and nothing else.
- **Evidence**: the report exposes counts of what was found (`namespaces`, `committed_refs`, `live_precommits`, `unowned_alive_manifests`, `edges`) but nothing about what was *dropped or skipped*: no dropped parent rows/holds/checkpoints, no count of lives whose recovery was checkpoint-empty, no count of manifests skipped by `prefixEligible` (`:2943`), no per-namespace edge attribution. `clamped_shards` is incremented once per held precommit, not per shard, so the name does not describe the value. On the SQL path the refusal is raised as an exception before the result row is built (`InterpreterSystemQuery.cpp:2500-2501`), so a refused rebuild yields no counters at all — the CLI at least prints them first (`CommandCaGcRebuild.cpp:53-56`). Finally, unlike the hot scan, the rebuild omits `reconcileRefCatalogCut`, so an in-server rebuild leaves the live store's cached catalog view un-reconciled with the cut it just used.
- **Notes**: `virgin_by_enumeration` deserves credit — it is surfaced in both the report and the `system.cas_gc_log`-facing `LOG_INFO` (`InterpreterSystemQuery.cpp:2502-2508`), and the accompanying shipped `LOG_WARNING` (`CasGc.cpp:1142-1151`) states plainly that the verdict rests on enumeration alone and that holds may be lost. That is the standard the rest of the report does not meet.

## By-design / info / non-actionable

- **Checkpoint-anchored recovery is the right design and I verified it holds.** `recoverRefTableDetailedFromAuthority` walks only up to `_ckpt.committed_through` and fails closed on any absent log or snapshot base (`CasRefProtocol.cpp:836-844,741-747,776-784,797-804`); `chooseRecoveryGrounding` refuses a `Live`/`Removing` namespace without a readable `_ckpt` carrying `life_epoch` (`Pool/CasRefCkpt.cpp:89-96`). Combined with the cursor being taken from the same recovery (`CasGc.cpp:2874`), a concurrent writer's edges are always above the cursor and are re-folded later, and cursor rewind is idempotent for `+1` and merely counted for an unmatched `-1` (`CasBlobInDegree.cpp:514-537`).
- **A committed ref naming a missing or invalid manifest is a refusal, not a silent skip** (`CasGc.cpp:2883-2889`) — the fail-closed choice, and the message names the next step ("run fsck forensics first").
- **A missing or undecodable prior fold seal is a refusal** (`:2662-2675`), and `newestFoldSealRef` refuses when a seal exists above the listed maximum, i.e. when the enumeration is demonstrably incomplete (`:1113-1126`). Both are fail-closed on unprovable holds.
- **In-flight builds of a live mount are protected during the unowned-manifest pass** via `prefixEligible` (`:2943`, `CasOrphanManifestSweep.cpp:373-387`): only prefixes strictly below the mount write floor are skipped.
- **The rebuild never deletes or condemns**: its `foldDeltasIntoGeneration` calls omit the head/peek/marker callbacks and the retired-merge sink (`:2816-2821`).
- **Access control on the destructive verbs is present and correctly scoped.** `SYSTEM CAS GC REBUILD`, `GC RUN`, `DROP POOL MEMBER`, `FSCK`, `FORGET`, `GC STOP`, `GC START` each have a distinct `GLOBAL SYSTEM` privilege (`AccessType.h:351-357`), checked in `execute` (`InterpreterSystemQuery.cpp:1012-1033`) and declared in `getRequiredAccessForDDLOnCluster` (`:3161-3183`). `FORCE` is a modifier on `SYSTEM CAS GC REBUILD` and correctly needs no separate privilege beyond it (`ParserSystemQuery.cpp:473-475`).
- **`clickhouse-disks`/`clickhouse-local` are unauthenticated by construction.** `cas-gc-rebuild`, `cas-drop-member` and friends mutate pool-wide GC state with no privilege check; the only gate is filesystem/credential access to the object store. Not actionable as a code defect, but it means the SQL privilege model is not the only route to these effects — worth stating because finding 1 makes `cas-gc-rebuild` writable-in-effect against a pool other servers may be mounting.
- **`cas-inspect` and `cas-fsck` are genuinely read-only** (no write calls in `Tools/CasInspect.cpp` or `Tools/CasFsck.cpp`), and `cas-fsck`'s exit-code contract plus its `note:` lines (`CommandFsck.cpp:68-97,126-147`) are the strongest operator-facing diagnostics on this surface — notably the `stale_edge` note, which names a rebuild as the only remedy.
- **`cas-drop-member` performs a victim-ownership check against a catalog cut and refuses on drift** ("catalog changed after the victim ownership check; refusing slot retirement against a stale cut", `Tools/CasDecommission.cpp:233`) and does a slot liveness recheck (`:302-329`). Its interaction with a *live* member is the `gc-protocol`/decommission surface, not this audit's; I found nothing rebuild-specific to flag.
- **Lock ordering is consistent** (`lifecycle_mutex` before `gc_scheduler_mutex` before `pointer_mutex` at every site), so finding 6's blocking is not a deadlock.
- `Gc`'s constructor installs real defaults for `now_ms_fn`/`mono_ms_fn` when the CLI passes none (`CasGc.cpp:306-313`), so the CLI rebuild's `now_ms_fn()` call at `:2971` is safe. Checked because both CLI call sites default them.
