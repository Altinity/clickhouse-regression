# bc1-offset-overflow -- fresh audit 2026-08-12

## Scope

Target: `/Volumes/workspace/altinity-clickhouse/ClickHouse`, branch `cas-code-only-strip`, base `842f2b37b8f`, working tree as-is, read-only. CAS root `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/` (~36.6 kLOC across 118 files) plus the CAS-owned call sites reached from it in `src/Disks/DiskObjectStorage/DiskObjectStorage.cpp`, `src/IO/ReadBufferFromFileView.{h,cpp}`, `src/IO/readIntText.h`.

Bug class: integer and arithmetic defects — signed/unsigned mixing, narrowing casts, overflow/underflow in offset/size/budget/time arithmetic, unsigned subtraction, division by zero, off-by-one, permissive numeric parsing, hash truncation.

Code-only rule honoured: no `docs/**` and no comments were used as evidence of intent. Shipped strings (exception messages, `ContentAddressedSettings.cpp` `DECLARE` descriptions) were used. All CAS tests are deleted in the working tree, so no test was used as a specification.

Cite-don't-duplicate (found by siblings, not re-reported here): the read path takes the payload offset from pool meta rather than from the envelope; `getStorageObjects` drops `BlobLocation.offset`. This report only covers the *arithmetic* on those values. Blob mtime *semantics* belong to bc6; only the timestamp multiplication overflow is reported here.

Trust model used: any byte in the bucket is untrusted. The part-manifest body is self-authenticated only by an unkeyed CityHash128 (`computePayloadDigest`, `CasPartManifestFormat.cpp:272-279`), so anyone who can write the bucket can produce a manifest that passes every decode check with arbitrary numeric fields.

## Findings

### bc1-1 -- manifest `sz` is an unbounded u64 and `offset + length` overflows on the read path (High)

- **Anchor**: `Formats/CasPartManifestFormat.cpp:205` and `:226` (decode); `Pool/CasManifestReader.cpp:139-143` (locate); `ContentAddressedMetadataStorage.cpp:1439`, `:1441`, `:1452`, `:1454` (read); `src/IO/ReadBufferFromFileView.cpp:13-29` and `src/IO/ReadBufferFromFileView.h:22` (consumer).
- **Expression**:
  - decode: `else if (key == "sz") sz = r.readU64Number();` then `e.blob_size = *sz;` — no range check of any kind.
  - locate: `BlobLocation{ .key = ..., .offset = meta.blob_header_len, .length = entry.blob_size }`.
  - read: `plan.object = StoredObject(physicalKey(location.key), path, location.offset + location.length);` / `plan.payload_end = location.offset + location.length;` and the same sum twice more in `readBlobPayload`.
  - consumer: `ReadBufferFromFileView(impl, path, left_bound_=offset, right_bound_=offset+length)`, whose constructor never checks `left_bound <= right_bound`, and `tryGetFileSize() { return right_bound - left_bound; }`.
- **Overflowing input**: a manifest record `{"p":"data.bin","pm":"blob","ha":"ch128","h":"<32 hex>","sz":18446744073709551516}` with `pd` recomputed over the re-encoded body (trivial: unkeyed CityHash128). With the pool default `blob_header_len = 256` (`Pool/CasPool.h:46`), `offset + length` = `256 + (2^64 - 100)` wraps to `156`.
- **Consequence**: `payload_end (156) < payload_offset (256)`. `StoredObject` is created with a 156-byte size for an object that is larger, and the file view is constructed with an inverted window: `tryGetFileSize()` returns `156 - 256 = 18446744073709551516` (an 18-exabyte file size handed to the read pipeline and to callers of `getFileSize`), `getPosition()` (`ReadBufferFromFileView.cpp:68`) underflows to a negative `off_t`, and `resizeWorkingBuffer()` (`:155-164`) collapses the working buffer to zero so every read returns EOF. The failure is a silent wrong/empty read plus a nonsense file size, not a `CORRUPTED_DATA` refusal. Without the wrap (e.g. `sz = 2^60`) the same path reads until the real object EOF and reports a 1-exabyte file size for a small part file.
- **Evidence**: no site between `decodePartManifest` and `readBlobPayload` compares `blob_size` with the blob object's real size or with `BlobMeta.size`; `getFileSize` returns the manifest value verbatim (`ContentAddressedMetadataStorage.cpp:1167-1168` → `ManifestEntry::size()`, `Formats/CasPartManifestFormat.h:29`). The write path *does* perform exactly the missing check — `PartWriteTxn::observeAndAdmit` refuses `hr.size < header_len` and derives `logical_size = hr.size - header_len` (`Pool/CasPartWriteTxn.cpp:253-257`) — so the asymmetry is in the reader, not in the model. Contrast the sibling range reader, which *does* clamp: `to_read = std::min(*range.length, available)` (`Backend/CasObjectStorageBackend.cpp:301-302`), yet still computes an unclamped `buf->setReadUntilPosition(range.offset + *range.length)` at `:305` and `:328` — the same u64 sum, so a wrapped `until` position lands below the seek offset there too.

### bc1-2 -- every CAS numeric field silently wraps mod 2^64, defeating all decoder range gates (High)

- **Anchor**: `Formats/CasTextFormat.cpp:207-215` (`readU64Number`), `:193-205` (`readU64String`), `:217-223` (`readU32Number`); `src/IO/readIntText.h:246-250` and `:25`.
- **Expression**: `uint64_t v = 0; readIntText(v, in); return v;` — `readIntText`'s default template argument is `ReadIntTextCheckOverflow::DO_NOT_CHECK_OVERFLOW`, and in that mode `readIntTextInBaseImpl` executes the bare `res *= base; res += digit;` loop (`readIntText.h:193-194`) with no overflow test. `readU32Number` layers its `> uint32::max` test on top of the already-wrapped u64, so it cannot see the original value either.
- **Overflowing input**: `_pool_meta` body `{"pid":"...","hln":18446744073709552016,"gcs":1,"mrg":1,"alg":"ch128"}`. `2^64 + 400` wraps to `400`.
- **Consequence**: `validatePoolBlobHeaderLen` (`Formats/CasPoolMetaFormat.cpp:21-30`, reached from `:149`) sees `400`: `>= 240`, `% 8 == 0`, `<= 16384` — accepted. The pool now reports a `blob_header_len` of 400 where the writer used 256, so every `BlobLocation.offset` (`Pool/CasManifestReader.cpp:141`) is 144 bytes too deep and every blob read returns shifted payload bytes, while `retiredLogicalSize` (`Gc/CasGc.cpp:268-277`) mis-accounts every retirement by 144 bytes. No error is raised anywhere. The same wrap applies to every numeric field in every CAS text format — `sz`, `il`, `gcs`, `cls`, `shard`, `ct`, `pt`, `rnd`, `sg`, `ls`, `ts`, `mo` — so *each* documented range gate in the CAS decoders is enforced against a value the object did not contain. This is the root cause amplifier for bc1-1, bc1-3 and bc1-5.
- **Evidence**: the codebase already contains the strict alternative and uses it elsewhere: `parseCanonicalU64` (`Formats/CasLayout.cpp:12-24`) uses `std::from_chars` and rejects out-of-range and non-canonical spellings; `tryParseManifestRef` (`Primitives/CasTypes.h:133-160`) likewise. Only the JSON body readers use the wrapping helper. Secondary defect at the same anchor: `readIntTextInBaseImpl` returns success with `x = 0` when it consumes no digits at all (`readIntText.h:198-206` — `has_number` false with no sign is not an error), so a value byte that is not a digit yields a silent `0`; in the CAS grammars this is usually caught afterwards by the `assertChar(',')`/`junk after record` checks, but the helper itself provides no guarantee.

### bc1-3 -- `gc_shards` is adopted from bucket bytes with no upper bound and then used to size vectors and loop bounds (High)

- **Anchor**: `Formats/CasPoolMetaFormat.cpp:116` and `:142`; `Pool/CasPoolMeta.cpp:94-95`; `Pool/CasPool.cpp:354` and `:550`; `Formats/CasGcStateFormat.cpp:53` and `:64`; `Gc/CasGc.cpp:1294`, `:2140`, `:2143`, `:2147`, `:2808-2810`, `:2961`; `Formats/CasFoldSealFormat.cpp:89`.
- **Expression**: decode only checks for zero — `if (!saw_gc_shards || pm.gc_shards == 0) throw ... "missing or zero gcs"` — and the mount then overwrites the operator's configured value with the bucket's: `config.gc_shards = meta.gc_shards;`. Consumers: `std::vector<std::vector<BlobDelta>> buckets(state.gc_shards);`, `std::vector<std::vector<BlobSourceRetirement>> retirement_buckets(state.gc_shards);`, `result.retired_merge.resize(state.gc_shards);`, `std::vector<uint64_t> attempt_of(gc_shards, 0);`, `std::vector<bool> run_seen(gc_shards, false);`, and `for (uint64_t shard = 0; shard < state.gc_shards; ++shard)`.
- **Overflowing input**: `_pool_meta` with `{"gcs":18446744073709551615}` (or, via bc1-2, any spelling that wraps to a huge in-range value); alternatively `gc/state` with the same `gcs`, which passes `decodeGcState`'s zero-only gate.
- **Consequence**: allocation-sized-by-attacker. `std::vector(2^64-1)` throws `std::length_error`/`bad_alloc` on every GC round and every fold-seal validation, so GC is permanently wedged and nothing is ever reclaimed (a durable storage-leak DoS, not a transient error). A merely large value such as `10^9` allocates ~48 GB of empty bucket vectors *and* drives an O(gc_shards) loop that issues per-shard backend work at `Gc/CasGc.cpp:2147-2168` — OOM or an effectively non-terminating round. `ContentAddressedSettings.cpp:39` ships the description "Blob-hash-prefix reducer shards (>= 1); creation-time only" and `:123-126` enforces only `>= 1`, so the same value can also arrive from a config typo (`gc_shards=10000000000`) and wedge the disk at mount.
- **Evidence**: the shard *index* is bounded (`ShardReducer` ctor rejects `shard >= gc_shards`, `Gc/CasGcShardPlan.cpp:26-31`; `validateFoldSealStructure` rejects `run.shard >= gc_shards`, `Formats/CasFoldSealFormat.cpp:96-99`) but the shard *count* is bounded nowhere. Note `Formats/CasFoldSealFormat.cpp:89` allocates `run_seen(gc_shards)` *before* the `condemned_summary.size() != gc_shards` cross-check at `:113`, so the allocation cannot be avoided by the totality check.

### bc1-4 -- `std::stoull` accepts `-1` for GC generation keys, then `max_gen + 1` overflows (Medium)

- **Anchor**: `Gc/CasGc.cpp:2796` with `:2803`; `Gc/CasGc.cpp:1094` with `:1116` and `:1120-1125`.
- **Expression**: `max_gen = std::max(max_gen, static_cast<uint64_t>(std::stoull(k.key.substr(from, slash - from))));` … `const uint64_t generation = max_gen + 1;` and, in `newestFoldSealRef`, `generation = std::stoull(...)` … `const uint64_t generation = listed_max_generation + above;`.
- **Overflowing input**: a single object whose key is `<pool_prefix>/gc/gen/-1/anything`. `std::stoull("-1")` does not throw: it negates into the unsigned result and returns `18446744073709551615`, so the `catch (...) { return; }` guard never fires. (Genuinely out-of-range digit strings *are* caught; `-1`, `+5` and leading whitespace are not.)
- **Consequence**: two distinct wedges. (a) In `runRebuild`, `max_gen + 1` wraps to `0`, so the rebuild targets generation 0 — the value that `validateFoldSealStructure` rejects as "blob-target run requires a nonempty key and nonzero physical generation" (`Formats/CasFoldSealFormat.cpp:92-95`) and that `gc/state.snap_generation == 0` uses as the never-sealed sentinel; the rebuild either aborts with `LOGICAL_ERROR` or restarts the generation lineage on top of the sentinel. (b) In `newestFoldSealRef`, `listed_max_generation + above` wraps to `0` and `1`, so the "is there a seal above the enumerated maximum?" probe actually probes generation 1 — which exists in any pool that has ever sealed and not yet pruned — and the function throws the terminal verdict `"CAS GC rebuild: a fold seal exists at generation {} (attempt {}) while the pool-wide enumeration of {} reported nothing above generation {} … GC refuses to rebuild; this pool must be recreated."` A one-object write thus makes the tool declare a healthy pool unrecoverable.
- **Evidence**: the attempt component at `:1175` is protected against the same permissiveness only accidentally, by the canonical-key re-render check at `:1181` (`layout.foldSealKey(generation, attempt) != k.key`); the generation components at `:1094` and `:2796` have no such re-render check. `Layout::parseBlobTargetRunKey` (`Formats/CasLayout.cpp:239-293`) parses the identical key shape with the strict `parseCanonicalU64`, which rejects `-1` and leading zeros — so the strict parser exists and is simply not used on these three paths.

### bc1-5 -- `published_at_ms` is unbounded and overflows the Poco timestamp multiplication (Medium)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:1180-1182`; source fields `Formats/CasRefSnapshotFormat.cpp:213` and `:230`, `Formats/CasRefLogFormat.cpp:210`.
- **Expression**: `return Poco::Timestamp::fromEpochTime(static_cast<time_t>(resolved->published_at_ms / 1000));` where the value arrives as `ts = r.readU64Number()` → `row.published_at_ms = *ts;` with no range check. `Poco::Timestamp::fromEpochTime(t)` multiplies by the 1'000'000 microsecond resolution in signed 64-bit.
- **Overflowing input**: a ref snapshot or ref-log row with `{"ts":18446744073709551615}` (any `ts > 9.2e15`, i.e. any date past ~year 293000, suffices).
- **Consequence**: `ms / 1000 = 1.8e16` fits `time_t`, then `1.8e16 * 1e6` overflows signed `Int64` — undefined behaviour that in practice wraps to an arbitrary, frequently negative, epoch. `getLastModified` is what MergeTree uses for stale-part and TTL-style decisions, so a wrapped mtime can make a part look arbitrarily old or arbitrarily far in the future. The write path only ever stores `nowMs()` (`Pool/CasPartWriteTxn.cpp:725`), so any other value is by construction not writer-produced and should have been refused at decode.

### bc1-6 -- `gc_interval_sec` and `part_folder_validate age` are converted to ms/µs without range checks (Low)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:200` with `Gc/CasGcScheduler.cpp:41-43` and `:227`; `Parts/PartFolderAccess.cpp:178`.
- **Expression**: `gc_interval(std::chrono::seconds(settings_[ContentAddressedSetting::gc_interval_sec].value))` then `hb_interval(std::max<std::chrono::milliseconds>(50ms, duration_cast<milliseconds>(interval_) / 4))`; and `(now_ms_fn() - cached->validatedAtMs()) < params.validate.age_seconds * 1000ULL`.
- **Overflowing input**: `<gc_interval_sec>9223372036854775808</gc_interval_sec>` (a UInt64 setting stored into a signed 64-bit `chrono::seconds` rep, then multiplied by 1000 for the ms cast); `<part_folder_validate>age 18446744073709552</part_folder_validate>` (`× 1000` wraps).
- **Consequence**: for the interval, a negative or wrapped duration makes `wake.wait_for(lock, interval, ...)` return immediately, converting the GC scheduler into a busy loop that runs a round every tick — the opposite of the configured intent. For the validate age, the wrapped product yields a near-random small TTL, so the part-folder cache revalidates on nearly every access. `ContentAddressedSettings.cpp:123-126` validates only `!= 0` for `gc_interval_sec`; there is no upper bound for either setting. Operator-supplied, hence Low.

### bc1-7 -- fsck's referenced-bytes accumulator overflows on untrusted sizes (Low)

- **Anchor**: `Tools/CasFsck.cpp:557`.
- **Expression**: `report.referenced_logical_bytes += e.blob_size;` inside the per-entry walk, with `blob_size` straight from the manifest (see bc1-1) and no saturating helper.
- **Overflowing input**: two manifest entries with `sz = 2^63` each, or one entry with `sz` near `2^64`.
- **Consequence**: the fsck report's logical-bytes total wraps to a small or zero value, so the operator-facing reconciliation between `referenced_logical_bytes` and `physical_bytes` (accumulated from real head sizes at `:596`, `:610`, `:850`) silently reads as consistent when it is not. Diagnostic-only, and the tree already ships the saturating helpers this line should use (`addByteBudget`, `Formats/CasByteBudget.h:8-11`).

### bc1-8 -- `blob_header_len - 1` underflows in the envelope encoder when the length is 0 (Low, latent)

- **Anchor**: `Formats/CasBlobEnvelopeFormat.cpp:123`, `:133`, `:139`.
- **Expression**: the `blob_header_len < 1` guard lives *inside* `if (header.intended_ref)` at `:123`; the two unconditional uses at `:133` (`json.size() > static_cast<size_t>(blob_header_len) - 1`) and `:139` (`out.append((static_cast<size_t>(blob_header_len) - 1) - out.size(), ' ')`) have no such guard.
- **Overflowing input**: any call with `blob_header_len == 0` and no `intended_ref` (manifest-kind envelopes take that branch).
- **Consequence**: `0 - 1` becomes `SIZE_MAX`, the size check at `:133` always passes, and `:139` requests an append of ~2^64 bytes — `std::length_error`. Not reachable today: both call sites pass `static_cast<uint32_t>(meta.blob_header_len)` (`Pool/CasPartWriteTxn.cpp:324`, `ContentAddressedTransaction.cpp:528`) from a `PoolMeta` that `validatePoolBlobHeaderLen` has pinned to `[240, 16384]`. Reported because the guard placement, not the arithmetic, is what makes it safe.

## Checked and sound

Verified by reading, no defect found:

- **Retry/backoff exponentials** — `CasRequestController::backoffBeforeAttempt` (`Backend/CasRequestControl.cpp:178-188`) and the ref-recovery twin (`Pool/CasRefLedger.cpp:1073-1075`) both pre-test `doublings >= 63` and `initial > (cap >> doublings)` before shifting; no shift-count UB, no overflow past the cap.
- **Budget validation subtraction** — `validateCasRequestBudget` (`Backend/CasRequestControl.cpp:106-107`) short-circuits `attempt_timeout_ms < ttl` before evaluating `ttl - attempt_timeout_ms`; `refAppendFenceOk` (`Pool/CasMountRuntime.cpp:101-111`) returns early on `now >= deadline` before `deadline - now`; `recovery_retry_sleep_fn` (`Pool/CasRefLedger.cpp:174-183`) guards `slept < total_ms` before `total_ms - slept`; `Pool/CasRefLedger.cpp:860-861` and the `GcRoundWorkBudget` remaining-helpers (`Gc/CasBlobInDegree.h`) all test `used < max` before subtracting.
- **Saturating byte budgets** — `addByteBudget`/`mulByteBudget` (`Formats/CasByteBudget.h:8-16`) are correct saturating primitives.
- **Bounded binary decode** — `readFixedBytes` (`Primitives/CasCodecUtil.h:37-45`) refuses `n > in.available()` before allocating; `decodeCondemnedRow` (`Gc/CasBlobInDegree.cpp:176-199`) validates the fixed prefix, the flag/type domains and `p.size() == kFixed + len` before slicing, and its encoder refuses a token longer than the 16-bit length field (`:168-171`) instead of truncating it.
- **Division by zero** — every `% gc_shards` site (`Gc/CasGcShardPlan.h:21`, `Gc/CasGcShardPlan.cpp:20`) is fed a value that both decoders (`Formats/CasPoolMetaFormat.cpp:142`, `Formats/CasGcStateFormat.cpp:64`), the minting path (`Pool/CasPoolMeta.cpp:94`), the settings gate (`ContentAddressedSettings.cpp:123`) and `ShardReducer`'s ctor have proven nonzero. Only the *upper* bound is missing (bc1-3).
- **Narrowing casts** — `manifestRefFromFields` range-checks against `kMaxManifestOrdinal` *before* `static_cast<uint32_t>` (`Formats/CasWireVocab.cpp:88-94`); `Layout::parseManifestKey`'s hand-rolled `ordinal = ordinal * 10 + …` is bounded by a fixed 6-digit field (`Formats/CasLayout.cpp:217-229`); `static_cast<uint32_t>(meta.blob_header_len)` is bounded by `validatePoolBlobHeaderLen`.
- **Strict key parsers** — `parseCanonicalU64` (`Formats/CasLayout.cpp:12-24`), `parseRefTxnId` (fixed 16-hex-digit fields, `Primitives/CasTypes.h:231-260`) and `tryParseManifestRef` (`:133-160`) are all range- and canonicality-safe.
- **Exact size reconciliation on the write path** — `resurrect` compares streamed bytes with the declared payload size in both modes and publishes nothing on mismatch (`Backend/CasObjectStorageBackend.cpp:827-847`, `Backend/CasInMemoryBackend.cpp:296-299`); `observeAndAdmit` refuses `hr.size < header_len` before subtracting (`Pool/CasPartWriteTxn.cpp:253-257`); `retiredLogicalSize` does the same (`Gc/CasGc.cpp:268-277`).
- **Decompression bomb caps** — `openObject` rejects a declared zstd content size above the per-format `object_cap` before `out.resize(content)`, and rejects the `ZSTD_CONTENTSIZE_UNKNOWN`/`_ERROR` sentinels (`Formats/CasTextFormat.cpp:373-401`); the one format with `object_cap == 0` (`RunFile`) is `PinnedRaw`, so the compressed branch refuses it outright (`Formats/CasFormat.cpp:111`).
- **Hash truncation** — `blobShard` (top 8 digest bytes) and `DigestCodec::shardOf` truncate a uniform hash and are only used for shard routing, never for identity; identity comparisons use the full 32-byte `BlobDigest`. Digest tails beyond the algo width are zeroed by `fromHex`/`fromBytesBE`, so the release-mode-only `chassert` zero-tail checks (`Primitives/CasBlobDigest.h:138-142`) are not load-bearing for reachable inputs.
- **`std::stoull` call sites** are all wrapped in `try/catch` (`Backend/CasObjectStorageBackend.cpp:353-360`, `Gc/CasGc.cpp:1092-1099`, `:1173-1180`, `:2794-2800`); the defect in bc1-4 is the values `stoull` accepts *without* throwing, not a missing catch.
- **In-memory COW counters** — `RefCowMap::size()` / `RefCowManifestSet::size()` (`Pool/CasRefCowMap.h:70`, `Pool/CasRefCowManifestSet.h:27`) mix `int64_t net_delta` with a `size_t` base, but the delta is maintained locally per insert/erase and is verified against a full rescan in debug builds (`Pool/CasRefProtocol.cpp:362-386`); the same holds for `snapshot_body_bytes`/`removal_body_bytes`, whose `-=` is always paired with a preceding successful `erase` of the row whose size is being subtracted.
- **Range clamping in the backend** — `readObjectRanged` returns empty for `range.offset >= object_size` and clamps `to_read` to `object_size - range.offset` (`Backend/CasObjectStorageBackend.cpp:298-309`); only the `setReadUntilPosition` sum is unclamped (folded into bc1-1).

Method: static reasoning only. Nothing was built, run, checked out or modified; no test exists in the working tree to confirm any trigger, so every finding above is argued from the cited source lines alone.
