# datatype-agnosticism -- fresh audit 2026-08-12

## Scope

Target: `/Volumes/workspace/altinity-clickhouse/ClickHouse`, branch `cas-code-only-strip`, base `842f2b37b8f`, working tree as-is (all CAS tests deleted). CAS root: `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/`.

Question: CAS presents itself as a byte-level part-file store. Is it genuinely agnostic to column types, serializations and stream-file naming, or do data-type-specific assumptions leak in?

Read in full or in the relevant part: `ContentAddressedTransaction.{h,cpp}` (write classification, inline/blob buffers, commit/publish), `Parts/PartPathParser.{h,cpp}`, `Parts/PartFolderAccess.cpp`, `Formats/CasPartManifestFormat.cpp`, `Formats/CasFormat.cpp`, `Formats/CasTextFormat.{h,cpp}`, `Formats/CasLayout.{h,cpp}`, `Pool/CasPartWriteTxn.cpp` (caps), `ContentAddressedMetadataStorage.cpp` (read paths), plus placement handling in `Gc/` and `Tools/`. Cross-checked against the real MergeTree stream/file-name space in `src/DataTypes/Serializations/ISerialization.cpp`, `src/Storages/MergeTree/MergeTreeIndexGranularityInfo.cpp`, `MergeTreeIndicesSerialization.h`, `MergeTreeIndexText.cpp`, `MergeTreeIndexMinMax.h`, `MergeTreeIndexVectorSimilarity.*`, `IMergeTreeDataPart.h`, `MergeTreeSettings.cpp`, `Common/escapeForFileName.cpp`.

Static reasoning only; no build, no run. Siblings own the two facts "placement is decided by filename suffix only" and "the inline caps can be tripped by many small files"; this report cites them rather than restating them, and concentrates on *which* real type- and index-driven file kinds fall on the wrong side of that suffix decision.

## Filename/stream-name handling as implemented   <- with anchors

There is exactly one place in CAS where a part file's *name* changes its treatment:

```65:73:src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/ContentAddressedTransaction.cpp
bool partFileMustStayBlob(std::string_view file_name)
{
    if (file_name == "primary.idx")
        return true;
    for (std::string_view suffix : {".bin", ".mrk", ".mrk2", ".mrk3", ".cmrk", ".cmrk2", ".cmrk3"})
        if (hasSuffix(file_name, suffix))
            return true;
    return false;
}
```

It is consulted in two places, both in `ContentAddressedTransaction.cpp`:

- `writeFile` (:598) — true ⇒ the streaming, content-hashing blob path, including the S3-staging fast path with adaptive buffers (:602-:623) or a scratch-file variant (:625-:635). False ⇒ `CaInlineWriteBuffer` (:638-:670), which accumulates the whole file in a `std::string` (:1336-:1341, `finalizeImpl` at :1343-:1348), then either embeds it in the part manifest if it is `<= INLINE_CAP` (1 MiB, :92 and :643) or, above that, materialises it into a local scratch temp file and stages it as a blob (:657-:667).
- `tryCreateWriteBuffer` (:539-:544) — the guard that rejects `autocommit` (i.e. non-transactional `IDisk::writeFile`) writes to part files. It only rejects files the allowlist recognises; everything else is allowed to autocommit a single-file publish through `publishStaging` (:244-:310).

Everything else is name-blind. Path parsing (`PartPathParser.cpp:187-:210`) only splits on `/` and locates the `store/xxx/<uuid>/<part>` anchor; the remainder is carried verbatim as `PartFilePath::file`. Manifest entry paths are opaque byte strings, JSON-escaped on write (`Formats/CasTextFormat.cpp:58-:99`, including control bytes, `"` , `\` and U+2028/9), validated only for emptiness / leading `/` / `.` / `..` segments (`CasPartManifestFormat.cpp:184-:193`), and ordered/deduplicated bytewise (:77-:81, :236-:239). Object keys never contain a file name at all — blobs are keyed by digest only (`CasLayout.cpp:28-:36`). The only other name-derived branch is projection-directory detection on the `.proj` / `.tmp_proj` suffix (`PartFolderAccess.cpp:68-:78`, `ContentAddressedTransaction.cpp:895`).

The real space of names this must cover, as shipped in this fork:

- Column substreams: `.null`, `.size<N>`, `.size`, `.dict`, `.dict_prefix`, `.sparse`, `.sparse.idx`, `.repl`, `.repl.idx`, `%2E`-escaped Tuple elements, Variant elements/`variant_discr`/`variant_offsets`, Dynamic `dynamic_structure`, and the whole `object_shared_data.*` family (`ISerialization.cpp:309-:399`). All of these are *stream name* fragments; the file always ends in `.bin` or the marks extension, so they are classified correctly.
- Marks extension is `".mrk"`/`".cmrk"` plus `""|2|3|4` (`MergeTreeIndexGranularityInfo.cpp:82-:102`); `4` = Compact part with per-substream marks.
- Primary index is `"primary" + (compress_primary_key ? ".cidx" : ".idx")` (`IMergeTreeDataPart.h:863`, `MergeTreeDataPartWriterOnDisk.cpp:115`, :343).
- Secondary indexes: `skp_idx_<name>[<suffix>]<ext>` with `ext` ∈ {`.idx`, `.idx2`} (`MergeTreeIndices.h:266`, `MergeTreeIndexMinMax.h:89`), text indexes adding `.dct`/`.pst`/`.pos` suffixes (`MergeTreeIndexText.cpp:1737-:1749`), plus the per-part archive `skp_idx.packed` (`MergeTreeIndicesSerialization.h:11-:16`).

## Findings

### datatype-agnosticism-1 -- Compact-part marks (`.cmrk4`/`.mrk4`) are not in the blob allowlist (High)

- **Anchor**: `ContentAddressedTransaction.cpp:69` (allowlist stops at `3`) vs `src/Storages/MergeTree/MergeTreeIndexGranularityInfo.cpp:98` (`return res + (with_substreams ? "4" : "3")`).
- **Trigger (schema/type)**: any table under default settings. `write_marks_for_substreams_in_compact_parts = true` (`MergeTreeSettings.cpp:405`) and `compress_marks = true` (:2117) make the marks file of every Compact part `data.cmrk4`. Compact is the default part type for parts below `min_bytes_for_wide_part`, i.e. the large majority of parts produced by ordinary inserts. The gap widens exactly with type complexity: mark size for Compact is `8 * (substreams * 2 + 1)` per granule (`MergeTreeIndexGranularityInfo.cpp:getAdaptiveMrkSizeCompact`), so `Tuple`/`Nested`/`Map`/`JSON`/`Dynamic` schemas with hundreds or thousands of substreams make `data.cmrk4` the dominant non-`.bin` file in the part.
- **Consequence**: the marks stream of nearly every part is treated as inline metadata rather than content. It is (a) buffered whole in memory instead of streamed (`:1336-:1341`), (b) embedded in the part manifest when `<= 1 MiB`, so it is never content-addressed — identical marks on two replicas or across a re-created part are stored twice, which is precisely the deduplication the layer exists to provide, (c) charged to the 16 MiB per-manifest inline budget (`Pool/CasPartWriteTxn.cpp:526`, cap at :54) and to the part-folder view cache, whose accounting is `256 + manifest_size` (`Parts/PartFolderAccess.cpp:128-:131`), so every part load transfers and caches the marks bytes even when only one column is read, and (d) exempt from the anti-bypass guard at `:539-:544`, so a non-transactional `writeFile` of `data.cmrk4` silently publishes a manifest instead of raising `NOT_IMPLEMENTED` as it would for `data.bin`.
- **Evidence**: the extension `4` is constructed only from `with_substreams` (`MergeTreeIndexGranularityInfo.cpp:58-:63` on parse, :93-:101 on render), and `MarkType` is built from the setting in `MergeTreeIndexGranularityInfo.cpp:119-:127`. No CAS code path treats a `mrk`-containing extension generically; `MarkType::isMarkFileExtension` (`MergeTreeIndexGranularityInfo.cpp:77-:80`, `extension.contains("mrk")`) exists upstream and is not used by CAS.

### datatype-agnosticism-2 -- the `primary.idx` special case is dead code; the shipped name is `primary.cidx` (High)

- **Anchor**: `ContentAddressedTransaction.cpp:67` (`if (file_name == "primary.idx")`) vs `src/Storages/MergeTree/IMergeTreeDataPart.h:863` (`is_compressed_primary_key ? ".cidx" : ".idx"`) and `MergeTreeDataPartWriterOnDisk.cpp:115` (`String index_name = "primary" + getIndexExtension(compress_primary_key);`).
- **Trigger (schema/type)**: any table with a non-empty primary key under default settings — `compress_primary_key = true` (`MergeTreeSettings.cpp:2121`). The single literal in the allowlist therefore never matches a part written by this build; it only matches parts inherited from a `compress_primary_key = 0` table. Size scales with key width and granule count, so a wide `ORDER BY` over `String`/`Tuple` key columns on a large part produces a multi-megabyte `primary.cidx`.
- **Consequence**: the primary index of every part takes the inline route. Below 1 MiB it is embedded in the manifest — not content-addressed, duplicated per replica, and pulled into memory on every part load together with the manifest. Above 1 MiB it takes the overflow path at `:655-:669`, which buffers the whole file in RAM and then writes it to `metadata_storage.scratchPath()` on the **local** filesystem, bypassing the S3 staging backend that the blob branch selects at `:602`. On a node configured for S3 staging with a small local disk, a large primary index is the one file that still demands local space. The autocommit guard hole described in finding 1 applies identically.
- **Evidence**: `getIndexExtensionFromFilesystem` (`IMergeTreeDataPart.cpp:150-:156`) probes `.cidx` first, and `IMergeTreeDataPart.cpp:2480-:2513` treats both names as valid, confirming `.cidx` is the primary on-disk spelling and `.idx` the legacy one. CAS knows only the legacy one.

### datatype-agnosticism-3 -- secondary-index data files (`.idx`, `.idx2`, `.dct.idx`, `.pst.idx`, `.pos.idx`, `skp_idx.packed`) take the fully in-memory inline route (High)

- **Anchor**: `ContentAddressedTransaction.cpp:69` (no index extension in the allowlist) → `:638-:670` (`CaInlineWriteBuffer`) → `:1336-:1341` (`accumulated.append(...)`, unbounded) → `:657-:667` (spill to local scratch above 1 MiB).
- **Trigger (schema/type)**:
  - `INDEX v_idx v TYPE vector_similarity(...)` (`src/Storages/MergeTree/MergeTreeIndexVectorSimilarity.cpp`, default substream `{Regular, "", ".idx"}` from `MergeTreeIndices.h:266`): the serialised HNSW graph for a part is a single `skp_idx_v_idx.idx` file that scales with rows × dimensions — hundreds of megabytes to gigabytes for one part.
  - `INDEX t_idx s TYPE text(...)`: `MergeTreeIndexText.cpp:1737-:1749` emits `skp_idx_t_idx.idx`, `.dct.idx`, `.pst.idx` and optionally `.pos.idx`; the postings substream is explicitly the unbounded one (it is not even write-buffer compressed, `MergeTreeIndicesSerialization.h:51-:56`).
  - `INDEX b_idx s TYPE tokenbf_v1(...)`/`ngrambf_v1`/`bloom_filter`: `.idx` bloom filters sized by `granules × filter_size`.
  - `TYPE minmax` → `.idx2` (`MergeTreeIndexMinMax.h:89`).
  - `packed_skip_index_max_bytes > 0` (`MergeTreeSettings.cpp:1952-:1969`) → one `skp_idx.packed` archive per part whose size is roughly `threshold × packed substream count`.
- **Consequence**: writing a part with any of these indexes drives RSS by the *full size of the largest index file* per concurrent write — the buffer has no spill-while-writing behaviour, it appends to a single `std::string` until `finalizeImpl`, and the overflow branch then makes a second full copy through `WriteBufferFromFile` at `:660-:663` before hashing. A merge that rebuilds a gigabyte-scale vector or text index on a CAS disk is an out-of-memory candidate where the same merge on a plain object-storage disk streams. Secondary effects match finding 2: the configured S3 staging backend is bypassed (local scratch is mandatory), the hash is computed over a whole in-memory buffer (`:642`, `poolContentHash`) instead of incrementally, and `use_adaptive_write_buffer` / `adaptive_write_buffer_initial_size` (honoured at `:615-:616`, `:629-:630` only on the blob branch) are ignored.
- **Evidence**: `CaInlineWriteBuffer` has no size limit and no sink other than `accumulated` (`ContentAddressedTransaction.h`, member `std::string accumulated`; `:1336-:1348`). The blob branch is the only one with a streaming sink (`Cas::CaContentWriteBuffer`, `:609-:635`).

### datatype-agnosticism-4 -- the placement decision is a closed extension allowlist with no diagnostic for unknown kinds (Medium)

- **Anchor**: `ContentAddressedTransaction.cpp:65-:73` is the entire classifier; `:598` and `:539` are its only consumers. There is no `else` branch that logs, meters or rejects an unrecognised part-file extension anywhere in the CAS tree (a targeted search over the CAS directory finds no other filename-derived branch besides `.proj`/`.tmp_proj` and the CAS-internal `.meta`/`.zst`/`/mount` suffixes).
- **Trigger (schema/type)**: any future or optional data-type / index feature that introduces a file extension. This fork already demonstrates the mechanism three times over (`4` marks, `.cidx`, index substream extensions), and the extension set is explicitly declared to be *versioned per substream* — "Extension of the index substream's file with data. Encodes the serialization version (`.idx`, `idx2`, etc.)" (`MergeTreeIndicesSerialization.h:48`) — i.e. it is designed to grow.
- **Consequence**: new file kinds fail silently in the direction of "small metadata": in-memory buffering, manifest embedding, loss of deduplication, consumption of the inline budget, and loss of the write-path bypass guard. Nothing surfaces the misclassification; `system.content_addressed_log` and `cas-fsck` classify by `EntryPlacement`, not by name, so an inlined index file looks perfectly healthy.
- **Evidence**: `Gc/CasGc.cpp:1000`, `Gc/CasOrphanManifestSweep.cpp:711`, `Tools/CasFsck.cpp:163`, `:552`, `:731` all branch on `e.placement`, never on `e.path`, so no downstream component can notice that a data file was placed inline.

### datatype-agnosticism-5 -- the per-manifest inline budget is consumed by row-count-scaled index/marks data, making the failure schema-dependent (Medium)

- **Anchor**: `Pool/CasPartWriteTxn.cpp:52-:55` (`kMaxLargestInlineEntryBytes = 1 MiB`, `kMaxManifestInlineBytesTotal = 16 MiB`), enforced at `:511-:528` with `ErrorCodes::LIMIT_EXCEEDED`.
- **Trigger (schema/type)**: because of findings 1-3 the inline set is not "a handful of small text files" but `primary.cidx` + `data.cmrk4` + every skip-index substream. Each entry is individually capped at 1 MiB by the disk-side overflow at `ContentAddressedTransaction.cpp:643`, so the reachable failure is the 16 MiB *total*: e.g. ~20 `minmax` indexes on a part with ~50-60k granules (each `.idx2` a few hundred KiB to just under 1 MiB), or a schema with `add_minmax_index_for_numeric_columns`-style breadth, or a `JSON`/`Dynamic` column whose `serialization.json`, `columns_substreams.txt` and per-substream marks are all inline. The total is a function of the *schema* and of the part's row count, not of any bounded metadata.
- **Consequence**: `stageManifest` throws `LIMIT_EXCEEDED` at commit, i.e. after all the data has been written and hashed. For a merge this is deterministic and self-repeating: the same merge is retried and fails again, so the part never becomes wide/merged, while a plain object-storage disk accepts it. The cap itself is a sibling finding ("inline caps can be tripped by many small files"); what is added here is that the *population* of inline files is type- and index-driven and grows with data volume, so the cap is reachable by ordinary schemas rather than by pathological file counts.
- **Evidence**: the write path never re-classifies by aggregate size — `stageBlobPartFile` (`ContentAddressedTransaction.cpp:497-:512`) and the inline branch make per-file decisions only, and `stageManifest` is the first place the totals are seen (`CasPartWriteTxn.cpp:514-:528`), by which point the transaction can only fail.

### datatype-agnosticism-6 -- the manifest payload-zone banner is a raw, unescaped, newline-delimited echo of the entry path (Low)

- **Anchor**: `Formats/CasPartManifestFormat.cpp:64-:67` (`bannerFor` = `"==> " + path + " il=" + n + " <=="`, appended raw at :106-:110) and the decoder's `readLine` + exact-string comparison at :248-:252. The entry-path validator at :184-:193 rejects only empty paths, a leading `/`, and empty/`.`/`..` segments — not LF.
- **Trigger (schema/type)**: any part file whose name contains a raw `\n`. Record lines are safe (JSON-escaped at `CasTextFormat.cpp:78`), so the asymmetry is confined to the banner: a path with LF encodes into a manifest that no reader can ever decode ("payload-zone banner mismatch"), i.e. a permanently unreadable part that `cas-fsck` can only report. I could not construct a reachable trigger in this fork — column names are `%XX`-escaped (`Common/escapeForFileName.cpp:18-:25`, so LF → `%0A`), and the unescaped name sources (Variant element names at `ISerialization.cpp:350-:361`, forced unescaped by `SerializationObjectSharedData.cpp:312`, :968) are type names rendered through quoted-string escaping (`DataTypeEnum.cpp:64`). Hence Low, and reported only because the invariant lives entirely outside CAS.
- **Consequence**: CAS's manifest format is byte-transparent for entry paths in the record zone but not in the payload zone, and nothing in CAS enforces the difference. Any future serialization that emits a raw control byte in a stream name turns a write into an unrecoverable read failure rather than a rejected write.
- **Evidence**: `encodePartManifest` performs no validation of `e.path` at all (:71-:113); validation exists only on the decode side (:184-:193) and does not cover the byte that actually breaks the format.

## Checked and sound

- **No filename-derived semantics beyond placement.** Nothing splits a file name on `.` and indexes a fixed position; nothing infers "is a data stream" from `.bin`. `PartPathParser.cpp:187-:210` treats the in-part path as an opaque tail, and `parsePartFilePath` re-joins multi-segment tails verbatim (:199-:202), so projection subdirectories and any future nesting survive.
- **Column names never reach an object key.** Blob keys are `blobs/<algo>/<2-hex-shard>/<hex-digest>` (`CasLayout.cpp:28-:31`, `shardedKey` in `CasLayout.h:264-:270`); manifest keys are namespace + txn + ordinal (`CasLayout.h:139-:145`). So long `%2E`/`%D0%9F`-escaped names, unicode, dashes and dots create no object-key length or charset exposure — a genuine strength relative to a `plain_rewritable`-style layout.
- **Escape-collision safety.** Entry paths are compared and ordered bytewise with a duplicate check on encode (`CasPartManifestFormat.cpp:77-:81`) and a strict-ascending check on decode (:236-:239), and looked up by exact `std::string_view` equality (`findEntry`, :291-:298). Two column names that differ only in case, or a name that escapes to something resembling another file, cannot be silently merged; they either differ (distinct entries) or are byte-identical (rejected as a duplicate). `escapeForFileName` mapping `.` → `%2E` (`escapeForFileName.cpp:18-:25`) also means no column-derived file can spoof the `.proj`/`.tmp_proj` directory suffix (`PartFolderAccess.cpp:75`) or a metadata name such as `count.txt`.
- **Control-byte-safe record encoding.** `CasJsonWriter::stringValue` (`CasTextFormat.cpp:58-:99`) escapes `"`, `\`, `\b\f\n\r\t`, all remaining control bytes as `\u00XX`, and U+2028/U+2029, so arbitrary escaped or unescaped stream-name bytes round-trip through the record zone (the payload-zone banner is the exception, finding 6).
- **Manifest line cap not reachable in the default config.** `PartManifest` traits are `object_cap = 256 MiB`, `line_cap = 64 KiB` (`Formats/CasFormat.cpp:110`); upstream caps stream file names at `max_file_name_length = 127` with `replace_long_file_name_to_hash = true` (`MergeTreeSettings.cpp:201`, :210), replacing longer names with a SipHash. Deep `Tuple`/`Nested` nesting and very long unicode names therefore cannot push a record line past the cap unless an operator disables that setting.
- **Entry-count fan-out is amply provisioned.** `kMaxManifestEntries = 1,048,576` (`CasPartWriteTxn.cpp:52`) versus a wide part's `2-3 files × substreams`; `Map`/`Nested`/`Array(Nullable(...))`/`JSON` fan-out (`ISerialization.cpp:309-:399`) does not approach it.
- **Read path is placement-agnostic.** `prepareInManifestRead` (`ContentAddressedMetadataStorage.cpp:1402-:1417`) serves inline entries from memory and `getBlobViewPlan` (:1419-:1445) serves blob entries with an offset window; `getStorageObjects`/`getStorageObjectsIfExist` (:1308-:1372) handle both. Nothing on the read side assumes a placement from the extension, so the misclassifications above degrade behaviour without corrupting reads.
- **GC, fsck and inspect classify by placement, not by name** (`Gc/CasGc.cpp:981`, :1000; `Gc/CasOrphanManifestSweep.cpp:711`; `Tools/CasFsck.cpp:163`, :552, :731; `Pool/CasManifestReader.cpp:137`), so inline entries are correctly excluded from blob in-degree and reachability.
- **Per-column codecs and encryption are transparent.** CAS hashes the bytes it is handed, after the column's `CODEC(...)` chain, and stores no type or codec metadata per entry (`ManifestEntry` carries path, placement, digest, size only). `CompressionCodecEncrypted` derives its nonce from configuration rather than randomly (`src/Compression/CompressionCodecEncrypted.cpp:84-:86`, :267-:281), so identical plaintext still deduplicates; only a key-id difference between replicas would degrade dedup, which is a property of the codec, not a CAS assumption.
- **No per-file size ceiling for a single huge stream.** Blob promotion goes through `copyObjectConditional` (`Backend/CasObjectStorageBackend.cpp:789-:812`), which reaches `copyS3File` with the `If-None-Match: *` precondition threaded through both the single-operation and multipart-complete paths (`src/IO/S3/copyS3File.cpp:696-:806`), so a `.bin` stream larger than the single-copy limit is not a special case. `blob_size` is `uint64`, and the offset arithmetic in `getBlobViewPlan` is 64-bit.
- **All type substream files land on the correct side of the allowlist** — `.null`, `.size<N>`, `.dict`, `.sparse.idx`, `.repl.idx`, Variant/Dynamic/JSON `object_shared_data.*` fragments are stream-name fragments that always receive `.bin` or the marks extension (`ISerialization.cpp:309-:399`), so `Array`, `Map`, `Tuple`, `Nullable`, `LowCardinality`, `Variant`, `Dynamic` and `JSON` data streams are classified as blobs. Their marks are misclassified only through the `.cmrk4` gap of finding 1.

## Coverage

Covered: the single filename classifier and both of its call sites; the inline and blob write buffers and their overflow/staging asymmetry; manifest encode/decode including path validation, ordering, escaping, payload zone and caps; layout/object-key construction; the read paths for both placements; placement handling in GC/fsck/inspect; and the upstream file-name space (column substreams for every composite and special type present in this fork, mark type extensions, primary-index extension, all secondary-index substream extensions including the packed archive, name escaping and long-name hashing).

Not covered: anything requiring execution (actual RSS, actual manifest sizes, actual failure messages); the GC/ref-ledger protocols and concurrency, crash consistency, and upgrade compatibility (sibling audits); the fetch/exchange protocol in `DataPartsExchange.cpp` beyond confirming it contains no CAS-specific filename logic; projection and mutation rename flows beyond the `.tmp_proj` → `.proj` transition; and non-MergeTree writers on a CAS disk. Findings 1-3 share one root cause and one fix site, so they should be triaged together; findings 5 and 6 are consequences that persist even if the allowlist is corrected only for today's extension set.
