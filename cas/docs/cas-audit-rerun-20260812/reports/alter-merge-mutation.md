## Findings

### alter-merge-mutation-1 -- every hardlinked file re-reads the source part manifest from the object store (High)

- **Anchor**: `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/ContentAddressedTransaction.cpp:816` (`getView(src->refKey(), Cas::Freshness::ForceFresh)` inside `createHardLink`); `Parts/PartFolderAccess.cpp:172-190` (the `ForceFresh` cache short-circuit is entered only when `validate.mode != Always`) and `:234-235` (`buildView` calls `readManifestShared` for every non-`CachedForLoad` request); `ContentAddressedSettings.cpp:55` (`part_folder_validate` defaults to `"always"`); `Pool/CasManifestReader.cpp:56-78` (one `backend.head()` per read, before any cache lookup); `Parts/PartFolderAccess.cpp:213` + `:217-229` (one `RefResolve` event per call). Contrast `ContentAddressedTransaction.cpp:1081-1086`, where `unlinkFile` memoizes exactly this proof in `force_fresh_validated_refs`; `createHardLink` never consults or fills that set.
- **Trigger**: any mutation, clone or freeze of a committed part on a CAS disk. `ALTER TABLE t UPDATE c = ... WHERE ...` on a wide part drives `MutateTask.cpp:2461` and `MutateTask.cpp:2497` (plus `:2522` per projection file) once per unchanged file; `ALTER TABLE t FREEZE PARTITION p` drives the same call through `Backup.cpp:70-71` under the transaction created at `DataPartStorageOnDiskBase.cpp:530-533`; `ATTACH`/`REPLACE PARTITION` drive it through `MergeTreeData.cpp:9640-9646`.
- **Consequence**: cost, not correctness. Per hardlinked file the disk performs one uncached ref resolve plus one object-store `HEAD` of the manifest key (and a body `GET` on the first miss), all serialized on the mutate/merge thread, plus one `system.cas_log` row. A part with 500 columns (≈1500 stream files) costs ≈1500 sequential round trips per mutated part and ≈1500 audit rows; the same source manifest is fetched 1500 times. FREEZE of a large partition multiplies that by the part count. The whole loop only needs one view of one manifest.
- **Evidence**: `createHardLink`'s committed-source branch resolves and re-reads per call with no per-transaction memo; the identical proof is memoized one function away for `unlinkFile`; `readManifestShared` issues `head(key)` before consulting `manifest_cache`, so even a decode-cache hit costs a network round trip; the default `part_folder_validate=always` disables the only `ForceFresh` cache path.

### alter-merge-mutation-2 -- `always_use_copy_instead_of_hardlinks` turns every mutation into a permanent NOT_IMPLEMENTED failure (Medium)

- **Anchor**: `MutateTask.cpp:2490-2494` and `:2513-2517` (`copyFileFrom` when the setting is on) and `MutateTask.cpp:3306-3311` (`clone_params.copy_instead_of_hardlink` from the same setting) → `DataPartStorageOnDiskFull.cpp:338-354` → `DiskObjectStorage.cpp:291-316` → `DiskObjectStorageTransaction.cpp:507-510` (`metadata_transaction->generateObjectKeyForPath`) → `ContentAddressedTransaction.cpp:363-366` → `notYet()` at `ContentAddressedTransaction.cpp:83-90`. The same route is reachable from `Backup.cpp:61-67` for `files_to_copy_instead_of_hardlinks`. No gate exists: `MergeTreeSettings.cpp:1902` declares the setting with no CAS check, and the two immutable-disk guards (`MergeTreeData.cpp:4585-4589`, `:5083-5085`) pass because CAS reports `supportsHardLinks() == true`.
- **Trigger**: `ALTER TABLE t MODIFY SETTING always_use_copy_instead_of_hardlinks = 1` (accepted silently) followed by any `ALTER TABLE t UPDATE/DELETE`, `MATERIALIZE INDEX`, `ATTACH/REPLACE PARTITION`, or `FREEZE`.
- **Consequence**: the mutation fails at execution time with `NOT_IMPLEMENTED` and is retried forever by the background pool (a replicated table wedges its queue entry). The refusal is loud but wrong in attribution: the shipped text blames "a layer that bypasses the content-addressed write path" and names an internal method, whereas the operator's actionable cause is a table setting. It is also late — accepted at ALTER time, failing at mutate time.
- **Evidence**: `copyFileImpl` unconditionally calls `generateObjectKeyForPath` on the destination metadata transaction; CAS implements that method as `notYet`; nothing between the setting and the call filters on `isContentAddressed()`.

### alter-merge-mutation-3 -- an aborted mutation leaks its S3 staging objects until the next mount (Medium)

- **Anchor**: `ContentAddressedTransaction.cpp:148-171` — `cleanupPendingTempFiles` deletes local scratch files unconditionally but deletes an S3 staging object only `else if (committed)` (`:159`); the destructor calls it on the abort path too (`:101-103`). Reclamation otherwise happens only at mount start, `ContentAddressedMetadataStorage.cpp:606-608` (`sweepOwnMountStaging`), or in decommission (`Tools/CasDecommission.cpp:198-199`). No GC phase sweeps the staging prefix.
- **Trigger**: `staging_backend=s3` on a bucket with conditional copy, then `KILL MUTATION` (or any exception/cancellation) after column blobs have been streamed to staging but before `commit()`; likewise a cancelled merge.
- **Consequence**: the staged objects (full size of the rewritten columns) stay in the bucket, unreferenced by any manifest, invisible to GC accounting, and are reclaimed only by a server restart of the same mount. Repeated killed mutations accumulate cost with no operator-visible counter.
- **Evidence**: the `committed` condition on the removal branch is the only difference between the local and S3 backends; the sweeper is wired exclusively into `startup()`.

### alter-merge-mutation-4 -- the temp text-index directory lives inside the part, publishes a ref early, and its cleanup is a silent no-op (Medium)

- **Anchor**: `TextIndexUtils.cpp:601-609` — the temp storage is `DataPartStorageOnDiskFull(volume, <part relative path>, "text_index_tmp")` with its **own** `beginTransaction()`, i.e. a sibling directory *inside* the part directory. It is committed separately at `MutateTask.cpp:1939-1941` and `MergeTask.cpp:2235-2236`, and cleaned at `MutateTask.cpp:2012-2014` / `MergeTask.cpp:2311-2313` via `removeRecursive()` → `DataPartStorageOnDiskBase.cpp:1106-1109`. On CAS that path parses as (ref = `tmp_mut_*`/`tmp_merge_*`, file = `text_index_tmp`) (`PartPathParser.cpp:187-210`) and hits the bare `return` at `ContentAddressedTransaction.cpp:764-765`.
- **Trigger**: `ALTER TABLE t MATERIALIZE INDEX idx` for a `text` index, or any merge that rebuilds a text index (`MergeTask.cpp:2843-2847`), on a CAS disk.
- **Consequence**: (a) the intended cleanup never happens — the `text_index_tmp/*` entries survive in the temporary part's manifest, and they disappear only incidentally because the later rename drops the whole temporary ref (`ContentAddressedTransaction.cpp:955-959`); (b) the temporary index segments are published into the pool as immutable blobs plus a manifest and a ref-log entry, then immediately become GC garbage, so a materialize costs one extra manifest publish and an upload+download of every segment instead of using local scratch; (c) if the operation is cancelled between the temp-index commit and the rename, a *live* ref named `tmp_mut_…`/`tmp_merge_…` remains in the table namespace and is listed as a part directory until the temporary-directory cleaner runs.
- **Evidence**: the temp storage takes its own disk transaction and commits it while the enclosing part transaction is still open, so the temporary part name becomes a committed CAS ref; `removeRecursive` has no branch for a directory *inside* a part and returns without touching the manifest.

### alter-merge-mutation-5 -- REPLACE/ATTACH PARTITION writes `metadata_version.txt` twice on CAS, the second time as a repoint of a committed ref (Medium)

- **Anchor**: `DataPartStorageOnDiskBase.cpp:530-533` forces an owned transaction whenever `disk->isContentAddressed()`, so the `if (clone_transaction)` branch at `:556-575` writes `metadata_version.txt` **inside** the clone transaction, which is committed at `:584`. `MergeTreeData.cpp:9667-9674` then writes the same file again, now with no active transaction, so it takes the autocommit route (`ContentAddressedTransaction.cpp:539-550`) and republishes the whole manifest through `repointRef` (`ContentAddressedTransaction.cpp:256-290`, `PartFolderAccess.cpp:442-473`). On a non-CAS disk without an external transaction there is no owned transaction, so only the second write happens — the double write is CAS-specific.
- **Trigger**: `ALTER TABLE dst REPLACE PARTITION p FROM src` / `ATTACH PARTITION FROM` / `MOVE PARTITION TO TABLE` on a ReplicatedMergeTree over CAS (`StorageReplicatedMergeTree.cpp:3347`, `:9210`, `:9501` set `metadata_version_to_write`).
- **Consequence**: per cloned part, two manifest objects and an extra repoint of a ref that was committed microseconds earlier, plus a `Repointed committed ref … standalone write/remove on a committed part` log line per part (`PartFolderAccess.cpp:461-463`) that reads like an anomaly during a perfectly normal ATTACH. Between the two commits the clone carries no `metadata_version.txt` at all (the first `removeFileIfExists` at `:561` already ran with `keep_metadata_version=false`), and per the cited sibling the repoint is not revertible by the commit-failure rollback.
- **Evidence**: both write sites are unconditional for the CAS case; the freeze-internal write is gated only on `clone_transaction` being non-null, which CAS guarantees.

### alter-merge-mutation-6 -- FREEZE/UNFREEZE shadow namespaces are not scoped by `server_root_id`, so mounts sharing a pool delete each other's frozen parts (Medium)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:886-889` — live namespaces are `serverPrefix() + "/" + …`; `:897-900` — `shadowNamespace()` returns `canonicalDiskPath(shadow_table_dir)` with **no** server prefix; `:1458-1463` — `ownsNamespace()` only recognizes namespaces starting with `server_root_id + "/"`, so shadow namespaces are owned by nobody. Removal: `ContentAddressedTransaction.cpp:713-722` drops the named shadow ref or `dropNamespace`s the whole shadow table dir; the callers are `Freeze.cpp:203` (per part) and `Freeze.cpp:176-180` (`SYSTEM UNFREEZE` removing the whole `shadow/<name>/` subtree, which enumerates and drops every namespace under the prefix, `ContentAddressedTransaction.cpp:723-735`). The frozen path itself is srid-free: `MergeTreeData.cpp:9888` builds `shadow/<backup_name>/…` and `:9993-10000` unfreezes by the same path.
- **Trigger**: two servers with distinct `server_root_id` mounted on one pool holding replicas of the same table (same table UUID). `ALTER TABLE t FREEZE WITH NAME 'b'` on both, then `ALTER TABLE t UNFREEZE WITH NAME 'b'` (or `SYSTEM UNFREEZE WITH NAME 'b'`) on either one.
- **Consequence**: the two servers write into one shared namespace with identical ref names. Unfreeze on one mount removes the other mount's frozen refs — the surviving server's `shadow/b` backup silently disappears, and with the last ref gone the blobs become GC-eligible. In the opposite direction, if the two replicas' manifests for a part are not byte-identical the second FREEZE hits the ref-conflict refusal instead of succeeding.
- **Evidence**: the namespace-construction asymmetry between `liveNamespace` and `shadowNamespace` is explicit in the two adjacent functions; `ownsNamespace` cannot attribute a shadow namespace to any mount; unfreeze drops refs/namespaces by name with no owner check.

### alter-merge-mutation-7 -- a no-op mutation costs two publishes and a full per-file adoption pass (Low)

- **Anchor**: `MutateTask.cpp:3305-3322` — when `isStorageTouchedByMutations` reports no affected rows, the part is cloned with `cloneAndLoadDataPart` (→ `freeze()`, which commits its own transaction at `DataPartStorageOnDiskBase.cpp:584`), and only then does `MutateTask.cpp:3320` open a second transaction. The rename of `tmp_clone_*` → final name finds no staged source and takes `ContentAddressedTransaction.cpp:961` → `PartFolderAccess.cpp:419-440`, i.e. read the source manifest, `publishEntries` at the destination, then `dropRef` the source.
- **Trigger**: `ALTER TABLE t UPDATE … WHERE <false for this part>` or `ALTER TABLE t DELETE WHERE <no match>` — the common "mutation version bump" case that touches every part of the table.
- **Consequence**: per untouched part, one adoption pass over every file (finding 1), one manifest for the clone, one more manifest for the republish, and three ref operations — for a mutation that changes nothing but the part name. The republish is also non-atomic: a crash between publish and drop leaves a live `tmp_clone_*` ref, which is reclaimed only by the temporary-directory cleaner.
- **Evidence**: the clone's transaction is committed before the mutation's own transaction exists, which is exactly what forces the rename onto the committed-ref `republishRef` path rather than a single in-transaction promote.

## Checked and sound

- **Adoption is genuinely metadata-only.** Unchanged files in a mutation are re-published by hash (`adoptEvidence` / manifest-entry copy) with no byte re-upload, so mutation write amplification is proportional to the *changed* columns, not to the part (`ContentAddressedTransaction.cpp:782-829`). RENAME COLUMN is a pure entry-path rewrite, and DROP COLUMN is "not adopted".
- **Lightweight ALTER touches no parts.** `writeMetadataVersion` has no callers in this tree, so a metadata-only ALTER performs zero CAS operations — the whole-manifest-republish-per-part risk does not exist for it.
- **Merge output publish is atomic per part.** `precommitTransaction` is a no-op (`DataPartStorageOnDiskFull.h:60`), the tmp→final rename happens inside the still-open transaction, and the commit performs a single `promoteBuild` (`MergeTreeData.cpp:8951-8961`, `ContentAddressedTransaction.cpp:293-310`).
- **Merge/mutation sources are dropped only after the new ref exists**, and because blobs are content-addressed and pool-global, dropping the source ref cannot orphan bytes the new part needs; blob reclamation is left entirely to GC refcounting (`PartFolderAccess.cpp:475-500`).
- **Zero-copy replication is off for CAS** (`DiskObjectStorage.h:51-55`), so the `checksums.txt`-copy branch that would otherwise hit the unimplemented `copyFile` (finding 2) is unreachable via `copy_checksumns` at `MutateTask.cpp:3297`.
- **Projection handling in merge/mutation is coherent**: on CAS the projection storage shares the parent transaction (`MergeTask.cpp:561-564`, `IMergeTreeDataPart.cpp:1360`), so per-projection `commitTransaction()` calls are no-ops and `.tmp_proj`→`.proj` is an in-memory staged-entry prefix rewrite (`ContentAddressedTransaction.cpp:893-906`).
- **The "all rows deleted" empty-part path commits its CAS transaction explicitly** instead of relying on the generic path (`MergeTreeData.cpp:5918-5922`).
- **Part removal never deletes blobs directly.** `removeRecursive` ignores the `files_not_to_remove` predicate and only drops refs, so the `REMOVE_BLOBS` temporary-part policy used by the parts mover cannot destroy bytes shared with a live part (`ContentAddressedTransaction.cpp:705-766`).
- **`truncateFile`, `WriteMode::Append` on part files, and autocommit writes to blob-class part files are refused loudly and correctly** (`ContentAddressedTransaction.cpp:1130-1135`, `:536-544`).
- **Storage-policy metadata operations are inert on CAS**: `createDirectories` is an admission check only, and the "new policy already contains data" probe resolves through namespace presence (`MergeTreeData.cpp:5236-5254`).

## Coverage

Covered: lightweight ALTER and per-part metadata-version flow; heavy ALTER/mutation hardlink-vs-rewrite decision and its cost; merge publish and source-drop ordering; lightweight DELETE and patch parts; projection and secondary-index add/drop/materialize; text-index materialization; TTL variants at the flow level; ALTER PARTITION DROP/DETACH/ATTACH/REPLACE/MOVE/FREEZE/UNFREEZE; mutation cancellation and staging residue; replicated-mutation commit-vs-verification ordering; ALTER MODIFY SETTING for storage policy and for `always_use_copy_instead_of_hardlinks`; the ClickHouse-side ALTER/mutation gates.

Not covered here (owned by siblings or out of scope for a static pass): FETCH PARTITION and the interserver relink protocol; cross-pool/cross-disk ATTACH; GC round mechanics and reclamation timing for the garbage this audit's flows produce; concurrency interleavings between a mutation and a concurrent GC/fsck; ref-log/precommit crash-consistency; the write-buffer spill sizing for wide merges; run-time confirmation of any cost estimate (no tests exist in this working tree, and no execution was performed).
