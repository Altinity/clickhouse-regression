## Write path as implemented

1. `ContentAddressedTransaction::writeFile` (`ContentAddressedTransaction.cpp:558`) classifies the path. Non-part paths become namespace-file or mountpoint-object writes through `CaInlineWriteBuffer` (`:562-589`); these are *immediate* writes on `finalize()`, outside the part publish protocol.
2. Placement is decided by file name, not size: `partFileMustStayBlob` (`:65-73`) forces `primary.idx` and `*.bin/.mrk*/.cmrk*` down the blob path; everything else is buffered in memory and inlined if `<= INLINE_CAP` (1 MiB, `:92`, `:643-654`), otherwise spilled to a local temp file and staged as a blob (`:655-669`).
3. Blob bytes are hashed while streaming. `CaContentWriteBuffer::finalizeImpl` (`:1276-1295`) takes the hash hex, finalizes the sink, then hands `(hash_hex, size, key)` to `stageBlobPartFile`. Inline bytes are hashed one-shot by `poolContentHash` (`CasPartWriteTxn.cpp:72`). The dedup key *is* the content hash: `BlobRef{algo, digest}` → `layout().blobKey(ref)` (`CasPartWriteTxn.cpp:145`).
4. Two staging backends: S3 staging (`ContentAddressedTransaction.cpp:602-623`, envelope header written up front, `check_fence_before_finalize` captured at buffer construction) or local temp files (`:625-635`). `stageBlobPartFile` (`:497-512`) records a `PendingBlob`, calls `buildFor()` (which lazily opens a `PartWriteTxn` via `Pool::beginPartWrite`, `CasPool.cpp:898`), records a *tokenless* pending dep, and replaces any same-path entry.
5. Nothing durable happens for a part until `commit()` (`:312`). `commit()` iterates `parts` (a `std::map` keyed by `(namespace, ref)`) and calls `publishStaging` per part (`:336-340`).
6. `publishStaging` (`:244`) has two shapes:
   - **New ref**: `stageManifest` → `precommitAdd` → `uploadPendingBlobs` → `promoteBuild` (`:297-309`).
   - **Existing committed ref** (`getView(..., ForceFresh)` non-null, `:258`): stage a *scratch* manifest of only the new entries → precommit it → upload blobs → merge old manifest entries minus `content_removed` with the new ones → `repointRef` (which internally builds a second, independent `PartWriteTxn` and promotes it with `allow_repoint=true`) → `abandon()` the scratch build (`:262-289`).
7. `stageManifest` (`CasPartWriteTxn.cpp:507`) enforces caps (1 M entries, 256 MiB encoded, 16 MiB inline total, 1 MiB per inline entry, ordinal cap), mints `ManifestRef{writer_epoch, build_seq, ordinal}`, canonicalises + seals the body, and writes it with `stagingPutIfAbsent` → `putIfAbsentControlled` (budget, deadline, fence). `DefiniteFailure` and `Unresolved` both fail closed as retry-later.
8. `precommitAdd` (`:576`) sets `precommit_state = Uncertain`, appends an `OwnerTransition{new=Precommit(ref,manifest)}` (plus `NamespaceBirth` if the table is not Live) via `appendRefOps`, then sets `Durable`. The manifest body is durable *before* the precommit edge exists, and the precommit is durable *before* any blob may be adopted — enforced by the `EDGE-BEFORE-OBSERVE` guard in `observeAndAdmit` (`:280-285`).
9. `uploadPendingBlobs` (`ContentAddressedTransaction.cpp:208`) builds one request per manifest-referenced pending blob and calls `fanOutBlobUploads` (`:1152`), which de-duplicates by `BlobRef`, validates declared vs. source size, runs one task per unique ref on `blobUploadPool()`, waits for all, rethrows the first error, and only then merges results into `deps` in one shot (`mergeBlobUploadResults`, `CasPartWriteTxn.cpp:196`, which rejects any tokenless result).
10. `uploadBlobDetached` (`:139`): optional HEAD-first probe (dedup cache hit, or size ≥ `deduplication_head_first_min_bytes`) → adopt the live incarnation; otherwise `uploadFromSource` with up to 8 `ABORTED` retries. `uploadFromSource` (`:307`) does conditional-create (`stagingConditionalCreate` → `conditionalCreateControlled`), then on `Occupied` re-HEADs; absent → retry create, else adopt; condemned meta → `resurrect` (unconditional overwrite) → `writeResurrectMetaClean` (CAS on the freshness meta, 8 attempts).
11. `promote` (`:633`) re-reads the manifest body, checks `refMatchesBody` and `manifestNamespaceMatches` (fail-closed), sets `commit_state = Uncertain`, and appends one ref-log transaction whose ops-builder: refuses if the precommit binding is gone; requires every blob leaf to have either a tokened dep or a trusted adopted dep; on `allow_repoint` emits `RemoveCommitted(old)` + `Promote(precommit→committed)` + `SetPublishedAt` in a *single* transaction (atomic by `applyRefLogTxn`, `CasRefProtocol.cpp:198-270`). Then `commit_state = Durable`, `precommit_state = Settled`, `retireBuildSeq`, and only afterwards the `BuildPublish` event (in a `try`/`catch`).
12. The ref-log append itself (`CasRefLedger::commitRefChunk`, `CasRefLedger.cpp:2245`) re-reads the catalog and requires the exact life to be `Live` for positive appends, arms a single `RefAppendAttempt` per lane, writes it with `putIfAbsentControlled`, publishes the checkpoint frontier *before* installing the transaction in the cached table, and maps outcomes as: `Committed` → install + ack; `DefiniteFailure` → lane back to Ready, id unconsumed, retry-later; `Unresolved` with `NoAttemptSent` → lane Ready, retry-later; any other `Unresolved` → lane **Wedged**, retry-later, resolved later by `resolveWedgeOnce` re-issuing the *same* key/bytes and classifying the occupant. Lost-ACK is therefore treated as unproven, never as failure-with-forgetting.
13. Fencing: `refAppendFenceOk` (`CasMountRuntime.cpp:101`) requires the lease deadline to exceed `attempt_timeout + safety_margin`; `checkFenceOrThrow` (`:90`) compares the fence generation; `PartWriteTxn::requireAlive` (`CasPartWriteTxn.cpp:117`) additionally rejects builds whose `writer_epoch` no longer matches `liveWriterEpoch()` and builds cancelled by `dropNamespace`.
14. Relink (write side): `prepareAdoptFromManifest` (`ContentAddressedMetadataStorage.cpp:1592`) decodes the sender's manifest, `prepareEntries` adopts every entry as a *trusted, tokenless* dep, stages a local manifest and precommits it; the caller then asks the sender to prove it still holds that exact ref (`DataPartsExchange.cpp:1196-1236`) and only then promotes. `Unresolved` promotion is surfaced as "do not fetch the bytes, retry the whole fetch" (`ContentAddressedMetadataStorage.cpp:1542-1567`).

## Findings

### write-protocol-1 -- a repointed committed ref is unrevertible, and `publishStaging` runs a throwable ref-log mutation after the repoint is already durable (High)

- **Anchor**: `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/ContentAddressedTransaction.cpp:280-289` and `:341-348`; `Parts/PartFolderAccess.cpp:457` (`publishEntries(..., allow_repoint=true)`), `:295-297` (`outcome.created = created`); `Pool/CasPartWriteTxn.cpp:661` (`created = !state.getCommitted().contains(final_ref_name)`).
- **Trigger**: any transaction that writes to, or unlinks a file from, a part whose ref is already committed (the `getView(...)` branch at `:258`), where the step after the repoint fails. Minimal case: one part. `repointRef` publishes the merged manifest durably at `:280`; the very next durable operation is `st.build->abandon()` at `:285`, which appends *another* ref-log transaction (`CasPartWriteTxn.cpp:807-821`). Any of the ordinary retry-later conditions on that append — lane wedged by an ambiguous PUT, lease/fence loss, `Removing` admission closed — throws `NETWORK_ERROR`. `commit()` catches at `:341`, sets `failed = true`, and the rollback loop at `:344-347` only drops refs for which `oc->created` is true. For a repoint `created` is false by construction, so **nothing is undone** and the exception is propagated to the caller.
- **Evidence**: the rollback is `if (oc && oc->created) partAccess()->dropRefIfMatches(...)`. `created` is computed inside the promote ops-builder as "the ref had no committed binding", so it is `false` exactly in the repoint case, which is the only case where the transaction *modified* pre-existing committed content. The merged entry list at `:267-275` drops every path in `st.content_removed`, so the durable, unrevertible effect can include *removing* files from a committed part. There is no compensating "repoint back to the old manifest" op anywhere in the tree (`repoint_old` is only used to build the forward transaction at `CasPartWriteTxn.cpp:709-714` and for an event at `:753-774`).
- **Notes**: the same structure also mis-reports the outcome: the durable publish succeeded and the caller is told the commit failed, with `failed = true` making the transaction non-retryable (`:314-316`). The non-repoint branch does not have this shape — `promoteBuild` is its last durable step and the following `st.build.reset()` cannot throw. Fixing this needs either (a) the scratch precommit removal to be folded into the repoint transaction, or (b) an explicit repoint-back compensation recorded in `part_outcomes`.

### write-protocol-2 -- multi-part `commit()` is N independent durable publishes with a best-effort, silently-failing rollback (Medium)

- **Anchor**: `ContentAddressedTransaction.cpp:327-348`; `Parts/PartFolderAccess.cpp:518-562` (`dropRefIfMatches` is `noexcept` and swallows every error).
- **Trigger**: a transaction staging two or more parts (reachable through `createHardLink` between two part directories, `moveFile`/`moveDirectory` across part directories, or plain `writeFile` calls into two part folders on one transaction). Part *i* publishes durably; part *i+1* fails on any retry-later condition; the loop then attempts to drop the earlier refs.
- **Evidence**: each `publishStaging` is its own ref-log transaction (a different lane per namespace, a different txn per ref), so there is no cross-part atomicity at any layer. The compensation is a conditional drop that (i) is skipped for repointed refs (finding 1), (ii) catches all exceptions, increments `CASRefRollbackBestEffortDropFailed`, logs "the ref may remain live" and returns, and (iii) is never retried or queued as a duty (contrast with `enqueueWriterCleanupDuty`, `CasPool.cpp:789`, which *is* a durable retry queue for precommit cleanup). So a failed multi-part commit can leave an arbitrary prefix of the parts published.
- **Notes**: this is inherent to per-ref ref-log transactions, but the gap worth closing is the missing durability of the rollback intent: a `WriterCleanupDuty`-style queued compensation would make the prefix converge instead of depending on one best-effort call.

### write-protocol-3 -- `resurrect` is an unconditional, budget-free, fence-unchecked overwrite that returns a token it did not write (Medium)

- **Anchor**: `Backend/CasObjectStorageBackend.cpp:814-856`; callers `Pool/CasPartWriteTxn.cpp:457-466` and `:470-475`.
- **Trigger**: two writers (or one writer and the tail of a GC delete/re-upload) touching the same condemned blob. Writer A reads `MetaState::Condemned` (`:445-450`), calls `checkFenceOrThrow(fenceGeneration())` — a check against the generation it captured one line earlier at `:452`, so it only asserts "the lease is not currently lost" — and then streams an unconditional `writeObject(..., WriteMode::Rewrite, ..., WriteSettings{})` over the blob key.
- **Evidence**: unlike every other durable write in the pool, this path does not go through `CasRequestController`: no `If-None-Match`/`If-Match`, no attempt budget, no operation deadline, no `SingleAttempt` retry profile (`conditionalWriteSettings()` at `:628-640` is not used), and — critically — **no post-write `fence_ok()` re-check**, which every conditional path performs and reports as `FenceLostPostWrite` (`CasRequestControl.cpp:305-309`, `:349-353`, `:404-411`). The returned token is taken from a *separate* `nativeHead(blob_key)` at `:850`, not from the write, so under a concurrent second resurrect the token handed back to the caller can name another writer's incarnation; that token is what lands in the `BlobDepRecord` and is later relied on for token-exact deletes. A writer whose lease expires mid-stream still completes the overwrite (only the follow-up meta CAS is fenced, `writeResurrectMetaClean` → `stagingConditionalOverwrite`), so the durable residue of a fenced-out writer is a re-created blob body with no matching Clean meta.
- **Notes**: payload bytes are content-addressed, so the *content* at the key cannot change; the exposure is token/incarnation churn and un-deleting a body the live incarnation's GC just reclaimed. `resurrect` in `EmulatedSingleProcess` mode serialises on a function-local `static std::mutex` (`:819`), which protects only within one process — consistent with the calibration that Emulated mode is single-process, but it means the Native path is the only one with real concurrency and it is the unguarded one.

### write-protocol-4 -- inline entries can be staged into a destination part that never gets a build, failing the whole commit closed (Low)

- **Anchor**: `ContentAddressedTransaction.cpp:800-812` (`createHardLink`, staged-source branch) and `:1035-1053` (`moveFile`, cross-part branch); guard that fires at `:293-295`.
- **Trigger**: in one transaction, write a small metadata file (anything not matched by `partFileMustStayBlob`, e.g. `count.txt`/`columns.txt`) into part A, then `createHardLink`/`moveFile`/`replaceFile` it into a part B that is not otherwise written and does not exist as a committed ref. `stagingFor(*dst)` creates the staging map entry, the entry is appended to `dst_st.entries`, but `buildFor` is only called on the `EntryPlacement::Blob` branch. At commit, `publishStaging` finds `st.entries` non-empty, `getView` returns null, and throws `LOGICAL_ERROR: "staged entries or removal marks for {}/{} without a Build"`.
- **Evidence**: `createHardLink` calls `buildFor(*dst, dst_st)` only as an argument to `adoptStagedBlob` inside `if (entry.placement == Blob)`; the `Inline` case falls straight through to `dst_st.entries.push_back`. `moveFile` guards the whole adoption block with `&src_st != &dst_st && entry.placement == Blob`. The committed-source path at `:816-828` does not have the bug (it always calls `buildFor(...).adoptEvidence(...)`).
- **Notes**: fail-closed, so no corruption — but it fails at `commit()`, i.e. after earlier parts in the same transaction may already be durable (see finding 2), and the error class is `LOGICAL_ERROR`, which callers treat as a bug rather than as retryable.

### write-protocol-5 -- dedup/HEAD-first ProfileEvents are emitted before the outcome they claim is decided (Low)

- **Anchor**: `Pool/CasPartWriteTxn.cpp:155-174`.
- **Trigger**: HEAD-first probe hits an existing body whose freshness meta is `Condemned`. `CASBlobHeadFirst`, `CASBlobBodyPutAvoided` and `CASBlobDeduplicationCacheHit` are all incremented at `:155-161`, *then* `observeAndAdmit` throws `ABORTED` at `:275`, the exception is swallowed at `:169-173`, and the code falls through to a full upload/resurrect.
- **Evidence**: `CASBlobBodyPutAvoided` is incremented unconditionally on `hr.exists` before the admit attempt; on the condemned path a body PUT is exactly what happens next. Same shape for the dedup-cache-hit counter.
- **Notes**: observability only — no durable effect, and no ordering hazard (the events are counters, not durable records). Listed because "side effects emitted before durability" is in scope and this is the one instance found on the blob path; every `CasEvent` emission on the publish path is correctly placed after its durable step.

### write-protocol-6 -- the writer-epoch fence on a build is checked only at entry to `promote`, not at the durable append (Low)

- **Anchor**: `Pool/CasPartWriteTxn.cpp:125-128` (`requireAlive`), `:635` (only call in `promote`), `:657-729` (the ops-builder never re-checks the epoch); `Pool/CasPool.cpp:722-740` (self-remount bumps `liveWriterEpoch` and quiesces the ref tables).
- **Trigger**: a build opened under writer epoch E1 enters `promote`, passes `requireAlive`, then blocks in `backend().get(manifest_key)` and in the append queue (bounded only by `operation_deadline_ms`, default 90 s). The mount loses its lease and self-remounts to E2. `appendRefOps` then acquires a *fresh* runtime under the new fence generation and the promote commits — publishing a manifest whose `ManifestRef` carries the superseded epoch E1.
- **Evidence**: the shipped exception text at `:126-128` ("belongs to a superseded mount incarnation … the mount was fenced out and self-remounted; restart the build") and the shipped log at `CasPool.cpp:738-740` ("older builds fail closed") state the intended invariant; nothing enforces it after the entry check. The append-side fences (`admitted_fence_generation`, `superseded_by_remount`, catalog life) are all evaluated against the *new* incarnation, so they do not reject the old build.
- **Notes**: rated Low because the outcome is still consistent — the build's seq stays in `active_build_seqs`/`inflight_builds` across a self-remount (`CasMountRuntime` survives, `:148-167`), so the newborn-blob watermark still protects the deps, and a cross-node takeover is excluded (`mayMutate()` stays false and `tryRemountOnce` refuses when "a live twin holds the lease"). The observable effect is a race with the stale-precommit sweep: whichever of promote/sweep reaches the lane first wins, so the same interleaving is sometimes a clean fail-closed and sometimes a publish.

## By-design / info / non-actionable

- **Lost-ACK on the ref-log append is handled correctly.** `Unresolved` never becomes "failure with the id released" unless `unresolvedProvesNothingWasSent` (`CasRequestControl.h:30-45`) is true, i.e. only `NoAttemptSent`. Everything else wedges the lane on the exact key/bytes and is resolved later by re-issuing the same object and classifying the occupant (`CasRefLedger.cpp:1563-1810`, `2684-2720`). `FenceLostPostWrite` is deliberately reported as unresolved even though the write committed — that is safe-direction.
- **Blob upload retries are idempotent.** `putIfAbsentControlled` re-issues the identical key/bytes and resolves ambiguity by exact GET (`CasRequestControl.cpp:212-239`, `290-303`); `conditionalCreateControlled` resolves an ambiguous attempt by HEAD and reports `Occupied`, which the caller turns into an adopt of the existing incarnation (`CasPartWriteTxn.cpp:432-450`). Because blob keys are content hashes, "someone else's object at my key" is the same bytes.
- **Repoint is atomic.** `RemoveCommitted(old)` + `Promote` + `SetPublishedAt` go in one ref-log transaction and `applyRefLogTxn` applies them on a scratch copy that replaces the state only on success (`CasRefProtocol.cpp:425-430`), and each shape asserts the exact expected binding (`:198-270`). There is no window where the ref names nothing.
- **The unique-ref invariant is enforced.** `promote` with `allow_repoint=false` refuses to overwrite a ref that names a different committed manifest (`CasPartWriteTxn.cpp:697-705`), and `AddPrecommit` refuses a manifest already owned (`CasRefProtocol.cpp:208-212`). Idempotent re-promote of the same manifest returns `{}` (no-op) rather than double-applying.
- **Manifest format is self-checking.** `encodePartManifest` canonicalises the entry order and rejects duplicate paths; `decodePartManifest` re-validates order, path segments, digest widths, trailer count, and the payload digest (`Formats/CasPartManifestFormat.cpp:71-270`). `promote` re-reads and re-validates the body it is about to publish.
- **Budgets exist on the manifest and on ref ops.** `stageManifest` caps entries/size/inline bytes/ordinals; `flushRefBatch` caps per-item op count, per-op encoded bytes, and applies `admits(...)` snapshot/removal budgets before any object is created (`CasRefLedger.cpp:2099-2172`). `clampCasWriteBufferSize` caps write-buffer memory at 256 MiB (`ContentAddressedTransaction.cpp:1144-1149`).
- **Precommit cleanup is durable, not best-effort.** `~PartWriteTxn` enqueues a `WriterCleanupDuty` when the precommit is `Uncertain` or `Durable` (`CasPartWriteTxn.cpp:107-112`), drained before later ref mutations on that namespace (`CasPool.cpp:828-896`), and a failure to enqueue sets `writer_cleanup_queue_failed`, which keeps the build in the active watermark.
- **Leaked S3 staging objects are reclaimed.** `cleanupPendingTempFiles` only deletes S3 staging objects when the transaction committed (`ContentAddressedTransaction.cpp:159-168`), but `sweepOwnMountStaging` (`Pool/CasServerRoot.cpp:1140-1163`) reclaims the mount's own staging prefix at mount start, and `CasDecommission.cpp:198` reclaims a victim's. Local temp files are removed on both paths.
- **Relink/adopt on the write side is a publish-then-confirm handshake.** The receiver's precommit is durable *before* it asks the sender to prove it still holds the exact `(ref, manifest_ref)` binding (`DataPartsExchange.cpp:1196-1236`), pool identity is checked in both directions (`:316`, `:781`), and an unresolved promote is surfaced as "must NOT fetch the bytes, retry later" rather than as failure. `prepareEntries` adopts entries untokened and unverified (`Parts/PartFolderAccess.cpp:399-402`) — that is the manifest-trust model, and every caller has an external liveness argument (sender confirm; source ref for `republishRef`; the live committed view plus the scratch precommit for `repointRef`).
- **Eager-transaction consequences already known.** Namespace-file and mountpoint writes, `dropRefIfPresent`, `dropNamespace` and `republishRef` all take effect at call time, not at `commit()`; `moveDirectory` for `RENAME TABLE` logs an explicit "SPLIT across namespaces / retry re-drives it" warning (`ContentAddressedTransaction.cpp:876-884`). Consistent with the calibrated eager-dispatch behaviour; not re-reported.
- **Not re-reported (already known):** `getStorageObjects` dropping `BlobLocation.offset`; `moveFile`/`replaceFile` requiring a same-transaction staged source (`ContentAddressedTransaction.cpp:1055`).
- **Info, no concrete trigger found:** `observeAndAdmit` derives the dep size from `HEAD size - blob_header_len` (`CasPartWriteTxn.cpp:250-257`) and never compares it with the size the caller declared for that ref, while the manifest entry keeps the declared `blob_size`; a divergence would require a hash collision or a foreign object at a blob key, so no minimal trigger exists in this tree.
- **Info, invariant-dependent:** `commitRefChunk` binds `const RefAppendAttempt & active_attempt = *rt->append_attempt` (`CasRefLedger.cpp:2449`) and later dereferences it outside `state_mutex` (`:2455`, `:2594`). This is sound only under the invariant that `append_attempt` is reset by the lane leader itself or by `installRecoveryResult`, which requires `lane_state == NeedsRecovery` — a state only the leader can set. I could not construct an interleaving that resets it while a leader is in `Writing`, so this is listed as a latent fragility, not a finding.

## Coverage

Checked and found sound: conditional-write outcome classification and the three-valued `CasWriteOutcome`; `unresolvedProvesNothingWasSent` truth table; wedge arming/resolution and the requirement that the *same* key/bytes resolve it; checkpoint-frontier publication ordered before in-memory install; catalog-life re-read before every positive append; per-namespace lane serialisation and batch carving (scope cuts, chunk reseed, per-item error isolation); `applyRefLogTxn` shape validation and copy-on-write application; manifest canonicalisation, digest, and re-validation at promote; blob dedup key derivation and HEAD-first fast path; upload fan-out grouping (one task and one dep per unique ref) and all-or-nothing dep merge; the `EDGE-BEFORE-OBSERVE` ordering (manifest body → precommit → adopt); condemned-token refusal and resurrect-then-mark-Clean ordering; precommit removal on abandon, on namespace cancellation, and via the durable writer-cleanup queue; `PreparedPartWrite`'s exactly-one-terminal-operation discipline and its `commitIsUnresolved` surface; relink pool-identity and confirm handshake; staging cleanup and mount-start sweep; write-buffer memory clamps and manifest/ref-op budgets.

Not covered (other audits): GC in-degree computation and reclaim decisions, checkpoint/snapshot compaction internals, the read path and manifest decode cache, namespace lifecycle and `dropNamespace`, fsck/inspect/decommission tooling, and the wire formats beyond `PartManifest`.

Findings: 1 High, 2 Medium, 3 Low.
