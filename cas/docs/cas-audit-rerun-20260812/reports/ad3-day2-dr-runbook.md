## Findings

### ad3-1 -- The only rebuild covers `gc/state`; every other control object has no DR path, and `_pool_meta` damage locks out the DR tools themselves (High)

- **Anchor**: `programs/disks/CommandCaGcRebuild.cpp:24-51`; `src/Disks/.../Pool/CasPool.cpp:293-368` (esp. `:351-353`); `src/Disks/.../Pool/CasRefCatalog.cpp:44-49`; `src/Disks/.../Gc/CasGc.cpp:2660-2668`.
- **Incident**: 5, 9.
- **Gap**: `cas-gc-rebuild` is the only shipped tool whose help text claims disaster recovery, and it rebuilds exactly one artifact (the GC baseline). The pool's other mandatory control objects — `<prefix>/_pool_meta`, `<prefix>/cas/ref_catalog`, per-life `_ckpt`, the per-member `owner`/`epoch` anchors — have no rebuild, no repair and no operator-writable surface. Worse, the recovery tools are gated on a successful pool open: `CommandCaGcRebuild::executeImpl` calls `ca->store()`, and `Pool::open` calls `PoolMeta::createOrValidate(..., /*create=*/!read_only)` before returning, so a corrupt `_pool_meta` makes the read-only DR path itself unusable. The shipped remediation strings are `"recreate the pool or restore _pool_meta"` and `"this pool must be recreated"` — i.e. the code's own stated recovery for a damaged control plane is total data loss.
- **Evidence**: `Pool::open` line 351 validates pool meta unconditionally on both read-only and writable opens; `CasRefCatalog::read` throws `CORRUPTED_DATA` ("refusing to interpret opaque life objects as an empty ownership universe") when the catalog is absent; `Gc::rebuildBaseline` throws when the prior fold seal is undecodable and names pool re-creation as the remedy. No `clickhouse-disks` command writes a raw pool key (`DisksApp.cpp:345-349` lists the entire CAS command set; the generic `write`/`sed` commands go through the CA filesystem, not the pool key space).

### ad3-2 -- `SYSTEM CAS FSCK` is counts-only: no keys, no timeout, no scoping, so the SQL path can detect corruption but never localize it (High)

- **Anchor**: `src/Interpreters/InterpreterSystemQuery.cpp:2534` (`ca->runFsckNow(/*detail=*/false)`); `src/Disks/.../ContentAddressedMetadataStorage.cpp:739-745`; `programs/disks/CommandFsck.cpp:27-32`, `:99-148`.
- **Incident**: 2, 5, 7.
- **Gap**: The CLI fsck accepts `--detail`, `--timeout`, `--namespace` and `--partial`, prints per-object rows with `reachable_from`, and exits nonzero on the four hard findings. The SQL verb hardcodes `detail=false`, passes no deadline, no namespace prefix and no progress callback, and returns 20 scalar counts. An operator who sees `dangling=3` in SQL has no way to learn *which* blobs or *which* parts are affected without configuring a second, read-only copy of the disk and dropping to `clickhouse-disks` — which in turn cannot be done on the live pool's own disk entry. The SQL column set also drops `meta_without_body`, `body_without_meta`, `partial` and `partial_reason`, which exist in `FsckReport` (`Tools/CasFsck.h:54-76`); the `clean()` exclusion of the body/meta counters is a sibling finding, but the SQL surface omits them from *display* as well, so they are unreachable from SQL at all.
- **Evidence**: `contentAddressedFsckColumns` (`:2397-2421`) enumerates 20 columns; `FsckReport` carries 24 scalars plus `objects`; the `static_assert` at `Tools/CasFsck.h:98-104` names `contentAddressedFsckColumns` as one of the three surfaces that must be kept in sync and states that two of the three have no test that can fail for you.

### ad3-3 -- No byte accounting outside `blobs/`, and no per-class bytes, so a bucket-vs-table byte gap cannot be attributed (High)

- **Anchor**: `src/Disks/.../Tools/CasFsck.cpp:578-596`; `src/Disks/.../Tools/CasFsck.h:44-79`; `src/Disks/.../Formats/CasLayout.h:85-251`.
- **Incident**: 2.
- **Gap**: The single physical-bytes number the system produces is accumulated by listing `layout.blobsPrefix()` only, and only when `namespace_prefix.empty()`. The pool's other five key spaces — `cas/manifests/`, `cas/ns/stream/`, `cas/ns/state/`, `gc/`, `staging/`, `roots/` — are never byte-counted anywhere in the codebase. Those are precisely where day-2 debris accumulates (orphan manifests, un-compacted ref logs, abandoned staging from a crashed writer, superseded fold generations). Additionally, every leak-ish class fsck does report (`unreachable`, `unaccounted`, `pending_gc`, `stale_edge`) is an *object count*, never bytes: the only per-class byte figure in `FsckReport` is `namespace_janitor_pending_bytes`. So "the bucket is 4 TB and the tables are 1 TB" cannot be decomposed by any shipped surface; the operator is left with `aws s3 ls` and manual prefix arithmetic.
- **Evidence**: `report.physical_bytes` is written at `:596` (sum over `present_blobs`) and `:610` (late HEAD of a reachable blob) and nowhere else; the whole physical-classification block is inside `if (namespace_prefix.empty())` at `:578`, and the CLI help text states this explicitly ("skips the pool-wide physical/pipeline classification").

### ad3-4 -- "How much space would dropping table X reclaim" has no surface at all (High)

- **Anchor**: `src/Interpreters/InterpreterSystemQuery.cpp:2397-2421`; `programs/disks/CommandFsck.cpp:29-31`; `src/Disks/.../Tools/CasFsck.h:79` (`dedupRatio`).
- **Incident**: 8.
- **Gap**: This is the single most common capacity question on a deduplicating store and nothing answers it. `referenced_logical_bytes` and `distinct_blobs` are pool-wide. `--namespace` scoping is the only per-table-ish filter and it explicitly turns off the physical accounting, so a scoped run reports no bytes at all. Because blobs are shared across namespaces by content, the logical size of table X (from `system.parts`) is an upper bound that can overstate the reclaim by an arbitrary factor — `dedupRatio()` exists and proves the code knows sharing is material, but it is a single pool-wide scalar with no per-namespace decomposition. There is no "bytes referenced only by namespace N" computation anywhere in the tree.
- **Evidence**: The fsck column list has no namespace dimension (one row per disk); `FsckReport` has no per-namespace byte map; `CommandFsck`'s `--namespace` help text documents the physical-accounting opt-out.

### ad3-5 -- The only way to clear a dead member's mount slot is a verb that first erases that member's data (High)

- **Anchor**: `programs/disks/CommandCaDropMember.cpp:23-25`; `src/Disks/.../Tools/CasDecommission.cpp:137-183` (namespace drops) executed before `:236-363` (slot retirement); `src/Interpreters/InterpreterSystemQuery.cpp:1048-1096`.
- **Incident**: 3, 10.
- **Gap**: `decommissionPoolMember` drops every namespace owned by the victim `srid`, sweeps its manifest debris, staging and `roots/` objects, and only then attempts to retire the mount slot. There is no verb that retires or tombstones a stale slot without the destructive drain. An operator whose node died with data still owned by that `srid` — the common case for a hardware failure where the replica's parts are still wanted and will be re-fetched, or where the same node will be rebuilt under a new `srid` — has exactly two options: leave the dead slot in the pool forever (`state='expired'`, permanently counted by GC's heartbeat floor logic and permanently visible in `cas_mounts`), or destroy the member's namespaces. The verb is also all-or-nothing at the member granularity: no `--slot-only`, no dry run, no per-namespace selection.
- **Evidence**: The loop at `:137-183` calls `admin->dropNamespace(life)` for every catalog entry under `victim_srid` and only the code from `:204` onward touches mount/epoch/owner. The slot-retirement branch is additionally gated on `report.warnings.empty()` (`:205`, `:224`, `:236`), so any drain hiccup means the slot is *not* cleared — the destructive half runs first and the useful half is the part that gets skipped.

### ad3-6 -- A half-decommissioned member is invisible: `cas_mounts` enumerates `/mount` objects only (High)

- **Anchor**: `src/Disks/.../Pool/CasServerRoot.cpp:606-649` (`listMounts`); `src/Storages/System/StorageSystemContentAddressedMounts.cpp:38-60`, `:142-197`; `src/Disks/.../Tools/CasDecommission.cpp:296-362`.
- **Incident**: 6, 3.
- **Gap**: `listMounts` pages `gc/server-roots/` and skips every key that does not end in `/mount`. The decommission sequence deletes `mount` and `epoch` *before* tombstoning `owner` (`:297-341`), so the window in which a member is half-retired — mount gone, owner still live, possibly namespaces still owned — produces zero rows in `system.cas_mounts`. The same holds permanently if the owner tombstone write fails, which the code anticipates with three distinct warning strings including "rerun the command to retry". Nothing exposes the `owner` anchor, its `retired_at_ms`, or the count of namespaces still owned by a retired `srid`; the ownership count is computed inside the verb (`:208-219`) and discarded into a warning string that only the caller of that one invocation ever sees. An operator arriving after a failed decommission has no query that tells them a member is stuck half-way.
- **Evidence**: `listMounts`'s `if (!k.key.ends_with(suffix)) continue;` at `:617`; the storage's fallback row (`:199-218`) is emitted per *disk*, not per orphaned slot, and carries no srid other than the local one.

### ad3-7 -- No surface exposes the namespace catalog, so every wedge state is countable but not nameable (Medium)

- **Anchor**: `src/Storages/System/StorageSystemContentAddressedMounts.cpp:55` (`wedged_namespace_count`); `src/Disks/.../Gc/CasGc.cpp:951-957`; `src/Disks/.../Pool/CasRefCatalog.cpp:227-374` (`NsState` transitions); `src/Common/ProfileEvents.cpp:777`.
- **Incident**: 4, 7.
- **Gap**: The catalog holds the state machine an operator needs during a wedge (`Creating`/`Live`/`Removing`, incarnation, life id), and no system table, no `SYSTEM CAS` verb and no `clickhouse-disks` command renders it. `cas_mounts` offers a single `wedged_namespace_count` integer, NULL for every non-local row; `CASRefAppendWedged` is a monotonic counter with no identity. The one place a stuck namespace is *named* is a `LOG_WARNING` emitted per adopted round (`CASGCStuckRemovals`), so the operator's only path from "the pool is wedged" to "which namespace" is grepping `system.text_log` on whichever node happened to be the GC leader. `cas-inspect` cannot help either: it has no decoder for `cas/ref_catalog` (see ad3-1), so even the raw object is opaque.
- **Evidence**: the `wedged_namespace_count` column comment reads "Ref-append lanes currently wedged on this disk. NULL on rows describing other servers' mounts."; `CASGCStuckRemovals`'s own description says "Incremented and warned every such round; diagnostic only".

### ad3-8 -- GC health is process-local, ephemeral, and `last_success_age_seconds=0` conflates "never led" with "just led" (Medium)

- **Anchor**: `src/Disks/.../Gc/CasGcScheduler.cpp:312-327`, `:123` (`std::atomic<Int64> pending_reclaim`), `:170-177`; `src/Storages/System/StorageSystemContentAddressedMounts.cpp:52-55`, `:177-191`.
- **Incident**: 1, 10.
- **Gap**: All four health columns come from in-memory atomics on one process's scheduler and are populated only on the row whose `srid` matches the local pool (`is_local_row` at `:177`); every other row is NULL. So a three-node pool gives each node visibility into one third of the picture and requires `clusterAllReplicas` plus knowledge of which node is leader. All four values reset to zero on restart, which is exactly when an operator queries them after an incident. `pending_reclaim` is a cumulative `condemned - redeleted` sum, not a pool-state gauge: it is unbounded, unsigned by the pool's actual backlog, and after a restart reads 0 no matter how large the real backlog is. Most sharply, `GcHealth` computes `ever_succeeded` (`:318`) precisely to disambiguate "never led" from "led recently" — and the system table drops that field, then documents the ambiguity as if it were a feature: "Seconds since this disk's GC last led a round (0 if it never led)". A monitoring rule of the form `last_success_age_seconds > threshold` therefore silently passes on a node whose GC has never once acquired the lease.
- **Evidence**: `GcHealth` (`Gc/CasGcScheduler.h:71-79`) has five fields; `appendLifecycle`/health insertion in the storage inserts four; `ever_succeeded` has no column.

### ad3-9 -- No gauge metrics, and the one counter that would flag a shut destructive gate fires on every round by construction (Medium)

- **Anchor**: `src/Common/CurrentMetrics.cpp:239-241`; `src/Common/ProfileEvents.cpp:803` (`CASGCClampSuppressedPasses`); `src/Disks/.../Gc/CasGc.cpp:2063-2098`.
- **Incident**: 1, 4, 2.
- **Gap**: The only CAS `CurrentMetrics` are the three blob-upload thread-pool gauges. Every other CAS signal is a monotonic ProfileEvent, so genuinely gauge-shaped state — reclaim backlog, wedged lane count, GC leadership, pool lifecycle, mount-lease-lost latch — is exportable only by polling `system.cas_mounts`, which as per ad3-8 is local-row-only and reset by restarts. Standard metrics-based alerting (Prometheus endpoint, `system.metrics`) therefore cannot alert on any CAS day-2 condition. Compounding this, the counter an operator would naturally alert on for "GC is not reclaiming" is self-documented as useless for that purpose: `CASGCClampSuppressedPasses`'s shipped description states that "In the current stage this is EVERY folding round by construction, not an anomaly". The genuinely actionable variant of that condition (`per_round_cause`) exists in the code and is the difference between the `LOG_WARNING` and the `LOG_INFO` branch at `Gc/CasGc.cpp:2081-2098` — but it is not surfaced as a separate counter, not surfaced as a `cas_gc_log` column, and not surfaced in the `SYSTEM CAS GC RUN` result set, so the only machine-readable form of "the destructive gate is shut for a real reason" is log-severity parsing.
- **Evidence**: the round-level `cas_gc_log` columns (`ContentAddressedGarbageCollectionLog.cpp:29-65`) contain no suppression field; suppression reaches the log only as a per-phase `phase_metrics` entry (`Gc/CasGc.cpp:855`, `:887`, `:934`, `:2211`) keyed inconsistently as `"suppressed"` and `"suppress_destructive"`.

### ad3-10 -- `GC STOP` is node-local, non-persistent, and unobservable; `is_leader=0` conflates stopped, follower, and crashed (Medium)

- **Anchor**: `src/Interpreters/InterpreterSystemQuery.cpp:2568-2601`; `src/Disks/.../ContentAddressedMetadataStorage.cpp:689-737`; `src/Disks/.../Gc/CasGcScheduler.cpp:67-79`.
- **Incident**: 1, 10.
- **Gap**: `gcStop()` sets a flag and joins two threads; nothing is written to the pool and nothing is persisted locally, so a restart silently resumes GC. That is defensible, but there is no way to *observe* the stopped state: no column in `cas_mounts`, no ProfileEvent, no metric. `stop()` sets `i_am_leader=false`, so a stopped node is indistinguishable in SQL from a healthy follower and from a node whose GC thread threw. The forward-looking failure is the routine one: an operator stops GC on all nodes to freeze the pool during an investigation, then a node restarts, GC resumes, and nothing in the operator's dashboard reflects that the freeze was lifted. `SYSTEM CAS GC STOP` also returns no result set, so a `ON CLUSTER` invocation cannot even confirm per-node which nodes actually had a scheduler to stop — the "no GC scheduler (disabled/read-only/not started) -- nothing to stop" case is `LOG_INFO`-only and reports success to the client.
- **Evidence**: `contentAddressedGcStop` returns `void`; the storage logs and returns when `!snapshot`; `cas_mounts` has no gc-enabled/gc-running column.

### ad3-11 -- Rolling restart and planned node removal have no quiesce, drain, or leadership-handoff verb (Medium)

- **Anchor**: `src/Disks/.../Gc/CasGcScheduler.cpp:67-79`; `src/Disks/.../Pool/CasPool.cpp:562-571` (`~Pool`), `:455-461` (decommission refusal); `src/Interpreters/InterpreterSystemQuery.cpp:1048-1060`.
- **Incident**: 10, 3.
- **Gap**: Shutdown does the right thing implicitly — `~Pool` drains ref lanes and writes a farewell so the slot reads `terminated` — but there is no verb to do it *before* shutdown, and no verb to release GC leadership. `CasGcScheduler::stop()` joins the round and heartbeat threads without relinquishing the GC lease in the pool, so a restarting leader leaves the pool leaderless until its heartbeat floor lapses; the other nodes meanwhile log "lease held by another mounter" every tenth tick and reclaim nothing. For planned node removal the sequence is necessarily cross-node and undocumented in code: the victim must be fully stopped (the decommission mount claim is `NoWait` and refuses with "no FORCE variant exists; stop the server or wait for its lease to lapse"), then `SYSTEM CAS DROP POOL MEMBER` must be issued from a *different* server that has the same pool mounted writable (`ca->checkNotReadOnly` at `:1057`). Nothing in the code expresses that ordering, and getting it wrong produces an `ABORTED` at best or the destructive-first behaviour of ad3-5 at worst.
- **Evidence**: no `releaseLease`/`resign`/`handoff` symbol exists in `Gc/CasGc.h` (only `acquireOrRenewLease` at `:285`); `stop()` has no pool-side write.

### ad3-12 -- `cas_mounts` renders an object-store outage identically to a not-yet-started disk (Low)

- **Anchor**: `src/Storages/System/StorageSystemContentAddressedMounts.cpp:146-156`, `:199-218`.
- **Incident**: 3, 9.
- **Gap**: When `Cas::listMounts` throws — the object store is unreachable, credentials expired, the bucket policy changed — the storage swallows the exception into `tryLogCurrentException`, sets `list_ok=false`, and falls through to the "no rows emitted" path, which inserts a single row with `insertDefault()` for `state` (empty string), for every lease column, and for all four health columns. That is byte-identical to the row produced for a disk whose pool has not been constructed. The one distinguishing signal, the exception text, goes only to the server log under the logger name `StorageSystemContentAddressedMounts`. During exactly the incident where an operator most needs `cas_mounts` — the pool's backing store is unreachable — the table reports a shape that reads as "nothing configured here".
- **Evidence**: `state` is a non-nullable `String`, so `insertDefault()` yields `''` rather than a distinguishable `unknown`/`unreadable` word, unlike `lifecycle` which has a dedicated `vanished`/`identity_lost` vocabulary.

### ad3-13 -- `cas-inspect` requires a raw object key but no shipped command enumerates raw pool keys (Low)

- **Anchor**: `programs/disks/CommandCaInspect.cpp:26-27`, `:47-49`; `programs/disks/DisksApp.cpp:345-349`; `programs/disks/CommandList.cpp`.
- **Incident**: 5, 7, 2.
- **Gap**: The decoder is key-addressed and mandatory-positional ("the raw object-storage key to decode"), and errors with "key does not exist" on a miss. But the disks shell's `list` walks the disk's filesystem view, not the pool key space, and no CAS command lists raw keys. The only shipped producers of raw keys are `cas-fsck --detail` and `cas-gc-dryrun`, both of which require the same read-only disk configuration and neither of which covers the control objects. So the practical entry point to `cas-inspect` is an external `aws s3 ls`, which puts the operator's bucket-listing hygiene on the critical path of every CAS investigation.
- **Evidence**: the unrecognized-key exception at `Tools/CasInspect.cpp:573-576` enumerates the recognized layouts, which is the closest thing to a key-space map the operator gets, and it is only reachable by guessing a key wrong.

## Checked and sound

- **Privilege granularity.** Each of the seven `SYSTEM CAS` verbs has its own `GLOBAL SYSTEM` access type (`AccessType.h:351-357`) and is both checked at execution (`InterpreterSystemQuery.cpp:1012-1050`) and declared in `getRequiredAccessForDDLOnCluster` (`:3161-3193`). A read-only fsck privilege can be granted without granting the destructive verbs.
- **`ON CLUSTER` support.** All seven verbs parse `ON CLUSTER` (`ParserSystemQuery.cpp:460-505`), and `CAS GC RUN` uniquely allows omitting the disk to sweep every CA disk on the node (`:460-472`, `InterpreterSystemQuery.cpp:2466-2479`) while still erroring when no CA disk exists.
- **`cas_gc_log` round forensics.** `round_id` correlates Start/Phase/Finish across attempts that never committed and never led; 18 named phases in execution order; per-phase ProfileEvents deltas and phase-specific `phase_metrics`; the `outcome` enum distinguishes `NotALeader` from `Deferred` from `Error` and carries the exception text. This is genuinely strong round-level observability.
- **CLI fsck triage text.** `CommandFsck.cpp:68-97` separates benign classes (`pending_gc`/`awaiting_gc` — "expected, no action needed") from actionable ones (`stale_edge` — "NOT expected, investigate"; a rebuild is named as the only clearing action) and from epistemically-limited ones (`unchecked` — "this run says nothing about them"). Nonzero exit is wired to the four hard findings with explanatory messages naming the violated invariant.
- **Mount-contention messages.** The stale-lease observation log (`CasPool.cpp:407-416`) names uuid/epoch/pid/hostname/expiry and explains the reclaim protocol; the decommission refusal (`:455-461`) states explicitly that no FORCE variant exists and names the two legitimate remedies. The bootstrap-residual refusals (`:317-336`) explain why they fail closed and warn against clearing the prefix.
- **Decommission re-runnability.** Warnings gate slot retirement at three points, the operator is told to re-run, and the `Removing`-state branch (`CasDecommission.cpp:152-164`) resumes an interrupted namespace drop rather than double-dropping. The verb's 10-column result set is machine-readable.
- **Read-only enforcement on offline tools.** All four CAS `clickhouse-disks` commands refuse a writable disk (`CommandFsck.cpp:51-54`, `CommandCaInspect.cpp:44-45`, `CommandCaGcDryRun.cpp:38-39`, `CommandCaGcRebuild.cpp:43-47`), with `cas-drop-member` explaining that a writable open would claim the tool's own `server_root_id`.
- **Rebuild refuses a healthy pool.** `Gc::rebuildBaseline` requires `--force`/`FORCE` when `gc/state` decodes cleanly, and surfaces the refusal as both a `refusal` string and a nonzero exit / thrown exception rather than silently no-op'ing.
- **`cas_log` vocabulary.** ~45 event types spanning blob, manifest, ref, root, GC, mount, decommission and error paths, with `object_hash`, `token`, `round`, `generation`, `at_version`, `query_id` and a structured `detail` map — enough to reconstruct a specific object's history if the log is retained.
