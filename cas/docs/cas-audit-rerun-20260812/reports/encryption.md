# encryption -- fresh audit 2026-08-12

## Scope

Target: `/Volumes/workspace/altinity-clickhouse/ClickHouse`, branch `cas-code-only-strip`, base `842f2b37b8f`, working tree as-is, read-only static reasoning. CAS root: `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/`.

Question: can encryption-at-rest be combined with a content-addressed (CAS) disk, and what happens to dedup, conditional writes/tokens, key rotation, and metadata confidentiality when it is.

Code-only rule honoured: no `docs/**` and no comments used as evidence of intent; shipped exception/description strings are used. All CAS tests are deleted in the working tree, so no test is cited.

First-order fact that frames everything below: **the CAS subtree contains no reference to encryption at all.** `grep -ril "encrypt"` over `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/` returns nothing — no gate, no warning, no capability negotiation, no key handling, and no CAS-native at-rest encryption of blobs or of CAS metadata. Every interaction below is therefore an emergent property of two layers that do not know about each other.

Cited from sibling audits, not re-derived here: the default content hash is non-cryptographic `cityhash128` and reads never re-verify the digest; there is no per-subject erasure primitive.

## Findings

### encryption-1 -- an encrypted disk can be layered over a CAS disk with no capability check, and the combination fails only at the first part write (High)

- **Anchor**: `src/Disks/DiskEncrypted.cpp:190-208` (`getDiskAndPathFromConfig` — takes any `DiskPtr` out of the `DisksMap` with no capability, metadata-type or object-storage check); `src/Disks/DiskEncrypted.cpp:517-536` (registration); `src/Disks/DiskEncrypted.h:135-144` (`writeFile` always takes the *auto-commit* path); `src/Disks/DiskEncrypted.h:329`, `:344-354` (`use_fake_transaction` defaults to `true`, so `createTransaction()` returns a `FakeDiskTransaction` that replays every operation directly on the disk, i.e. also through the auto-commit path); refusal at `.../ContentAddressedTransaction.cpp:536-537` (Append) and `:539-544` ("Autocommit writes are not supported for content part files on a content-addressed disk", reached whenever `partFileMustStayBlob` is true — `.bin`, `.mrk`, `.mrk2/3`, `.cmrk`, `.cmrk2/3`, `primary.idx`, `.../ContentAddressedTransaction.cpp:65-73`).
- **Trigger**: configure `<disk name="enc"><type>encrypted</type><disk>cas_disk</disk><key_hex>…</key_hex></disk>`, put `enc` in a storage policy, `CREATE TABLE … SETTINGS storage_policy='enc'`, `INSERT`. Server start and disk startup succeed — the boot access check writes `clickhouse_access_check_<uuid>`, which is not a part path and is absorbed by the mountpoint-object branch (`.../ContentAddressedTransaction.cpp:579-588`), and `DiskEncrypted`'s constructor `createDirectories` is a no-op on CAS (`.../ContentAddressedTransaction.cpp:673-679`). The first column data file of the first part then throws.
- **Consequence**: "encryption at rest over CAS" is neither supported nor refused. It is accepted by config validation and by the startup probe, and surfaces as a `NOT_IMPLEMENTED` at INSERT time, i.e. after tables exist and after an operator believes the disk is healthy. Files that *are* accepted are worse than the refusal: an inline-eligible part file takes the auto-commit branch (`:546-549`) and commits a **separate manifest publish per file**, so the part is published incrementally instead of atomically. Backup/zero-copy style calls that route through `writeFileUsingBlobWritingFunction` land on `generateObjectKeyForPath` → `notYet` (`:365`, `:83-89`).
- **Evidence**: the shipped `notYet` string itself names this hazard — "Hitting it usually means the disk is wrapped by a layer that bypasses the content-addressed write path" (`.../ContentAddressedTransaction.cpp:83-89`). So the wrapping hazard is anticipated in shipped text, yet the only response is a post-hoc exception from deep inside the write path; there is no admission-time gate on either side (`DiskEncrypted.cpp:190-208` performs no check; the CAS subtree has no encryption awareness at all).

### encryption-2 -- per-file random IV makes every file a unique blob: CAS's core value is destroyed and nothing detects it (High)

- **Anchor**: `src/Disks/DiskEncryptedTransaction.cpp:105-112` (`header.init_vector = FileEncryption::InitVector::random()` for every rewrite-mode write) and `src/IO/FileEncryptionCommon.h:131`, `:139` (AES-CTR, 64-byte per-file header carrying the random IV and the key fingerprint); CAS hashes exactly what it is handed — `.../ContentAddressedTransaction.cpp:600-635`, `:641-642`, and the digest becomes the object key (`.../Formats/CasLayout.cpp:28-31`).
- **Trigger**: any write at all through an encrypted wrapper over CAS, in particular two replicas merging the same rows, or an `ATTACH`/re-insert of byte-identical data.
- **Consequence**: quantified loss. AES-CTR keystream is a function of (key, IV); with a fresh 128-bit random IV per file, two byte-identical plaintext files produce ciphertexts that differ in every byte, so their content digests differ. Dedup hit rate for freshly written blobs goes to **zero** — not "reduced": there is no code path by which two independent encryptions of the same plaintext can collide. Concretely: (a) identical merged parts on two replicas of one shard now occupy 2× storage instead of sharing blobs; (b) re-inserting an identical batch stores a second full copy; (c) each file additionally grows by 64 bytes; (d) the presence-probe optimisation inverts into pure overhead — every blob at or above `deduplication_head_first_min_bytes` (default 1 MiB) pays one HEAD that can never hit (`.../Pool/CasPartWriteTxn.cpp:149-175`), and the 64 MiB `deduplication_cache_bytes` cache (`.../ContentAddressedSettings.cpp:36`) fills with entries that are never reused. The only sharing that survives is manifest-level reuse that never re-hashes bytes (clone/hardlink, `.../Parts/PartFolderAccess.cpp:395`).
- **Evidence**: no code detects or warns. There is no reference to encryption anywhere under the CAS root, `getDataSourceDescription().is_encrypted` is set by the wrapper (`src/Disks/DiskEncrypted.h:311-316`) but is consumed only by backups and by `DiskSelector::unwrapEncryptedAndCacheLayers` (`src/Disks/DiskSelector.cpp:28-30`) — never by CAS mount, by pool-precondition checks (`.../Backend/CasObjectStorageBackend.cpp:53-91`), or by any dedup-efficiency metric.

### encryption-3 -- the encrypted wrapper's `path` prefix silently reshapes CAS path classification (Medium)

- **Anchor**: `src/Disks/DiskEncryptedTransaction.h:36-42` (`wrappedPath` prepends the configured `path` to every path handed to the delegate; `DiskEncrypted.cpp:205-207` only requires that it end with `/`); consumers on the CAS side: `.../Parts/PartPathParser.cpp:226-230` (`isAtomicShardDir` requires exactly `store/<3 chars>`), `:290-300` (`isShadowPath` requires the *first* segment to be `shadow`), `:246-278` (`parseTableFilePath` falls back to joining all leading segments into the namespace id), and `.../Formats/CasLayout.cpp:295-320` (`checkNamespace` accepts any non-empty, non-reserved segment sequence, so a prefixed namespace is accepted rather than rejected).
- **Trigger**: `<disk><type>encrypted</type><disk>cas_disk</disk><path>enc/</path>…` plus `ALTER TABLE … FREEZE` (or any table-level file write).
- **Consequence**: with a prefix configured, frozen/`shadow` paths are no longer recognised as shadow paths, `store/<3>` shard directories are no longer recognised, and table-level namespaces acquire the prefix as part of their identity — so the same table reached through the wrapper and through the bare CAS disk resolves to two different namespaces. Nothing rejects the prefix; the pool simply grows a second, differently-named namespace tree.
- **Evidence**: `checkNamespace` rejects only empty and the reserved `_files` / `_manifests` segments; a prefix segment passes validation, which is why the misclassification is silent rather than fatal.

### encryption-4 -- SSE-C breaks CAS's S3 staging promotion (server-side conditional copy) (Medium)

- **Anchor**: `src/IO/S3/Client.cpp:1273-1287` — SSE-C is implemented by pushing `x-amz-server-side-encryption-customer-{algorithm,key,key-MD5}` into `client_configuration.extra_headers`, i.e. onto every request. There are **no** `x-amz-copy-source-server-side-encryption-customer-*` headers anywhere in `src` (repo-wide grep for `copy_source_server_side` / `copy-source-server-side` / `CopySourceSSECustomer`: no matches), and `fillCopyRequest` sets only copy-source, bucket/key, metadata, `If-None-Match`, storage class and KMS headers (`src/IO/S3/copyS3File.cpp:684-707`). CAS's promote path: `.../ContentAddressedTransaction.cpp:602-623` (S3 staging when `staging_backend=s3` and conditional copy is supported) → `.../Backend/CasObjectStorageBackend.cpp:789-812` (`promoteStaged` → `copyObjectConditional`) → `src/Disks/DiskObjectStorage/ObjectStorages/S3/S3ObjectStorage.cpp:755-804` (always with `if_none_match="*"`).
- **Trigger**: `server_side_encryption_customer_key_base64` set on the CAS disk's S3 endpoint together with `staging_backend=s3`, then INSERT a part with a blob-class file.
- **Consequence**: copying an SSE-C-encrypted source without copy-source key headers is rejected by S3. In `processCopyRequest` the `InvalidRequest`/`AccessDenied` branch is taken (`copyS3File.cpp:733-745`), and because `if_none_match` is always set for CAS, the code either rethrows immediately or retries as multipart copy, which needs the same missing headers — the exception is not a `PreconditionFailed`, so `promoteStaged` propagates it (`CasObjectStorageBackend.cpp:795-807`) and the part write fails. Not fatal by default (`staging_backend` defaults to `local`, `.../ContentAddressedSettings.cpp:58`), hence Medium.
- **Evidence**: the only SSE-C header injection point is the client-wide `extra_headers` list; nothing in `copyS3File` or `S3ObjectStorage::copyObjectConditional` adds source-side SSE-C material, and CAS has no probe for it — `checkPoolPreconditions` / `checkConditionalWriteSingleAttemptSupport` (`CasObjectStorageBackend.cpp:53-91`) test versioning and retry profile only.

### encryption-5 -- CAS metadata carries plaintext-sensitive names, sizes and small-file bodies that client-side encryption never covers (Medium)

- **Anchor**: manifest entries store the part-relative file name, the placement, the blob size and, for files at or under 1 MiB, the bytes themselves — `.../ContentAddressedTransaction.cpp:505-511` (`entry.path = route.file`, `entry.blob_size = size`), `:638-654` with `INLINE_CAP` at `:92`, schema at `.../Formats/CasPartManifestFormat.h:20-39`. Every blob object is prefixed by a CAS envelope header whose `intended_ref` is `<namespace>/<ref>` = table identity plus part name — `.../ContentAddressedTransaction.cpp:521-528`, `.../Pool/CasPartWriteTxn.cpp:323`, format at `.../Formats/CasBlobEnvelopeFormat.h:37-47`. Object keys embed namespace and part name (`.../Formats/CasLayout.h:113-148`). `system.cas_log` publishes `namespace`, `ref_name`, `object_hash`, `token` per event and is on by default while the feature is experimental — `src/Interpreters/ContentAddressedLog.cpp:26-31`, `src/Interpreters/SystemLog.h:21`. Diagnostics print `intended_ref` verbatim (`.../Tools/CasInspect.cpp:424`).
- **Trigger**: wrap CAS in an encrypted disk (or read the bucket / `SELECT … FROM system.cas_log`) and inspect anything other than blob payload bytes.
- **Consequence**: the client-side layer encrypts only file payloads. It does not encrypt file *names*, so `<column>.bin` / `<column>.cmrk2` entry paths in manifests disclose the column list; entry sizes disclose per-column data volume; `intended_ref` in each blob's plaintext header and in each object key discloses table UUID and part name (and therefore partition values encoded in part names); the envelope also records creator server id, CH version and provenance op (insert/merge/mutation/attach) at `CasBlobEnvelopeFormat.h:29-35`. Under SSE-only deployments the same inventory is plaintext to any principal with bucket read access rather than only to the storage provider. See the inventory section below.
- **Evidence**: no field of `ManifestEntry`, `EnvelopeHeader` or `CasEvent` is redacted, hashed or key-wrapped anywhere; the only transform applied to manifests/ref objects is the CAS wire encoding (`.../Formats/CasFormat.*`).

### encryption-6 -- under server-side encryption the content address is a hash of plaintext, exposed in key names and in a system table: a confirmation oracle (Medium)

- **Anchor**: blob key = algorithm name + hex digest of the stored bytes (`.../Formats/CasLayout.cpp:28-35`, `.../Primitives/CasBlobDigest.h:169-177`); the digest is computed over what CAS is handed (`.../ContentAddressedTransaction.cpp:600-642`), which under SSE-S3/SSE-KMS/SSE-C is the plaintext; the same digest is written to `system.cas_log.object_hash` (`src/Interpreters/ContentAddressedLog.cpp:29`) and is probeable by HEAD before upload (`.../Pool/CasPartWriteTxn.cpp:149-175`).
- **Trigger**: any SSE-only deployment. An adversary with bucket LIST (or merely `SELECT` on `system.cas_log`) enumerates plaintext digests; anyone able to write to the pool can also test a guess by observing whether their upload dedups (`CASBlobBodyPutAvoided` / `CASBlobDeduplicationCacheHit`, `.../Pool/CasPartWriteTxn.cpp:159-161`).
- **Consequence**: existence of a guessed plaintext blob is confirmable at negligible cost, and with the default `cityhash128` (cited from the sibling audit) the digest offers no preimage strength to lean on. Server-side encryption therefore protects the bytes but not the *fact* of their content; the address is the oracle. Client-side `DiskEncrypted` does not have this property (the digest is over ciphertext), but pays encryption-2 to get there — the two properties are mutually exclusive in this code, and nothing documents or enforces a choice.
- **Evidence**: no salting, keying or truncation is applied to the digest before it is used as a key name or logged; `blobIdOf` / `blobHexOf` emit it verbatim.

### encryption-7 -- AES-CTR with no MAC, over a store that never re-verifies digests on read (Medium)

- **Anchor**: the only available algorithms are `AES_128_CTR`, `AES_192_CTR`, `AES_256_CTR` (`src/IO/FileEncryptionCommon.h:21-30`), default `AES_128_CTR` (`src/Disks/DiskEncrypted.cpp:37`); the per-file header stores IV and key fingerprint but no authentication tag (`FileEncryptionCommon.h:114-139`); no HMAC or signature exists anywhere in CAS — the only crypto primitive present is the optional SHA-256 blob hash (`.../Primitives/CasBlobHashingWriteBuffer.cpp:121-140`), confirming the sibling security audit's finding.
- **Trigger**: a single flipped ciphertext byte in a blob object (bucket-write adversary, or storage-level bit rot).
- **Consequence**: CTR is malleable, so a chosen ciphertext bit flip is a chosen plaintext bit flip at a known offset; there is no tag to reject it, and reads never recompute the content digest (sibling cite), so the corruption is caught only if MergeTree's own checksum happens to cover the touched file and is itself checked. The two layers each assume the other verifies: CAS treats the address as proof of content, the encryption layer provides confidentiality only.
- **Evidence**: `WriteBufferFromEncryptedFile`/`ReadBufferFromEncryptedFile` are keystream-only (`DiskEncryptedTransaction.cpp:114-118`, `DiskEncrypted.cpp:428-448`); the CAS read path has no verification hook to attach one to.

### encryption-8 -- key rotation cannot re-key a CAS pool, and old keys become permanent (Medium)

- **Anchor**: all historical keys must stay in the config, indexed by fingerprint (`src/Disks/DiskEncrypted.cpp:221-245`), and a missing fingerprint is a hard read failure — `DATA_ENCRYPTION_ERROR "Not found an encryption key required to decipher file"` (`src/Disks/DiskEncryptedTransaction.cpp:42-53`); rotation only changes which key new writes use (`DiskEncrypted.cpp:243-247`, `:499-514`); CAS blobs are immutable and shared, and in-place mutation is explicitly refused (`.../ContentAddressedTransaction.cpp:1130-1134` `truncateFile`, `:536-537` Append).
- **Trigger**: `current_key_id` rotation on the encrypted disk, then attempting to retire the old key; or expecting rotation to change content addresses.
- **Consequence**: rotation is write-forward only. Existing blobs remain encrypted under the old key for as long as any manifest references them, so the old key can never be removed without making those parts unreadable; there is no re-key, scrub or rewrite tool for a CAS pool, and blob immutability plus shared reference counting means one cannot be added naively (a blob may be referenced by parts of several tables). Rotation also does not help dedup: a merge that rewrites the same logical rows under the new key mints a *new* address, so post-rotation storage transiently holds both. Crypto-shredding as a deletion strategy is unavailable for a second reason as well — per the sibling audit, no per-subject erasure primitive exists, and keys here are pool-wide, not per-subject.
- **Evidence**: `applyNewSettings` accepts a new key set but explicitly refuses to change the wrapped disk or path (`DiskEncrypted.cpp:505-511`) — i.e. the only supported rotation is one that leaves every existing ciphertext exactly where it is.

### encryption-9 -- algorithm agility and FIPS posture as implemented (Low)

- **Anchor**: blob-hash agility exists and is real — `cityhash128 | xxh3-128 | sha256` (`.../ContentAddressedSettings.cpp:33-34`, `.../Primitives/CasBlobDigest.cpp:37-44`, SHA-256 via OpenSSL EVP at `.../Primitives/CasBlobHashingWriteBuffer.cpp:121-140`), it is pinned at pool creation, and admitting a new algorithm into an existing pool requires the explicit `blob_hash_allow_new` opt-in; keys are algorithm-tagged in the wire format (`.../Formats/CasRecordStreamFormat.cpp:40`, `.../Formats/CasLayout.cpp:63-73`). Cipher agility is limited to AES-CTR key length (`FileEncryptionCommon.h:21-30`). The encrypted disk type only exists under `USE_SSL` (`src/Disks/registerDisks.cpp:13-31`).
- **Trigger**: a deployment required to use approved algorithms only.
- **Consequence**: the *default* is the non-approved, non-cryptographic `cityhash128`, and there is no FIPS-mode switch, no policy check, and no way to require SHA-256 pool-wide from a central setting — it must be set per disk before the pool is created, and cannot be changed afterwards without an opt-in migration flag. On a non-SSL build, `type=encrypted` is simply an unknown disk type rather than a clear "encryption unavailable" diagnostic.
- **Evidence**: `validate()` (`.../ContentAddressedSettings.cpp:119-137`) checks GC parameters, `server_root_id` and parse-ability of the hash name; it applies no algorithm policy.

Minor, anchored, not counted above: `DiskEncryptedTransaction::truncateFile` forwards the plaintext size to the delegate without adding the 64-byte header (`src/Disks/DiskEncryptedTransaction.h:253-257`), unlike `DiskEncrypted::truncateFile` (`DiskEncrypted.cpp:474-478`). On CAS this is masked because truncation is refused outright (`.../ContentAddressedTransaction.cpp:1130-1134`); it is listed only so the asymmetry is on record.

## Checked and sound

- SSE-S3 / SSE-KMS leave CAS's conditional-write protocol intact. KMS headers are attached to `PutObject`, `CreateMultipartUpload` and `CopyObject` (`src/IO/S3/Client.cpp:413-432`, `src/IO/WriteBufferFromS3.cpp:436`, `:744`, `src/IO/S3/copyS3File.cpp:150`, `:491`, `:706`), and CAS's tokens are ETags obtained from the write result or a follow-up HEAD (`.../Backend/CasObjectStorageBackend.cpp:94-106`, `:154-174`, `:191-209`) — server-side encryption changes the ETag's derivation but not its availability or its use in `If-Match` / `If-None-Match` / token-exact DELETE (`:642-694`, `:734-787`). Dedup is fully preserved because hashing happens before the object storage client.
- SSE-C headers are attached client-wide via `extra_headers` (`src/IO/S3/Client.cpp:1273-1290`), so ordinary CAS reads, HEADs, conditional PUTs and conditional DELETEs are covered; only the server-side copy path is not (encryption-4).
- CAS's own integrity story is unaffected by either scheme: it hashes and later re-reads *stored* bytes, so `fsck`-style checks compare like with like regardless of whether those bytes are ciphertext or plaintext.
- The CAS write path refuses, rather than silently mishandles, the two operations a wrapper is most likely to attempt on immutable content: `WriteMode::Append` on a part file and `truncateFile` (`.../ContentAddressedTransaction.cpp:536-537`, `:1130-1134`).
- No secret material is written into CAS metadata: the encryption key fingerprint and IV live in the 64-byte per-file header, which the wrapper produces as part of the file body; no CAS structure records a key, a key id or a fingerprint of its own.
- Confirmed absent as claimed by the sibling security audit: no HMAC, MAC or signature anywhere in the CAS subtree; the only cryptographic primitive is the optional SHA-256 blob hash.
