# ad4-migration -- fresh audit 2026-08-12

## Scope

Target: `/Volumes/workspace/altinity-clickhouse/ClickHouse`, branch `cas-code-only-strip`, base `842f2b37b8f`, working tree as-is (all CAS tests deleted). Static reading only; no build, no execution.

Question: how does data get **into** a CAS disk, **out of** a CAS disk, and **between** CAS pools/disks. Every route that exists in shipped code was traced end to end: `ALTER TABLE MOVE PART/PARTITION TO DISK|VOLUME` and storage-policy/TTL moves (`MergeTreeData::movePartitionToDisk` 6864-6931, `MergeTreePartsMover` 103-375), `ATTACH/REPLACE PARTITION FROM` (`MergeTreeData::cloneAndLoadDataPart` 9597-9728 → `freeze` / `freezeRemote`), interserver `FETCH PARTITION` incl. the manifest relink fast path (`DataPartsExchange.cpp` 109-330, 585-800, 1136-1266; `ContentAddressedExchange.*`; `ContentAddressedMetadataStorage::getRelinkOffer` / `prepareAdoptFromManifest` 1502-1636), `BACKUP`/`RESTORE` (`DataPartStorageOnDiskBase::backup` 401-518, `MergeTreeData::backupParts` 7200-7267, restore 7460-7540), `FREEZE`/`UNFREEZE`/shadow (`MergeTreeData::freezePartitionsByMatcher` 9856-9960, `Storages/Freeze.cpp` 128-240), clone/hardlink part creation (`ContentAddressedTransaction::createHardLink` 782-829, `moveDirectory` 846-967), and the initial on-boarding/off-boarding of an existing table.

Code-only rule honoured: `docs/**` is deleted/ignored, comments are not treated as intent, only shipped strings and control flow are evidence.

Cited, not re-derived (sibling findings):
* `ContentAddressedMetadataStorage::getStorageObjects` (`ContentAddressedMetadataStorage.cpp:1308-1342`) returns `StoredObject(location.key, path, location.length)` and drops `BlobLocation.offset`; because `DataSourceDescription::operator==` (`Disks/DiskType.cpp:35`) ignores `metadata_type`, a CAS→plain-object-storage copy takes the server-side-copy branch of `DiskObjectStorage::copyFile` (`DiskObjectStorage.cpp:300-317`) and produces a corrupt (or, when `physical_key_prefix` is non-empty, a `NoSuchKey`-failing) destination file. **Sibling: idisk-contract / read-protocol.**
* `ContentAddressedTransaction::generateObjectKeyForPath` (`:363-366`) and `createMetadataFile` (`:492-495`) both call `notYet(...)` and throw `NOT_IMPLEMENTED`, so `DiskObjectStorageTransaction::copyFileImpl` (`DiskObjectStorageTransaction.cpp:491-556`) can never target a CAS disk. **Sibling: idisk-contract.**

Below, "relink" means metadata-only (manifest/ref republish, no payload bytes move); "copy" means every byte is re-read, re-hashed and re-uploaded.

## Findings

### ad4-1 -- cross-disk ATTACH/REPLACE PARTITION FROM into a CAS disk is unimplemented and fails part-way through the part (High)

- **Anchor**: `src/Storages/MergeTree/DataPartStorageOnDiskBase.cpp:593-621` (`freezeRemote`) — compare `:531-533` (`freeze` opens `disk->createTransaction()` when `disk->isContentAddressed()`) and `:702-718` (`clonePart` does the same for a CAS destination). `freezeRemote` passes only `params.external_transaction`, which is empty on this path (`MergeTreeData.cpp:9657-9664`), so `Backup(...)` takes its transaction-less copy branch `Storages/MergeTree/Backup.cpp:180-184` → `src_disk->copyDirectoryContent` → `IDisk::copyThroughBuffers` (`Disks/IDisk.cpp:174-205`, a 16-thread pool) → `IDisk::copyFile` (`:63-79`) → `to_disk.writeFile(...)` → `DiskObjectStorage::writeFile` (`DiskObjectStorage.cpp:918-928`) which calls `writeFileWithAutoCommit`, i.e. `autocommit=true`. CAS rejects exactly that: `ContentAddressedTransaction::tryCreateWriteBuffer` `:539-544` throws `NOT_IMPLEMENTED` — *"Autocommit writes are not supported for content part files on a content-addressed disk"* — for every path where `Cas::partFileMustStayBlob` holds (`:65-73`: `primary.idx`, `*.bin`, `*.mrk*`, `*.cmrk*`).
- **Trigger**: `ALTER TABLE cas_tbl ATTACH PARTITION p FROM src_tbl` (or `REPLACE PARTITION` when the policies are not partition-op compatible, `StorageMergeTree.cpp:3013-3055`) where `src_tbl`'s disk is not in `cas_tbl`'s storage policy — i.e. every local→CAS, plain-S3→CAS and CAS-pool-A→CAS-pool-B attach. `on_same_disk` is false at `MergeTreeData.cpp:9610-9618`, so `freezeRemote` is chosen.
- **Consequence**: the documented cheap route for on-boarding an existing table onto CAS, and the only route for moving a partition between two CAS pools, does not exist. The failure is not clean: the copy is fan-out parallel and the non-blob files (`checksums.txt`, `columns.txt`, `count.txt`, `partition.dat`, …) are accepted by the autocommit branch and each one commits its own CAS transaction; the first one creates the destination ref via `promoteBuild` and the rest go through the read-modify-write merge in `publishStaging` (`ContentAddressedTransaction.cpp:256-291`) → `repointRef` (`Parts/PartFolderAccess.cpp:442-473`). So before the `NOT_IMPLEMENTED` lands there is a *published, live, partial* part ref in the destination namespace. Two aggravating mechanisms on the same path: (a) `repointRef` → `promoteBuild(allow_repoint=true)` retargets the committed ref with no expected-old-manifest check (`Pool/CasPartWriteTxn.cpp:697-705`), so two concurrent file commits that both read the same view lose one of the two entries; (b) two threads that both see *no* view race into `promoteBuild(allow_repoint=false)`, whose loser hits *"promote: ref '{}' already names a different committed manifest — refusing to overwrite"* (`:700-703`). Cleanup is best-effort only (`Backup.cpp:182` `CleanupOnFail` → `removeRecursive` → `dropRefIfPresent`, `ContentAddressedTransaction.cpp:759-763`) and does not run if the process dies.
- **Evidence**: `freezeRemote` is the only one of the three clone entry points that omits the CAS transaction; `Backup.cpp:163-179` shows the transaction branch would have used `transaction->copyFile`, which is itself dead on CAS (cited sibling). Shipped strings: `ContentAddressedTransaction.cpp:543-544`, `Pool/CasPartWriteTxn.cpp:701-703`.

### ad4-2 -- `always_use_copy_instead_of_hardlinks=1` makes every same-disk CAS clone throw NOT_IMPLEMENTED (Medium)

- **Anchor**: `IDataPartStorage::ClonePartParams::copy_instead_of_hardlink` is set from the MergeTree setting at `StorageReplicatedMergeTree.cpp:3346`, `:5589`, `:9209`, `:9500`, `StorageMergeTree.cpp:3213`, `MutateTask.cpp:3309`. On the same-disk path it reaches `DataPartStorageOnDiskBase::freeze:540-551` → `Backup.cpp:163-178` with a live CAS transaction → `BackupImpl.cpp` (`Backup.cpp:61-67`) `transaction->copyFile(...)` → `DiskObjectStorageTransaction::copyFileImpl` (`DiskObjectStorageTransaction.cpp:491-556`), which needs `generateObjectKeyForPath` and `createMetadataFile` — both `notYet(...)` on CAS (cited sibling, `ContentAddressedTransaction.cpp:363-366`, `:492-495`, message at `:85-89`).
- **Trigger**: `ALTER TABLE cas_tbl MODIFY SETTING always_use_copy_instead_of_hardlinks = 1` (or the same in `CREATE`), then any `ATTACH/REPLACE PARTITION FROM` on the same disk, `MOVE PARTITION TO TABLE`, mutation-untouched clone, or `restoreDataFromBackup` clone. Nothing rejects the setting on a CAS table and nothing downgrades it to the hardlink/relink path.
- **Consequence**: routes that work perfectly with the default setting fail with a message about "the generic disk-transaction surface", which does not name the setting. `files_to_copy_instead_of_hardlinks` reaches the same dead end, but on CAS it is currently always empty: its only producer (`MutateTask.cpp:3297-3299`) is gated on `isStoredOnRemoteDiskWithZeroCopySupport()`, which is false because `DiskObjectStorage::supportZeroCopyReplication` excludes `MetadataStorageType::CAS` (`DiskObjectStorage.h:51-55`).
- **Evidence**: control flow above; no `isContentAddressed()` guard exists anywhere on the `copy_instead_of_hardlink` producers (the only CAS-aware sites in `Storages/` are `MergeTreeData.cpp:5920`, `:7499`, `MergeTask.cpp:562`, `IMergeTreeDataPart.cpp:1359`, `DataPartsExchange.cpp:111`, `:311`, `DataPartStorageOnDiskBase.cpp:276`, `:417`, `:531`, `:702`).

### ad4-3 -- two CAS disks that share a pool and a `server_root_id` share one namespace; a MOVE between them deletes the moved part (Medium, config-gated, silent)

- **Anchor**: `ContentAddressedMetadataStorage::liveNamespace` (`ContentAddressedMetadataStorage.cpp:886-889`) is `server_root_id + "/" + mirroredArchiveNamespace(table_uuid)` and `route()` (`:903-934`) derives the ref name from the part directory only — neither carries any per-disk identity. `server_root_id` is a per-disk config value (`ContentAddressedSettings.cpp:50`, `:113-114`) and `validate()` (`:119-137`) only checks that it is present and well-formed; nothing rejects two disks with the same pool prefix and the same `server_root_id`.
- **Trigger**: a storage policy with two CAS disks pointing at one pool prefix with the same `server_root_id` (a plausible "two volumes over one pool" configuration), then `ALTER TABLE ... MOVE PARTITION ... TO DISK 'cas2'`.
- **Consequence**: the mover copies to `moving/<part>` (ref `moving/<part>` in the *same* namespace), then `renameClonedPart` → `moveDirectory` → `republishRef(moving/x → x)` finds `x` already committed with byte-identical entries and therefore just drops the source ref and returns success (`Parts/PartFolderAccess.cpp:419-440`). The "moved" part on disk 2 never gets its own ref. When the now-Outdated part on disk 1 is removed, its rename-to-`delete_tmp_` and `removeRecursive` drop namespace ref `x` (`ContentAddressedTransaction.cpp:846-967`, `:759-763`), so the live part on disk 2 loses its manifest: reads fail with `ContentAddressed: no ref for ...` (`ContentAddressedMetadataStorage.cpp:1335`) and the data is unreachable. No warning is emitted at any step.
- **Evidence**: the equal-entries shortcut in `republishRef` (`:426-435`) is the only reason the move reports success; the same-namespace collision is invisible to `DataPartStorageOnDiskBase::clonePart:695-700`, whose `existsDirectory` pre-check is satisfied because `moving/<part>` does not exist yet.

### ad4-4 -- no relink fast path for local moves inside one CAS pool, and the CAS copy is serial (Medium)

- **Anchor**: `DataPartStorageOnDiskBase::clonePart:702-718` sends *every* CAS destination through `copyDirectoryContentIntoTransaction` (`:652-679`), a plain recursive `readFile`/`writeFile` loop with no parallelism and no source-side check for "the destination disk is the same pool". Contrast the interserver path, which does exactly this optimisation: `DataPartsExchange.cpp:310-330` offers a manifest relink when `receiver_pool_uuid == ca_meta->getPoolUUID()`, and `ContentAddressedMetadataStorage::prepareAdoptFromManifest:1592-1636` adopts it with zero bytes transferred.
- **Trigger**: `ALTER TABLE ... MOVE PARTITION ... TO DISK 'cas2'` / TTL move between two CAS disks backed by the same pool.
- **Consequence**: a move that is representable as a ref publish instead re-reads, re-hashes and re-stages the entire part; at best the pool dedups the blobs on `promoteStaged`, so the cost is a full read plus a full staging write. It is also *slower than the non-CAS path*, because the non-CAS branch (`:719-731`) uses `IDisk::copyThroughBuffers`' 16-thread pool while the CAS branch is single-threaded, and the whole part sits in one transaction. `MergeTreePartsMover` has no CAS-specific handling at all.
- **Evidence**: the relink machinery (`ContentAddressedExchange.h:58-92`, `getRelinkOffer` `ContentAddressedMetadataStorage.cpp:1502-1528`) is only reachable from `DataPartsExchange`; no local caller exists (grep for `getRelinkOffer`/`prepareAdoptFromManifest` yields only `DataPartsExchange.cpp:318`, `:1182`).

### ad4-5 -- the relink receiver publishes an adopted part without verifying it (Medium)

- **Anchor**: `Fetcher::relinkPartToDisk` finishes with `new_data_part->loadColumnsChecksumsIndexes(true, /*check_consistency=*/false)` (`DataPartsExchange.cpp:1262`), whereas the byte-fetch path validates with `new_data_part->checksums.checkEqual(data_checksums, false, name)` (`:1113-1125`). The adoption itself is trust-only: `prepareEntries` (`Parts/PartFolderAccess.cpp:392-410`) calls `build->adoptEvidence(entry)`, which merely records `BlobDepRecord{..., /*adopted=*/true}` without any existence or size probe (`Pool/CasPartWriteTxn.cpp:478-486`), and the promote path logs the adoption as `"manifest-trust"` (`Pool/CasPartWriteTxn.cpp:692-694`).
- **Trigger**: relink a part whose transferred manifest references a blob that is not resolvable in the receiver's pool view — e.g. the sender advertises a `pool_uuid` that matches while pointing at a different physical prefix, or a blob of the offered manifest has already been graduated by GC on the receiver's side. The publish-then-confirm handshake (`:1196-1236`) only proves that the *sender still holds the ref it offered*; it proves nothing about the receiver's own blob reachability.
- **Consequence**: the part becomes Active with no read ever attempted, and the defect surfaces later as a read-time `FILE_DOESNT_EXIST` / missing object on a user query or a merge, i.e. as a "broken part" far from the fetch that created it. The relink path is on by default (`allow_ca_relink = true`, `DataPartsExchange.h:101`) for ordinary replication fetches, `FETCH PARTITION` (`StorageReplicatedMergeTree.cpp:5621`, `to_detached=true`) and `REPLACE PARTITION FROM`'s fetch (`:3375-3378`).
- **Evidence**: the asymmetry between `:1262` and `:1113-1125` in the same function family; `adoptEvidence` has no probe; there is no `checkConsistency` call anywhere on the relink branch.

### ad4-6 -- a CAS table outside an Atomic database cannot be backed up at all (Medium)

- **Anchor**: `DataPartStorageOnDiskBase::backup:417-422` throws `SUPPORT_IS_DISABLED` — *"BACKUP via temporary hard links is not supported on a CAS disk yet (B16/B34); use an Atomic database (which backs up via pointer-holding) instead"*. `MergeTreeData::backupParts:7213-7231` sets `make_temporary_hard_links = true` unless the storage id has a UUID **or** the part is on a zero-copy-capable remote disk; the second escape hatch can never fire for CAS because `DiskObjectStorage::supportZeroCopyReplication` explicitly excludes `MetadataStorageType::CAS` (`DiskObjectStorage.h:51-55`).
- **Trigger**: `BACKUP TABLE ordinary_db.cas_tbl TO ...` where the database engine is `Ordinary`/`Memory`/anything without a table UUID.
- **Consequence**: no backup route at all for those tables — not degraded, refused. The message names the intended workaround, so this is a known gap rather than a surprise; the risk is that the only recovery route for a CAS table is tied to the database engine.
- **Evidence**: the two anchors above; the projection call at `MergeTreeData.cpp:7257-7266` passes the same flag, so projections hit the same refusal.

### ad4-7 -- BACKUP of a CAS table always re-reads every byte to compute checksums (Low)

- **Anchor**: `BackupEntryWithChecksumCalculation::canCalculateChecksumFromRemotePath` requires `getDisk()->areBlobPathsRandom()` (`Backups/BackupEntryWithChecksumCalculation.cpp:124-127`); `ContentAddressedMetadataStorage::areBlobPathsRandom()` returns `false` (`ContentAddressedMetadataStorage.h:120`), so the method resolves to `FromReading` (`:101-112`, `:193-269`).
- **Trigger**: any `BACKUP` of a CAS table, including an incremental `BACKUP ... SETTINGS base_backup=...`.
- **Consequence**: every backup streams the full part payload out of object storage just to hash it, even when the base backup already contains the identical content. This is the safe choice given that `getStorageObjects` drops the blob offset (cited sibling) — a remote-path-derived checksum on CAS would be computed from a key/length pair that does not identify the byte range — but it means CAS gets none of the incremental-dedup shortcut that plain object-storage disks get.
- **Evidence**: the `false` at `ContentAddressedMetadataStorage.h:120`; the `object.remote_path`-keyed hash at `BackupEntryWithChecksumCalculation.cpp:319-320` is what it avoids.

### ad4-8 -- a failed migration into CAS leaves S3-staged blobs behind until the next mount (Low)

- **Anchor**: `ContentAddressedTransaction::cleanupPendingTempFiles` (`ContentAddressedTransaction.cpp:148-172`) unconditionally deletes local staging temp files, but removes `StagingBackend::S3` staging objects only inside `else if (committed)`. On the abort path (`clonePart`'s `clone_transaction->undo()` at `DataPartStorageOnDiskBase.cpp:712-717`, or the destructor at `:101-123`) the staged objects are left in the pool.
- **Trigger**: `staging_backend=s3` on the destination CAS disk (`ContentAddressedSettings.cpp:58`) plus any interrupted move/attach/restore into it — cancelled `MOVE PARTITION`, `NOT_ENOUGH_SPACE`, killed query, the ad4-1 failure.
- **Consequence**: orphan objects under `<pool_prefix>/staging/<server_root_id>/` that no GC round targets; they are reclaimed only by `Cas::sweepOwnMountStaging`, which runs once at mount time (`ContentAddressedMetadataStorage.cpp:595-607`). A server that retries migrations for a long time without restarting accumulates them.
- **Evidence**: the `committed`-gated branch at `:159-168`; the sweep call site is the only other deleter of that prefix.

## Routes with no code support

1. **Cross-disk `ATTACH`/`REPLACE PARTITION FROM` into CAS** — no CAS transaction on `freezeRemote`, and CAS refuses autocommit blob writes (ad4-1). This is simultaneously the missing "on-board an existing table onto CAS" route and the missing "move a partition between two CAS pools" route.
2. **Any `IDiskTransaction::copyFile` whose destination is CAS** — dead by construction (`generateObjectKeyForPath` / `createMetadataFile` are `notYet`, cited sibling); reachable via `always_use_copy_instead_of_hardlinks` (ad4-2) and via `files_to_copy_instead_of_hardlinks` should that set ever become non-empty on CAS.
3. **Metadata-only (relink) local move between two CAS disks of one pool** — implemented for the interserver fetch only; no local caller (ad4-4).
4. **Byte-correct copy out of CAS to another object-storage disk of the same type** — the shared-`DataSourceDescription` server-side copy path drops the blob offset (cited sibling). There is no CAS-aware fallback: nothing forces the through-buffer path for a CAS source.
5. **Zero-copy replication / zero-copy move on CAS** — excluded on purpose (`DiskObjectStorage.h:51-55`), so `MergeTreePartsMover::clonePart`'s `tryToFetchIfShared` branch (`MergeTreePartsMover.cpp:241-277`) is unreachable when the destination is CAS.
6. **`BACKUP` of a CAS table in a non-Atomic database** — refused (ad4-6).
7. **Append / truncate based migration tooling** — `WriteMode::Append` on a part file and `truncateFile` throw `NOT_IMPLEMENTED` by design (`ContentAddressedTransaction.cpp:536-537`, `:1130-1135`).

## Checked and sound

* **MOVE PART/PARTITION onto CAS** (`clonePart:702-718`): one CAS transaction for the whole part, content re-hashed on the way in, `MergeTreePartsMover.cpp:299` then validates with `loadColumnsChecksumsIndexes(true, true)`, and `swapClonedPart:328-375` renames via `moveDirectory` → `republishRef`, i.e. the `moving/<part>` → `<part>` promotion is metadata-only and idempotent. Failure rolls back with `undo()` and the `moving/` ref is dropped.
* **MOVE PARTITION off CAS to a local disk**: `IDisk::copyFile` reads through `DiskObjectStorage::prepareRead`, which uses `getBlobViewPlan`/`prepareInManifestRead` and therefore honours the payload window (`DiskObjectStorage.cpp:802-822`, `ContentAddressedMetadataStorage.cpp:1419-1445`). Offsets, sizes and checksums survive.
* **Same-disk `ATTACH PARTITION FROM` inside CAS**: `freeze` opens the CAS transaction (`:531-533`) and `BackupImpl` hardlinks, which `ContentAddressedTransaction::createHardLink:782-829` turns into manifest-entry adoption (`adoptEvidence` / staged-entry reuse) — a true relink with no bytes moved, published atomically by `commit:312-352`, then verified by `cloneAndLoadDataPart`'s `loadColumnsChecksumsIndexes(require_part_metadata, true)` (`MergeTreeData.cpp:9725`).
* **`MOVE PARTITION TO TABLE` across disks** is refused up front with a clear message (`MergeTreeData.cpp:9619-9623`), so it cannot silently degrade into the broken `freezeRemote` route.
* **FREEZE/UNFREEZE**: `freeze` routes shadow paths into a dedicated shadow namespace (`shadowNamespace` `:897-900`, `route` `:907-913`) and `removeRecursive` drops shadow refs at part, table and prefix granularity (`ContentAddressedTransaction.cpp:711-736`). `createAndStoreFreezeMetadata` is a no-op on CAS because it is gated on `supportZeroCopyReplication()` (`StorageReplicatedMergeTree.cpp:11615-11623`), so no `frozen_metadata.txt` autocommit write is attempted.
* **RESTORE onto CAS**: explicitly CAS-aware — one `disk->createTransaction()` for the whole part and `restore_tx->writeFile` per file, committed once (`MergeTreeData.cpp:7499-7538`). This is precisely the shape `freezeRemote` is missing.
* **Byte-fetch fallbacks in the relink protocol** are conservative in the right direction: a cookie mismatch, a reservation that lands outside the advertised pool, a missing source token, an undecodable manifest and a `MechanismFallbackAllowed` prepare/promote all fall back to a byte fetch, while an `Unresolved` promote throws instead of fetching bytes (`DataPartsExchange.cpp:761-800`, `:1159-1249`, `ContentAddressedMetadataStorage.cpp:1542-1567`). The relink source token is length- and charset-bounded and version-tagged (`ContentAddressedExchange.cpp:90-152`).
* **Detached-part attach inside CAS** (`ATTACH PARTITION` from `detached/`) is a `moveDirectory` between two refs of one namespace → `republishRef`, metadata-only, with an explicit conflict refusal when the destination already holds different content (`Parts/PartFolderAccess.cpp:429-432`).
