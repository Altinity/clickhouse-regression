## Findings

### ad5-1 -- ref-table runtime cache budget is enforced only at recovery and cannot evict a table that is being written (High)

- **Anchor**: `Pool/CasRefLedger.cpp:1105` (sole call site), `:1149-1210` (`enforceRefTableCacheBudget`), `:1158-1162` (`weightOf`), `:1180-1181` and `:1202-1203` (skip predicates), `Pool/CasPool.h:92` (256 MiB, hardcoded), `Pool/CasRefProtocol.h:126`.
- **Trigger**: Any workload with many simultaneously-written tables on one CAS disk. Two independent defects compound:
  1. `enforceRefTableCacheBudget` has exactly one call site — the tail of `ensureRefTableRecovered`. It runs when a namespace runtime is first recovered after mount or eviction, and **never again**. A set of tables that is recovered once and then grows for hours through `appendRefOps` never re-enters the check, so the budget is not consulted while the memory it governs is actually accumulating.
  2. Even when it does run, the candidate filter at `:1180-1181` and `:1202-1203` skips every runtime with `use_count() != 1`, `leader_active`, or a non-empty `pending` queue, and `:1175-1176` skips the namespace being recovered. Under concurrent writes to N tables, every runtime is pinned, `cands` is empty, and the function returns having evicted nothing. There is no log, no metric increment, and no admission or blocking path — the budget is silently exceeded.
- **Magnitude**: The governed structure is `RefTableRuntime::state`, a `RefCowMap` = `std::map<String, RefCommittedRow>` plus the parallel `owned_manifests` set, at ~272 B resident per committed ref (derivation in Scope). Two separate over-runs:
  - *Accounting*: `weightOf` sums `base_snapshot_bytes + tail_bytes_since_snapshot`, i.e. **encoded** bytes (~110 B/ref), against a budget meant to bound resident memory. Even if the budget were enforced, 256 MiB of accounted weight is 2.44M refs, which is **~633 MiB resident** — a 2.5x overshoot before the eviction defects are considered.
  - *Absence of enforcement*: the real ceiling is the per-namespace admission cap (ad5-5), 610k refs ≈ **166 MiB resident per table**. 100 concurrently-written tables at 100k parts each = 10M refs = **2.7 GB**; 1,000 tables at that size = **27 GB**. The stated budget is 256 MiB. Behavior at the real limit is process OOM, not fail-closed — there is no error path that reports "ref-table memory exhausted".
- **Evidence**: The weight function reads two `std::atomic<uint64_t>` counters that are maintained as encoded-byte tallies (`:3064-3068` decrements them by `captured_bytes` after a snapshot publish, and `:1113-1114` seeds them from `RecoveryResult::tail_bytes`/`base_snapshot_bytes`, both produced by the ref-log/snapshot *encoders*). Nothing in `RefCowMap` (`Pool/CasRefCowMap.h`) or `RefTableState` (`Pool/CasRefProtocol.h:131-186`) tracks resident bytes. The single call site is verifiable by exhaustive grep: only `Pool/CasRefLedger.cpp:1105`, the definition at `:1149`, and the declaration at `Pool/CasRefLedger.h:478`.

### ad5-2 -- the GC fold has no per-round budget on ref-log GETs, manifest decodes, or the in-memory delta vector (High)

- **Anchor**: `Gc/CasGc.cpp:1379` (`std::vector<BlobDelta> deltas;`), `:1383` and `:1797` (`logs_applied` counted, never compared to any budget), `:1955` (`deltas.size()` only reported as a metric), `:961-1002` (`foldManifestEdges` pushes one `BlobDelta` per manifest entry), `Gc/CasBlobInDegree.h:88-90` (`kBlobDeltaSize = 64`), `Gc/CasBlobInDegree.cpp:330` (`std::stable_sort` over the whole vector), `Gc/CasGc.cpp:440-448` (the eight budgets that *are* wired — none of them bounds intake).
- **Trigger**: Any interval during which the fold does not keep up: GC leader loss, `gc_enabled=false` followed by re-enable, a namespace `hold` that clears, a long object-store outage, or simply a sustained commit rate above the cleanup ceiling in ad5-4. The next round must absorb the entire accumulated backlog in one pass: `GET` every unfolded ref-log object, decode every manifest those logs reference, and accumulate one 64-byte `BlobDelta` per manifest entry.
- **Magnitude**: With `P` part-commits/s over a backlog window of `T` seconds and `E = 2C + 1` blob edges per part, the round holds `T·P·E` deltas. For a 24-hour backlog at 10 parts/s with `C = 10` (`E = 21`): 18.1M deltas × 64 B = **1.16 GB** for `deltas` alone, and `std::stable_sort` (`CasBlobInDegree.cpp:330`) allocates a temporary buffer of the same order, so peak is **~2.3 GB** in a single background thread. The same round issues **~864,000 ref-log GETs** and up to **864,000 manifest GETs** (the 128 MiB decode cache holds only ~4,000 manifests of a 100-column part, so it thrashes rather than helps). At `C = 100` (`E = 201`) the delta vector alone is **11 GB**. Contrast: `rebuild_edge_budget = 8,000,000` exists for the *rebuild* path (`Gc/CasGc.cpp:2804-2805`) but the steady-state fold has no analogue.
- **Evidence**: `logs_applied` is incremented at `:1797`, copied to `logs_applied_this_round` at `:1950`, and used only for a metric at `:1954` and an accounting cross-check at `:2237-2242`. The walk loop starting at `:1473` iterates `walk_targets` (one entry per live namespace) and, per namespace, the listed log range, with no early exit on a request or byte count — the only budget consulted anywhere in intake is `frontier_probe_budget`, which defaults to `UINT64_MAX` (`Pool/CasPool.h:64`). Every wired budget in `:440-448` gates *output* work (graduations, redeletes, deletes, sweeps, outcome entries), never input.

### ad5-3 -- the blob upload pool is server-wide, 16 threads with a 16-slot queue, and enqueue blocks (High)

- **Anchor**: `ServerSettings.cpp:151` (`cas_blob_upload_pool_size = 16`), `Pool/CasBlobUploadPool.cpp:45-49` (single process-wide instance, constructed with the 4-arg `ThreadPool` ctor), `Common/ThreadPool.cpp:162` (that ctor sets `max_free_threads = queue_size = max_threads`), `:180` and `:342` (`job_finished.wait(lock, pred)` with `pred = scheduled_jobs < queue_size`), `ContentAddressedTransaction.cpp:1196-1206` (fan-out enqueues one task per unique blob and waits for all), `Common/threadPoolCallbackRunner.h:229-232` (`scheduleOrThrowOnError`, i.e. `wait_microseconds == nullopt`, i.e. block), `ContentAddressedTransaction.cpp:241` (`Cas::blobUploadPool()` — the global), `:299` and `:264` (called once per part inside the commit loop).
- **Trigger**: More than 16 in-flight CAS blob uploads anywhere on the server. A single wide part exceeds this on its own: `B = 2C + 1` tasks are enqueued into a 16-slot queue, so a 100-column part enqueues 201 tasks and the committing thread blocks inside `scheduleImpl` for the majority of them.
- **Magnitude**: Server-wide concurrency ceiling of **16 blob uploads and 16 queued**, shared across every CAS disk, every table, and every concurrent INSERT/merge/mutation. Commit latency for one part is `ceil(B/16) × upload_time`: at `C = 100` (201 blobs) and 50 ms per small blob that is 13 sequential waves ≈ **650 ms of pure scheduling latency per part**, and one part containing 16 multi-GB `.bin` blobs occupies the entire server's CAS upload capacity for the duration of those uploads. Because the enqueue blocks rather than failing or degrading, the pressure is invisible: it surfaces as INSERT latency on unrelated tables with no error, no `CANNOT_SCHEDULE_TASK`, and no queue-depth signal beyond `CASBlobUploadPoolThreadsScheduled`. The knob is a `ServerSetting`, so raising it requires a restart, and raising it also raises the queue size in lockstep (same ctor argument), so the two cannot be tuned independently.
- **Evidence**: `blobUploadPool()` returns `*pool_instance`, a `static`-lifetime singleton guarded by `pool_mutex`; there is exactly one for the process (`initializeBlobUploadPool` throws `LOGICAL_ERROR` on a second call, `CasBlobUploadPool.cpp:42-43`), and it is initialized once from `Server.cpp:1722` / `LocalServer.cpp:425`. `fanOutBlobUploads` takes `ThreadPool &` but its only production caller passes that singleton. The blocking path is unambiguous: `enqueueAndGiveOwnership` with a defaulted `wait_microseconds` takes the `else` branch at `threadPoolCallbackRunner.h:232`, reaching `scheduleImpl`'s unconditional `job_finished.wait` at `ThreadPool.cpp:342`.

### ad5-4 -- ref-object cleanup is budgeted at 5,000/round while every part commit creates 2 ref objects, and the GC round re-LISTs the entire ref prefix each time (High)

- **Anchor**: `ContentAddressedSettings.cpp:46` (`gc_round_ref_cleanup_budget = 5000`), `Gc/CasGc.cpp:2398-2411` (both log and snapshot deletes charged to that one budget), `:897` (cleanup runs only when not `suppress_destructive`), `ContentAddressedSettings.cpp:32` (`gc_interval_sec = 60`), `Gc/CasGc.cpp:2561-2593` (`enumerateRefPrefix`: full LIST of `casRefsPrefix()` in 1,000-key pages), `:2597` (called unconditionally at the head of every round), `Pool/CasPartWriteTxn.cpp:592` (precommit append) and `Parts/PartFolderAccess.cpp:291,370` (commit append) — two ref-log objects per part commit.
- **Trigger**: A sustained part-commit rate above the cleanup ceiling. Each part commit appends a precommit transition and a commit transition, so it creates **2 ref-log objects**; snapshots add one more per 256 appends. Cleanup reclaims at most 5,000 ref objects per round, and rounds are 60 s apart.
- **Magnitude**: Sustainable rate = 5,000 objects / 2 objects per commit / 60 s ≈ **41.7 part-commits/s per pool**. Above that, the live ref-object count `R` grows without bound, and because `enumerateRefPrefix` LISTs the whole prefix every round with no incremental cursor, round cost grows linearly with the backlog it failed to clear — a positive feedback loop. At `R = 1M`: `ceil(1M/1000) = 1,000 LIST requests per round` × 60 rounds/hour = **60,000 LIST/hour = \$0.30/hour = ~\$216/month per CAS disk in enumeration requests alone**, plus a `RefScanSummary::keys` vector of 1M `String`s (~160 B each with allocator overhead) = **~160 MB resident per round**, plus `logs_by_life` (`std::map<…, std::set<RefTxnId>>`, ~64 B/node) = **~64 MB**, all of which is moved into `RoundInput` → `RefPlan` and additionally copied into `FoldResult::ref_tables` at `:1981`. At `R = 10M` the enumeration alone is 10,000 LISTs/round (600k/hour, ~\$2,160/month) and ~2.2 GB of round-local scan state.
- **Evidence**: `RefScanSummary` (`Gc/CasGc.h:110-121`) holds `std::vector<String> keys` plus three keyed containers, all filled by the unbudgeted `forEachListedKey` at `:2569-2589`; `kListPageLimit = 1000` at `:2567` is the page size, not a stop condition. `listRefPrefix` at `:2595-2597` calls it with no staleness or delta check. The cleanup budget is shared: `:2398-2402` charges log deletes and `:2407-2411` charges snapshot deletes to the same `ref_cleanup_objects_used`, so snapshot reclamation competes with log reclamation for the same 5,000.

### ad5-5 -- per-namespace 64 MiB ref-table admission cap fails writes permanently and non-retryably at ~610k refs per table (Medium)

- **Anchor**: `Formats/CasRefLogFormat.h:50` (`ref_removal_max_bytes = 64 MiB`), `Formats/CasRefSnapshotFormat.h:40` (`ref_snapshot_max_bytes = ref_removal_max_bytes`), `Pool/CasRefLedger.cpp:859-861` (budget = 64 MiB − `4 + len(ns) + 4096`), `Pool/CasRefLedger.h:419` (`kRefAdmissionSafetyMargin = 4096`), `:2161-2169` (`admits()` gate, `LIMIT_EXCEEDED`), `Pool/CasRefProtocol.cpp:514-527` (`admits` checks both snapshot and removal budgets), `Backend/CasRequestControl.cpp:145-149` (the *retryable* class uses `NETWORK_ERROR` — this path does not).
- **Trigger**: A single table (namespace) accumulating enough committed refs that one more `OwnerTransition`/`SetPublishedAt` would push the encoded snapshot or the encoded terminal-removal transaction past 64 MiB. Reached by normal part accumulation on a wide-partitioned table, or faster by a table with long part names.
- **Magnitude**: `(64 MiB − 4100) / 110 B` ≈ **610,000 committed refs per namespace**; at a 40-character ref name it falls to ~470,000. Behavior is fail-closed with a precise message ("would exceed the table's admission budget … refusing before any object is created"), which is the right shape — but the code is `LIMIT_EXCEEDED`, not `NETWORK_ERROR`, so it is a **hard, non-retryable INSERT failure**, and it is **permanent**: the only way to get back under the cap is to remove refs, i.e. DROP parts or partitions. Note what this means for the write-availability question: **write availability is not coupled to GC liveness here.** The fold does not shrink `snapshot_body_bytes` — that counter is maintained purely by ref-table mutation (`Pool/CasRefProtocol.cpp:215-286`), so GC running, lagging, or being disabled has no effect on whether a table can accept writes. Write availability is coupled to *part removal*, which is an operator action. That is a safer coupling than GC-liveness, but it is also a cliff with no warning: nothing in the append path emits a metric or log as the table approaches the cap, so the first symptom is a hard INSERT failure on a table that has been healthy for months. The removal budget is the sharper edge — it bounds the *terminal removal* transaction, so a table can in principle reach a state where the encoded `RemoveNamespace` transaction that DROP would need does not fit either; `admits` checks both budgets on every growing op (`CasRefProtocol.cpp:524-526`), which is what keeps that from happening, and is correct.
- **Evidence**: `admits` builds `scratch = state`, applies the op, and compares `encodedSnapshotBudgetSize(scratch)` and `encodedRemovalBudgetSize(scratch)` against the two budgets. Both sizes are O(1) — they read the cached `snapshot_body_bytes`/`removal_body_bytes` counters plus a framing computation (`CasRefProtocol.cpp:500-512`) — and `RefCowMap`'s copy-on-write base (`Pool/CasRefCowMap.h:99`) keeps `scratch = state` from copying the map, so the admission check itself is cheap. The budgets are set only in `RecoveryResult` (`:859-861`) and installed at `:1116-1117`, so they are established once per recovery and are constants thereafter.

### ad5-6 -- the dedup presence cache weight function under-accounts entry cost by ~3.1x (Medium)

- **Anchor**: `Pool/CasPool.h:464-471` (`struct DedupPresent {}`, `DedupWeight` returns a constant `64`), `Pool/CasPool.cpp:165-168` (constructed with `deduplication_cache_bytes` and `NO_MAX_COUNT` — no entry-count backstop), `ContentAddressedSettings.cpp:36` (64 MiB default), `Common/LRUCachePolicy.h:204-216` (`std::list<Key> queue` + `std::unordered_map<Key, Cell>`, `Cell` = `MappedPtr` + `size_t` + iterator), `Primitives/CasBlobDigest.h:39-41` (`BlobDigest` = `std::array<uint8_t,32>`).
- **Trigger**: Any pool that writes more than ~1M distinct blobs — i.e. any pool at all, since `dedupCacheAdd` is called on every successful upload and every HEAD hit (`Pool/CasPartWriteTxn.cpp:165`, `:183`).
- **Magnitude**: `DedupPresent` is empty and the declared weight is 64 B, but the real per-entry cost is: `unordered_map` node ≈ 96 B (next pointer + cached hash + 33-byte `BlobRef` key padded + 32-byte `Cell`), `std::list<Key>` node ≈ 64 B (two pointers + the key stored a *second* time), `make_shared<DedupPresent>` control block ≈ 32 B, bucket-array share ≈ 8 B — **~200 B**. The 64 MiB budget therefore admits `64 MiB / 64 = 1,048,576` entries whose true footprint is **~200 MiB**, an overshoot of **~136 MiB per CAS disk** with `NO_MAX_COUNT` meaning nothing else caps it. The value carries no information at all (presence is the whole payload), so the `shared_ptr` allocation and the duplicated key are pure overhead: a `std::unordered_set<BlobRef>` or an entry-count cap would cost ~40% of this.
- **Evidence**: `DedupWeight::operator()` ignores its argument and returns a literal `64`, while `CacheBase`'s LRU policy charges `max_size_in_bytes` against the sum of those weights (`LRUCachePolicy.h`, `current_size_in_bytes`). `Pool/CasPool.cpp:200` and `:212` are the only accessors — `contains` and `set(ref, make_shared<DedupPresent>())` — confirming the mapped value is never read.

### ad5-7 -- three single-key CAS loops retry 100 times with zero backoff (Medium)

- **Anchor**: `Pool/CasPlainObjects.cpp:18` (`MAX_CAS_ATTEMPTS = 100`), `:25-39` (`casPutObject`: 100 × HEAD+PUT, no sleep), `:55-65` (`casRemoveObject`: 100 × HEAD+DELETE, no sleep), `Pool/CasRefCatalog.cpp:101,111-121` (`casUpdateImpl`: 100 × read+`casPut`, no sleep), `Pool/CasRefCkpt.cpp:22,146-192` (`MAX_CKPT_CAS_ATTEMPTS = 100`, deadline-bounded but no backoff), `Backend/CasObjectStorageBackend.cpp:696-713` (`casPut` is a single conditional PUT — no internal retry or delay to absorb the spin).
- **Trigger**: Contention on any single key: the ref catalog (`refCatalogKey()`, one object per pool, touched by every namespace create/remove), a namespace file (`putNamespaceFile`, e.g. concurrent metadata writes to the same table), or a `_ckpt` object.
- **Magnitude**: Up to **200 object-store requests per call, issued back-to-back with no delay** — the loops contain no `sleep_ms`, no jitter, and no `CasRequestController` (which does have backoff: `retry_initial_backoff_ms = 200`, `retry_max_backoff_ms = 5000`, `Backend/CasRequestControl.h:88-89`). Each of the inner `head`/`putIfAbsent`/`casPut` calls may itself burn up to 16 controller attempts, so the worst-case fan-out for one `casPutObject` is **~3,200 requests against one key**. With `W` writers contending, aggregate request rate is `W × 200` per contention episode with no dispersion, which is the textbook shape for provoking 503 SlowDown on a single-key hot spot — and 503s are classified `Unresolved` (`CasRequestControl.cpp:43-53`), which feeds the retry rather than damping it. Terminal behavior is fail-closed (`ABORTED` "object CAS contention", or `NETWORK_ERROR` from `throwCasWriteRetryLater`), so this costs requests and latency rather than correctness.
- **Evidence**: The three loop bodies are complete in the anchors above and contain no time-based call. Compare the same file's sibling machinery: `CasRequestController::pauseBeforeReissue`/`backoffBeforeAttempt` (`Backend/CasRequestControl.h:168-170`) exists precisely for this and is not used by these three paths. `publishCkpt` at `CasRefCkpt.cpp:146-149` at least checks `deadline.now_ms() >= deadline.deadline_ms` per iteration, bounding wall-clock spend to `operation_deadline_ms = 90 s`; the two `CasPlainObjects` loops have no deadline check at all.

### ad5-8 -- every positive ref append re-reads the entire ref catalog (Medium)

- **Anchor**: `Pool/CasRefLedger.cpp:2313-2325` (`positive_append` → `CasRefCatalog::read(backend, layout)` then a linear scan for this namespace's entry), `:2292` (the removal-class path does the same), `Formats/CasFormat.cpp:108` (`RefCatalog` object cap 256 MiB, 4 KiB per line), `Pool/CasRefCatalog.cpp:109,120` (each `casUpdateImpl` iteration re-reads it too), and the 34 `CasRefCatalog::read` call sites across the pool, GC, fsck and decommission paths.
- **Trigger**: Every ref-log chunk commit, i.e. at least twice per part commit (precommit transition and commit transition). Cost scales with the number of namespaces in the pool, which is unrelated to the namespace being written.
- **Magnitude**: The catalog is one object holding one line per namespace, each up to the 4 KiB line cap. At 10,000 tables and a realistic ~300 B line, the catalog is ~3 MB. Two full GETs plus two full decodes per part commit = **~6 MB downloaded and parsed per part commit**; at 100 part-commits/s that is **~600 MB/s of catalog traffic and 200 catalog decodes/s** on top of the actual work. At the 4 KiB-per-line worst case with 10,000 namespaces the object is 40 MB and one part commit pulls 80 MB. There is no cache and no token-conditional short-circuit: `CasRefCatalog::read` unconditionally issues a `Backend::get`, which (per the sibling finding on control-object materialization) buffers the whole object. Batching is the only mitigation present — `kMaxRefBatch = 1000` (`Pool/CasRefLedger.h:416`) means one catalog read can be amortized across up to 1,000 queued mutations — but that only helps under concurrency; a table receiving one INSERT at a time pays the full price per commit.
- **Evidence**: `commitRefChunk`'s `positive_append` branch reads the catalog solely to confirm this namespace's `CatalogEntry` is present with the expected incarnation (`:2321-2325`) — a per-namespace fact fetched via a pool-global object. The lookup is `std::find_if` over `catalog.entries` (`:2321`), so decode plus scan is O(namespaces) per append.

### ad5-9 -- encoded-size caps are checked after the oversized buffer has already been built (Medium)

- **Anchor**: `Pool/CasPartWriteTxn.cpp:541-544` (`encodePartManifest(body)` runs, *then* `encoded_text.size() > kMaxManifestEncodedBytes` throws), `Formats/CasRefSnapshotFormat.cpp:115-133` (`encodeRefTableSnapshot` builds the full text with a `256 + 128×rows` up-front reservation, *then* checks `text.size() > ref_snapshot_max_bytes`), `Formats/CasRefLogFormat.cpp:49-64` (`checkBudget` is called on the encoded size at `:360`), `Formats/CasByteBudget.h:8-26` (the saturating helpers exist and are used for *pre*-checks elsewhere, e.g. `Formats/CasRefCatalogFormat.cpp:70-77`).
- **Trigger**: Any object whose encoding lands over its cap. For the manifest, `kMaxManifestEntries = 1,048,576` gates entry count and `kMaxManifestInlineBytesTotal = 16 MiB` gates inline volume, but the 256 MiB encoded cap is only discoverable by encoding: 1M entries at ~250 B of encoded path plus refs exceeds 256 MiB while satisfying both pre-checks.
- **Magnitude**: The cap does not prevent the allocation it names. Peak transient allocation before the throw is the full encoded string — up to **256 MiB for a manifest, 64 MiB for a ref snapshot** — plus, for the snapshot, `sealObject` with `CompressionPolicy::Always` (`Formats/CasFormat.cpp:106`) then compresses it, adding another buffer. So the "64 MiB snapshot limit" can transiently cost **~128-192 MiB** across the encode + seal + compress chain for one namespace, and each of the unbounded concurrent publishers in ad5-10 can be in that window simultaneously. `CasByteBudget.h` provides exactly the arithmetic needed to pre-compute these sizes (`addByteBudget`, `mulByteBudget`, `fitsObjectCap`) and the catalog path uses it correctly per line; the manifest and snapshot encoders do not.
- **Evidence**: `stageManifest`'s three pre-checks (`:511-528`) are on entry count and inline bytes; the encoded-size check at `:542` follows `const String encoded_text = encodePartManifest(body);` at `:541`. `encodeRefTableSnapshot` reserves `256 + 128 * rows` at `CasRefSnapshotFormat.cpp:119`, writes every row, and only then compares at `:131`. For the snapshot the ad5-5 admission gate normally keeps state under the cap, so the throw at `:131` is a backstop — but it is a backstop that has already paid the memory.

### ad5-10 -- snapshot publication fan-out is capped per namespace and unbounded pool-wide (Medium)

- **Anchor**: `Pool/CasRefLedger.cpp:2732-2752` (`admitSnapshotPublishUnderStateLock`: per-namespace guard is `pending_snapshot_publishes == 0`, thresholds are 256 logs / 1 MiB), `:2754-2772` (`dispatchSnapshotPublisher`: `ThreadFromGlobalPool(...).detach()` per namespace, no global counter), `:2964` (`candidate_state = rt->state`), `:2990` (`snapshotOf` materializes every row into vectors), `:3000` (`sealObject(encodeRefTableSnapshot(snap))`), `Pool/CasPool.h:85-86` (thresholds hardcoded, not disk settings).
- **Trigger**: N tables crossing the 256-log / 1 MiB tail threshold at about the same time — the normal outcome of a broad ingest wave, since the threshold is per-table and the trigger is per-append.
- **Magnitude**: One detached global-pool thread per namespace, with no pool-wide ceiling. Each publisher's peak resident cost is the `RefTableSnapshot` (a `std::vector<RefCommittedRow>` + `std::vector<RefOwnerBinding>`, ~64 B/row plus string heaps) **plus** the encoded text **plus** the zstd output. At the ad5-5 ceiling that is **~64 MiB encoded + ~40 MiB of row vectors + compression buffer ≈ 130 MiB per in-flight publisher**. 100 tables publishing concurrently at a modest 4 MiB table size ≈ **1.2 GB**; 1,000 tables at the ceiling is not survivable. Thread-wise, 1,000 concurrent detached publishers is a significant fraction of the global pool. The code does correctly release the state copy before encoding (`:2992-2995`), which halves the peak, and `RefCowMap`'s shared base makes `candidate_state = rt->state` cheap — so the cost is the encode chain, not the capture.
- **Evidence**: The only concurrency guard is `rt.pending_snapshot_publishes.load(...) == 0` at `:2738`, which is per-`RefTableRuntime`; there is no counterpart at `CasRefLedger` or `Pool` scope, and `dispatchSnapshotPublisher` does not consult one before spawning. Failure handling backs off per namespace (`advancePublishBackoff` at `:3005`, `:3014`, `:3053`, bounded by `snapshot_publish_backoff_max_ms = 30000`), so a pool-wide encode failure degrades to a 30 s retry storm across all namespaces rather than a coordinated pause.

### ad5-11 -- seven pool-level resource caps are unreachable from configuration (Low)

- **Anchor**: `Pool/CasPool.h:64` (`gc_frontier_probe_budget = UINT64_MAX`), `:65-66` (`gc_fold_threshold = 1`, `gc_fold_max_defer_rounds = 8`), `:67` (`gc_stuck_removal_rounds = 10`), `:68` (`rebuild_edge_budget = 8,000,000`), `:85-86` (`snapshot_log_count_threshold = 256`, `snapshot_log_bytes_threshold = 1 MiB`), `:92` (`ref_table_cache_bytes = 256 MiB`); versus the 27-entry `DECLARE` list at `ContentAddressedSettings.cpp:29-58` and the wiring block at `ContentAddressedMetadataStorage.cpp:543-568`.
- **Trigger**: Any attempt to tune CAS memory or GC pacing for a workload that does not match the built-in constants.
- **Magnitude**: The wiring block assigns 24 `PoolConfig` fields from disk settings; the seven above are never assigned and silently keep their struct defaults. Two of them govern the largest memory pools in the subsystem (`ref_table_cache_bytes` = 256 MiB, the budget in ad5-1) and the pacing of the largest object writes (`snapshot_log_*_threshold`, ad5-10), and one is a disabled safety valve (`gc_frontier_probe_budget = UINT64_MAX` means the probe-budget branch at `Gc/CasGc.cpp:1445-1452` can never trip, so `intake_unprobed_budget` is dead in production and the warning at `:1891` is unreachable). An operator hitting ad5-1 or ad5-10 has no configuration response short of a rebuild.
- **Evidence**: Exhaustive grep for each identifier finds it only in `Pool/CasPool.h` (declaration/default), its consumer, and — for the four that pass through — `refLedgerConfig()` at `Pool/CasPool.h:94-107`. None appears in `ContentAddressedSettings.cpp`, so no config key reaches them; `loadFromConfig` at `:94-99` would reject an unknown key anyway by passing it to `impl->set`, which throws for names outside the `DECLARE` list.

### ad5-12 -- local scratch consumption is proportional to in-flight insert bytes while the CAS disk reports no free space at all (Medium)

- **Anchor**: `ContentAddressedSettings.cpp:30,58` (`scratch_path` default empty, `staging_backend = "local"` — local staging is the default), `MetadataStorageFactory.cpp:233-238` (default scratch = `<clickhouse_path>/disks/<name>/cas_scratch/`, i.e. the server data volume), `ContentAddressedTransaction.cpp:625-635` (blob files stream to a scratch temp file), `:657-668` (inline overflow above 1 MiB also spills to scratch), `:148-172` (temps freed only in `cleanupPendingTempFiles`, at transaction teardown), `DiskObjectStorage.h:65-69` (`getTotalSpace()` and `getAvailableSpace()` both return `{}`), `DiskObjectStorage.cpp:562-580` (`tryReserve` skips every constraint check when those are `nullopt`).
- **Trigger**: Concurrent INSERTs/merges on a CAS disk with the default local staging backend. Sibling audit owns the "unreserved and uncapped" characterization of the spill itself; the resource consequence quantified here is the interaction with space reporting.
- **Magnitude**: Every blob-bearing file of a part is written to local scratch in full before upload, and temps survive until the transaction commits (`cleanupPendingTempFiles` runs from `commit` at `:322` and from the destructor at `:103`). So peak local scratch = **the full uncompressed-on-disk size of every part in every in-flight CAS transaction**, on the same filesystem as the server's own data and logs. Ten concurrent 10 GB merges = **100 GB of local scratch**, and exhaustion is a server-wide ENOSPC, not a CAS-scoped error. Meanwhile the disk reports `getAvailableSpace() == nullopt`, so `tryReserve` returns true for any byte count and MergeTree's `min_bytes`/`min_ratio` constraints are structurally unenforceable — CAS never tells MergeTree to slow down, and it cannot: there is no path from CAS pressure (scratch fullness, ad5-3 queue depth, ad5-4 GC backlog) to any writer-visible signal. Note that `nullopt` space reporting is inherited `DiskObjectStorage` behavior shared with all object-storage disks; what is CAS-specific is that a CAS insert makes a *local* allocation proportional to the insert size while presenting itself as a disk with no local footprint. The FD count follows the same shape: one scratch FD per open part-file write buffer (`CaContentWriteBuffer` holds a `WriteBufferFromFile`, `:1226-1236`) plus one `ReadBufferFromFile` per concurrent upload (`:230-233`), bounded only by MergeTree's stream concurrency and the 16-way pool of ad5-3.
- **Evidence**: The S3 staging alternative exists (`:602-623`) but requires both `staging_backend = "s3"` **and** `conditionalCopySupported()`, and `staging_backend` defaults to `"local"` (`ContentAddressedSettings.cpp:58`, description confirms "s3 is opt-in"). Nothing between `writeFile` and `stageBlobPartFile` consults free space, a byte budget, or a semaphore.

## Checked and sound

- **Admission is O(1) and pre-write.** `admits()` (`Pool/CasRefProtocol.cpp:514-527`) copies the state, applies the op to a `RefCowMap` whose base is shared (`Pool/CasRefCowMap.h:99`), and compares against cached `snapshot_body_bytes`/`removal_body_bytes` counters maintained incrementally at `CasRefProtocol.cpp:215-286`. No O(refs) work and no allocation of the encoded form. The refusal happens "before any object is created", as the shipped message states, and the same is true of the op-count and per-op checks at `Pool/CasRefLedger.cpp:2099-2112`.
- **Byte-budget arithmetic cannot overflow.** `addByteBudget`/`mulByteBudget` (`Formats/CasByteBudget.h:8-16`) saturate at `UINT64_MAX`, and `fitsObjectCap`/`fitsLineCap` treat `0` as unbounded consistently. `Formats/CasRefCatalogFormat.cpp:305,321` uses `numeric_limits<uint64_t>::max()` guards in the same style.
- **The fold's reducer is a streaming merge, not a materialization.** `foldDeltasIntoGeneration` (`Gc/CasBlobInDegree.cpp:484-526`) advances a run cursor alongside the sorted `scattered` and `source_retirements` vectors, so run bytes are streamed rather than loaded. `SourceEdgeRunView` (`Gc/CasBlobInDegree.h:59-73`) wraps a `ReadBuffer`. The resident cost is the delta vector only (which is the ad5-2 problem, not this one), and `BlobDelta` is deliberately pinned at 64 B by `static_assert` (`:88-90`).
- **Output-side GC budgets are coherent and reserved separately.** `GcRoundWorkBudget` (`Gc/CasBlobInDegree.h:127-174`) treats `0` as unbounded uniformly, and the hand-off prefix reclaim gets its own reservation so a prune-heavy round cannot starve the one-shot hand-off — matching the shipped description at `ContentAddressedSettings.cpp:48`.
- **The manifest decode cache accounts honestly enough.** `PartManifestWeight` (`Pool/CasManifestReader.h:49-58`) charges `256 + Σ(path.size + inline_bytes.size + 96)`; measured against `sizeof(ManifestEntry)` ≈ 112 B plus two string allocations, real cost is ~1.2x the declared weight. A 128 MiB budget holds ~155 MiB — an overshoot worth noting but an order of magnitude better than ad5-6.
- **GC meta writes are bounded and never wedge the round.** `gc_meta_pool_size = 16` with a matching queue, and `scheduleMetaJob` falls back to running inline if scheduling fails (`Gc/CasGc.cpp:339-349`), with the failure charged to `CASGCMetaWriteAnomaly` and explicitly advisory.
- **Request budgets are validated for internal consistency at mount.** `validateCasRequestBudget` (`Backend/CasRequestControl.cpp:98-120`) rejects `max_attempts < 1` and any budget where `attempt_timeout_ms + lease_safety_margin_ms` is not strictly below the mount lease TTL — so a writable mount cannot open with a budget that would let an attempt outlive its own fence.
- **The GC maintenance cursor cap is comfortable.** 64 KiB (`Formats/CasGcMaintenanceStateFormat.h:9`) against a cursor that holds one object key bounded by the 512-byte namespace limit; checked symmetrically on encode and decode (`.cpp:18-20`, `:61-63`). Not a realistic exhaustion path.

## Coverage

Covered with anchored findings: memory (dedup cache, manifest decode cache, ref-table runtime cache, per-namespace ref-table state, GC round scan state, GC fold delta vector, snapshot-publisher fan-out, post-materialization cap checks); local disk (scratch/staging spill and its interaction with space reporting, inline-overflow temps); threads (server-wide blob upload pool, GC meta pool, GC loop + heartbeat + remount + snapshot-publisher threads); file descriptors (scratch write and upload read FDs, bounded only by writer concurrency); object-store request rate and cost (per-part-commit formula `4C + 11`, the `.meta` sidecar doubling PUTs, per-append catalog GETs, per-round ref-prefix LIST cost, unbackoffed 100-iteration CAS loops); ref-log/journal growth and the hard caps that fail writes (per-namespace 64 MiB admission cap, ref-object cleanup ceiling); per-namespace and pool-global caps (enumerated in the budget table); the byte-budget machinery (`Formats/CasByteBudget.h`, `Backend/CasRequestControl.{h,cpp}`) and whether enforcement precedes allocation (pre-allocation for admission and line caps, post-allocation for encoded-object caps — ad5-9); behavior at the caps (fail-closed for ad5-5/ad5-7/ad5-9, silent degradation for ad5-1/ad5-3/ad5-6/ad5-11, unbounded-to-OOM for ad5-1/ad5-2); backpressure to the MergeTree writer (none exists; free space is `nullopt` — ad5-12).

Explicitly resolved: **write availability is not coupled to GC liveness in this code.** The per-namespace admission budget is driven by ref-table mutation counters that GC does not touch (ad5-5 Evidence), and the ref-log tail is bounded by writer-side snapshot publication (`Pool/CasRefLedger.cpp:2937-3071`), not by the fold. GC lag costs object count, request volume, round memory, and storage bill (ad5-2, ad5-4) — not the ability to commit a part.

Cited to siblings rather than re-derived: part-folder view-cache byte budget inoperative; `Backend::get` full materialization of control objects (load-bearing for ad5-8's per-append catalog cost); local scratch spill unreserved and uncapped (ad5-12 quantifies the space-reporting interaction only); zstd frame size driving a pre-decompress resize.

Not covered: object-storage client internals (S3 connection pool sizing, HTTP keep-alive, multipart thresholds) live outside the CAS root and outside `PoolConfig`; per-query memory tracker attribution for CAS allocations (CAS allocates on background and detached threads, so tracker attribution is a separate question); the `benchmarks/` subtree; runtime measurement of any figure above — every number here is derived from shipped defaults and structure sizes by static reasoning, and the resident-byte estimates assume a glibc-style allocator with 16-byte granularity.
