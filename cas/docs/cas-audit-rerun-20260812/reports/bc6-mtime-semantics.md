## Findings

### bc6-1 -- getLastModified never consults the manifest, so it dates files that do not exist (Medium)

- **Anchor**: `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/ContentAddressedMetadataStorage.cpp:1185-1190`; contrast `getFileSize` at `1157-1169`.
- **Trigger**: `disk->getLastModified("<data_path>/<part_name>/does_not_exist.bin")` on a CAS disk where `<part_name>` resolves to a committed ref.
- **Consequence**: `parsePartFilePath` + `route` succeed for any tail under a part directory, and `resolve_stamp` only resolves the ref — it never asks the manifest whether `r->file` is present. A plausible timestamp is returned for a file that is not in the part. `getFileSize` on the same path correctly throws `FILE_DOESNT_EXIST` ("file {} not in manifest of {}"), and `DiskLocal`/`MetadataStorageFromPlainObjectStorage` throw for a missing path, so this is a one-method divergence in the disk contract. The reachable in-tree effect is `MergeTreeDataPartWide::getColumnModificationTime` (`MergeTreeDataPartWide.cpp:549-561`): after `getStreamNameOrHash` returns a name from `checksums` that is absent from the CAS manifest, the method returns a timestamp instead of `{}`, so `system.parts_columns` reports a modification time for a column whose data file does not exist on the disk.
- **Evidence**: `if (auto p = Cas::parsePartFilePath(path)) { auto r = route(*p); if (r && !r->ref.empty()) return resolve_stamp(*r); }` — the only guard is a non-empty ref name; `r->file` is never checked, unlike `getFileSize` which requires `view->fileSize(r->file)`.

### bc6-2 -- per-file mtime collapses to a single per-part stamp (Low)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:1175-1190`; consumers `MergeTreeDataPartWide.cpp:557`, `MergeTreeDataPartCompact.cpp:234`, `StorageSystemPartsColumns.cpp:262`.
- **Trigger**: `SELECT column, column_modification_time FROM system.parts_columns` on a CAS wide part after a mutation that rewrote only some columns.
- **Consequence**: every column of every part reports the same value (the part's last publish time), because the stamp is a property of the ref, not of the manifest entry. On a local or plain-object-storage disk the per-column values differ and are the intended signal for "when was this column last materialised". `ManifestEntry` carries no per-entry timestamp, so the information does not exist to be returned. Additionally, because a mutation republishes the whole part, all columns' reported times move together to the mutation time even for untouched columns.
- **Evidence**: `resolve_stamp` is keyed on `r.refKey()` alone; the file component of the route is discarded before the stamp is computed.

### bc6-3 -- ms->s truncation and two distinct meanings collapsed onto epoch 0 (Low)

- **Anchor**: `ContentAddressedMetadataStorage.cpp:1180-1182` and `1191-1192`.
- **Trigger**: `disk->getLastModified("<data_path>/format_version.txt")` (or any namespace file / mountpoint object) on a CAS disk.
- **Consequence**: `Poco::Timestamp(0)` is returned, i.e. 1970-01-01, and the same value is also returned when a ref carries `published_at_ms == 0`, so "this is a non-part file, I have no stamp" and "this ref has no stamp" are indistinguishable from a genuine epoch mtime. Every age comparison downstream reads epoch 0 as maximally old — `isOldPartDirectory` (`MergeTreeData.cpp:3316-3321`) would classify such a path as old on its first check rather than waiting out the lifetime. Separately, `published_at_ms / 1000` floors a millisecond value to whole seconds before `Poco::Timestamp::fromEpochTime`, so parts published within the same second are indistinguishable and the ms precision that is stored durably and exposed elsewhere (`system.cas_mounts` uses `DateTime64(3)`) is discarded on this path.
- **Evidence**: `if (resolved->published_at_ms == 0) return Poco::Timestamp(0); return Poco::Timestamp::fromEpochTime(static_cast<time_t>(resolved->published_at_ms / 1000));` and `if (existsFile(path)) return Poco::Timestamp(0);`.

### bc6-4 -- setLastModified is a silent no-op, and one rename shape refreshes nothing (Low)

- **Anchor**: `ContentAddressedTransaction.cpp:831-834`; caller `DataPartStorageOnDiskBase.cpp:780-783`; the unbumped shape `ContentAddressedTransaction.cpp:908-913`.
- **Trigger**: any `disk->setLastModified(path, ts)` on a CAS disk; and a `moveDirectory` whose source and destination route to the same `(namespace, ref)` pair.
- **Consequence**: the method admits the write (`checkOpAdmitted(CasOpClass::Write)`) and then does nothing, reporting success. A caller that wants to *set* a specific timestamp — not bump to now — gets silent success with no effect. For the one in-tree caller the effect is masked: `rename` stamps the source then moves it, and CAS's `moveDirectory` -> `republishRef` -> `publishEntries` -> `promote` sets `published_at_ms = nowMs()` (`PartFolderAccess.cpp:437`, `CasPartWriteTxn.cpp:725`), so the bump happens for a different reason. The exception is the `src_key == dst_key` early return at `912-913`, where neither the no-op nor a republish runs, so the stamp is not refreshed at all.
- **Evidence**: the body of `ContentAddressedTransaction::setLastModified` consists of the admission check only; both parameters are unnamed.

### bc6-5 -- the write fence is on CLOCK_BOOTTIME but the request it admits is bounded on CLOCK_MONOTONIC (Medium)

- **Anchor**: `CasMountRuntime.cpp:57-62` (`bootMs` = `CLOCK_BOOTTIME`), `CasMountRuntime.cpp:101-111` (`refAppendFenceOk`), `CasMountRuntime.cpp:212-213` (deadline armed from the renew attempt's boot time); against `CasRequestControl.cpp:80-83` (`steadyClockNowMs`), `168`, `202`, `247`, `264`.
- **Trigger**: the host suspends, or the VM is paused / live-migrated, for `S` seconds between the moment `refAppendFenceOk()` admits a durable ref append and the moment the underlying conditional PUT completes.
- **Consequence**: `refAppendFenceOk` grants admission when `attempt_timeout_ms + lease_safety_margin_ms < deadline_boot_ms - now_boot_ms`, i.e. it budgets the request against a **boot-clock** deadline. `CLOCK_BOOTTIME` advances during suspend; the `steady_clock` (`CLOCK_MONOTONIC`) that enforces `attempt_timeout_ms` and `operation_deadline_ms` inside `CasRequestController` does not. After a suspend of `S`, the boot deadline (and therefore the durable `expires_at_ms` the lease advertises) can have elapsed while the in-flight attempt still believes it is inside its timeout, so the PUT can land after the lease expiry — precisely the window the fence exists to close, and the window in which a GC leader may already have fenced the slot (`CasServerRoot.cpp:524-539`). Choosing `CLOCK_BOOTTIME` for the fence is the conservative half of the pair; the mismatch is that the admitted work is not measured on the same clock.
- **Evidence**: `refAppendFenceOk` reads `bootMsNow()`/`deadline_boot_ms` and compares against `cas_request_budget.attempt_timeout_ms + cas_request_budget.lease_safety_margin_ms`, while every deadline check inside `CasRequestController` (`now_ms() + budget.attempt_timeout_ms > deadline_ms`) uses the `steadyClockNowMs` default installed at `CasRequestControl.cpp:168`.

### bc6-6 -- one surviving cross-node wall-clock liveness gate, in the decommission epoch mint (Low)

- **Anchor**: `CasServerRoot.cpp:196-209`, in particular `const bool live = !surviving.gc_fenced && surviving.expires_at_ms > now_ms;`; `now_ms` supplied by `CasPool.cpp:386-396` from `system_clock`.
- **Trigger**: `SYSTEM CAS DROP MEMBER` (which selects `EpochMintPolicy::DecommissionRecovery`, `CasPool.cpp:392-394`) run from a node whose wall clock is ahead of the surviving member's stamped `expires_at_ms`, in the narrow state where the durable epoch object is absent but the mount slot is present.
- **Consequence**: this is the only place in the tree where one node's judgement about another node's liveness rests on comparing a wall-clock timestamp minted by that other node against the local wall clock. Under skew larger than the remaining lease, the "refusing to re-mint an epoch under a live member" guard is bypassed and an epoch is minted. The blast radius is bounded, not a double writer: the following `claimMount` fails closed on the same slot (`ForeignOwner` at `318-322`, `LiveDoubleStart` at `362-365`), so the outcome is a burned writer epoch and a misleading operator error. Every other fencing or takeover decision is monotonic: token-stability against the observer's own clock (`506-507`, `430-452`), and the shipped string at `362-364` states the rule explicitly ("no wall-clock trust").
- **Evidence**: `chassert(now_ms != 0);` immediately precedes the comparison, confirming the wall clock is a required input on this branch and not an incidental one; the `listMounts` state column applies a `ttl/2` skew margin (`638`, `StorageSystemContentAddressedMounts.cpp:144`) but this branch applies none.

### bc6-7 -- the emulated conditional-write token is a filesystem mtime, disambiguated only by per-instance in-process state (Medium)

- **Anchor**: `src/Disks/DiskObjectStorage/ObjectStorages/Local/LocalObjectStorage.cpp:391` and `:424` (`object_metadata.etag = std::to_string(...nanoseconds(last_write_time)...)`); `CasObjectStorageBackend.cpp:447-465` (`emuMintToken`), `690` (`putOverwrite`), `727` (`casPut`); mode selection `ContentAddressedMetadataStorage.cpp:509-512`.
- **Trigger**: a CAS disk over `object_storage_type=local` (which selects `Mode::EmulatedSingleProcess`) on a filesystem whose mtime granularity is coarser than the rewrite interval for a hot key, combined with more than one `ObjectStorageBackend` over the same pool path — `openPoolView()` constructs a fresh one, with an empty `emu_token_state`, on every mount and remount.
- **Consequence**: in emulated mode the compare-and-swap token that carries the entire single-writer protocol is the object's mtime. Two versions written at the same mtime are separated **only** by `emu_token_state[key] = {etag, counter}`, an in-memory per-backend-instance counter that is incremented only when this instance did the write (`if (just_wrote) ++it->second.second;`). There is no durable version counter. A backend instance that observes a key for the first time therefore mints the bare `etag` (counter 0) for a key whose durable content is already at logical `etag#N`, and `casPut`/`putOverwrite`/`deleteExact` compare `expected` against that freshly minted value — so a token that does not name the current version can compare equal and the conditional write commits, a lost update in the protocol that all CAS ref-log serialisation depends on. The shipped warning at `ContentAddressedMetadataStorage.cpp:515-520` scopes emulated mode to a single *server*; it says nothing about a single backend instance, which is the property the counter actually requires.
- **Evidence**: `emuMintToken` returns `etag` when the key is absent from `emu_token_state`, and `etag + "#" + counter` only when the same instance has seen that exact etag before; `emu_token_state` is a plain `std::map` member of `ObjectStorageBackend` (`CasObjectStorageBackend.h:91`) with no persistence.

### bc6-8 -- emulated token-state pruning stalls permanently when object mtimes are not behind the local wall clock (Medium)

- **Anchor**: `CasObjectStorageBackend.cpp:347-362` (`etagComfortablyInThePast`), `396-416` (`emuPruneTokenState`), `777-784` (the enqueue on delete).
- **Trigger**: the local wall clock is stepped backwards (NTP step, `settimeofday`), or the pool path lives on a mount whose mtimes are produced by a clock ahead of ours (NFS/CIFS server, or files restored with future mtimes), while CAS runs in `Mode::EmulatedSingleProcess`.
- **Consequence**: `etagComfortablyInThePast` reinterprets the etag as wall-clock nanoseconds and requires `now_ns > etag_ns && (now_ns - etag_ns) >= 2s`. If object mtimes are at or ahead of the local clock this is false for the head of `emu_token_expiry`, and `emuPruneTokenState` `break`s out of the sweep at line 409 without popping it — the deque is drained strictly in order, so a single unexpirable head blocks every later entry. `emu_token_expiry` and `emu_token_state` then grow monotonically with every `deleteExact`, for the whole duration of the skew, with no cap; `emuMintToken` calls the sweep on every single token mint, so the stall is silent and the growth is proportional to CAS delete traffic. The same predicate also misreads any all-digits etag that is not a nanosecond timestamp (e.g. a small generation counter) as ancient, erasing live token state eagerly.
- **Evidence**: `if (now_ns <= candidate.queued_at_ns || now_ns - candidate.queued_at_ns < EMU_TOKEN_STALE_AGE_NS) break;` followed by the `etagComfortablyInThePast` erase — both conditions are wall-clock differences against a filesystem-supplied value, and neither has a fallback for the non-monotonic case.

### bc6-9 -- CLOCK_BOOTTIME is used unguarded and is Linux-only (Low)

- **Anchor**: `CasMountRuntime.cpp:60` and `CasServerRoot.cpp:54`, both `clock_gettime(CLOCK_BOOTTIME, &ts)`.
- **Trigger**: a Darwin or FreeBSD build of this tree (both are supported targets — `CMakeLists.txt` carries `OS_DARWIN` branches at `175`, `278`, `359`, `396`, `457`).
- **Consequence**: `CLOCK_BOOTTIME` is a Linux extension; Darwin offers `CLOCK_UPTIME_RAW`/`CLOCK_MONOTONIC_RAW` and FreeBSD offers `CLOCK_UPTIME`, neither under this name. These are the only two occurrences of the macro anywhere in `src/`, `base/` or `contrib/`, so there is no existing compatibility shim to pick it up, and the mount fence — the one clock in the tree deliberately chosen to advance across suspend — has no portable fallback.
- **Evidence**: repository-wide search for `CLOCK_BOOTTIME` returns exactly these two lines; both are inside unconditional function bodies with no `#if defined(OS_LINUX)` guard and no `#else`.

## Checked and sound

- GC round-age health arithmetic is single-clock: `last_success_ms` is stored from `steady_clock` and the age is computed against `steady_clock` with an underflow guard (`CasGcScheduler.cpp:173-176`, `321-323`).
- GC condemnation, graduation and redeletion are generation-based, not wall-clock aged. The only clocks in the mark/sweep path are measurement-only: `Stopwatch watch{CLOCK_MONOTONIC}` (`CasGcPhaseTimer.h:53`) and the round duration at `CasGcScheduler.cpp:151`, `193-194`, `203-204`. There is no time-based condemn grace window to skew.
- Heartbeat-floor fence-out decides on the GC leader's own monotonic clock (`mono_now_ms - first_seen_mono_ms >= stable_threshold_ms`, `CasServerRoot.cpp:506-507`); the wall clock appears only inside the log line (`533-537`), which labels it as such.
- Mount takeover refuses wall-clock trust by construction, with the rule in a shipped string: "not fenced/clean/proven-dead — no wall-clock trust; the caller must run the token-stability observation wait before reclaiming" (`CasServerRoot.cpp:362-364`). The double-start diagnostic explicitly documents its own skew caveat (`377-379`).
- The write fence deadline is anchored on the renew *attempt's* boot time, captured before the request is issued (`CasServerRoot.cpp:741-746`, `849-853`; `CasMountRuntime.cpp:212-213`), so a slow renewal shortens rather than extends the fence. `mayMutate()` and `refAppendFenceOk()` both read that boot deadline (`CasMountRuntime.cpp:77-111`). (The cross-clock issue with the work it admits is bc6-5.)
- Request-control deadlines, attempt timeouts and backoff are `steady_clock` end to end (`CasRequestControl.cpp:80-83`, `168`, `202`, `247`, `264`, `322`, `382`, `453`, `524`); no wall clock participates in any retry decision.
- `system.cas_mounts` units match their columns: `started_at`/`expires_at` are `DateTime64(3)` fed raw millisecond values (`StorageSystemContentAddressedMounts.cpp:47-48`, `171-172`), and `lifecycle_since` is `DateTime` fed whole seconds from `wallClockNowSeconds()` (`59`, `114-115`; `CasMountRuntime.cpp:32-36`, `255`). The `0` sentinel for "live" is filtered before insertion rather than surfacing as 1970.
- CAS event log and GC round log rows derive `event_time` (seconds) and `event_time_microseconds` (microseconds) from one `system_clock::now()` call, so the two columns can never disagree (`ContentAddressedMetadataStorage.cpp:363-365`, `437-439`).
- The part-folder view age check fails safe under a backward clock step: `now_ms_fn() - validatedAtMs()` underflows to a huge unsigned value, which is not `< age_seconds * 1000`, so the entry is revalidated rather than trusted (`PartFolderAccess.cpp:177-178`). A forward step only revalidates early.
- `old_parts_lifetime` and temporary-part protection use the in-memory `remove_time` and the `temporary_parts` set, never disk mtime (`MergeTreeData.cpp:3545`, `3388`, `6099`), so CAS stamps cannot delay or hasten part removal.
- Backup and incremental-backup logic does not consult disk mtime: there is no `getLastModified` call anywhere under `src/Backups`.
- `DatabaseCatalog::cleanupStoreDirectoryTask` cannot act on a CAS disk: it skips any disk whose `supportsStat()` or `supportsChmod()` is false (`DatabaseCatalog.cpp:2025`) and CAS returns false for both (`ContentAddressedMetadataStorage.h:108-109`). This is what keeps the `setLastModified` no-op (bc6-4) from combining with a zeroed `stat` into an unused-directory removal at `DatabaseCatalog.cpp:2099-2126`.
- The persisted decommission timestamp is explicitly UTC-formatted via `gmtime_r` and carries the literal `UTC` suffix in the stored string (`ContentAddressedMetadataStorage.cpp:650-658`), so the `lifecycle_detail` text has no local-timezone ambiguity.
- Detached-part `modification_time` matches local-disk semantics rather than diverging: local `rename` bumps the directory mtime deliberately (`DataPartStorageOnDiskBase.cpp:782`) and CAS's republish sets `published_at_ms` to now, so both report the detach time in `system.detached_parts`.
- `published_at_ms` is written in exactly one place (`CasPartWriteTxn.cpp:721-726`) and always in the same ref transaction as the `OwnerTransition` that creates the committed row (`CasRefProtocol.cpp:248-267`, applied together at `302-303`), so no crash window can leave a committed ref with a `0` stamp. It survives snapshot and log round-trips as the required `ts` field (`CasRefSnapshotFormat.cpp:63-64`, `226-230`; `CasRefLogFormat.cpp:102-103`, `204-210`). No path outside the protocol constructs a `RefCommittedRow`, so fsck and rebuild cannot resurrect refs with a zero stamp. `Pool::updateRefPublishedAt` (`CasPool.cpp:1158`, `CasRefLedger.cpp:3230-3253`) has no production caller.
- Every other `OwnerTransition` producer in the tree is a removal shape, never a promote: `PartFolderAccess.cpp:532`, `CasRefLedger.cpp:3160`, `3208`, `3565`, `3572`, `CasPool.cpp:871`.

No in-tree caller feeds it a CAS path today, so this was not written up as a finding; it becomes one the moment a caller appears.
- Mtimes of namespace files under `deduplication_logs/` were not traced to a consumer; they fall in the epoch-0 class (bc6-3) but no reader of their mtime was found.
- Shadow/freeze stamp behaviour was read statically from the routing and promote paths only. The interaction between `ALTER TABLE FREEZE` re-freezing an existing backup name and the resulting stamp was not traced end to end.
- Dynamic confirmation of every finding is unavailable in this tree: all CAS tests are deleted in the working tree, so nothing asserts the returned values, the epoch-0 sentinel, the emulated token disambiguation, or the boot-vs-monotonic budget relationship. Triggers above are stated as code paths, not as observed runs.
