Distributed-systems audit for PR #2159 (ClickHouse CAS at `ceee42c51a06cb05e2c9a2d811ef7e1726825552`):

Model assumptions:
- Actors: ClickHouse servers (each a `cas_server_root_id` mount), one shared object-store pool (S3/GCS/local), in-process GC leader + heartbeat, mount-lease keeper, detached-work dispatcher; Keeper is used only by ReplicatedMergeTree, not by the pool protocol.
- Channels: conditional object-store PUT/GET/HEAD/DELETE/LIST (refs, leases, catalog, GC state); no RPC between CAS nodes; shared bucket is the sole coordination medium.
- Failure model assumed by code: crash-recover processes, lossy/ambiguous object-store responses (resolved by exact GET + `write_attempt_id`), bounded request budget (~90s / 16 attempts), CLOCK_BOOTTIME local fences, observation-window GC steal (no wall-clock GC-lease TTL), fail-closed on identity/format mismatch. Environment is partially synchronous with unbounded object-store delay.

Confirmed defects:

### Partition / availability

    High: Nested `server_root_id` is a valid identity, but decommission and emptiness probes treat it as a path prefix
        Impact: `SYSTEM CAS DROP POOL MEMBER` on parent `a` drops live member `a/b`'s catalog namespaces and deletes its manifests, staging, and `roots/` objects. Two legally mounted members become one destructive domain.
        Anchor: `Pool/CasServerRoot.h` / `validateServerRootId`; `Tools/CasDecommission.cpp` / `decommissionPoolMember` (`victim_srid + "/"`); `Pool/CasServerRoot.cpp` / `serverRootSubtreeEmpty`; `Formats/CasLayout.h` / `serverRootPrefix`, `serverRootDataPrefix`, `casManifestsServerPrefix`
        Trigger: Two replicas configured with hierarchical ids the validator accepts (`dc1` and `dc1/host1`, or `{cluster}/{replica}` next to `{cluster}`). Operator decommissions the shorter id.
        Why defect: Distinct owner/epoch/mount keys exist, but every ownership sweep concatenates `srid + "/"` or `<prefix>/<srid>/`. The slash that stops `victim` matching `victim2` does not stop `a` matching `a/b/...`.
        Fix direction (short): Reject any `server_root_id` that is a path prefix of another mounted id; match ownership by exact catalog creator / exact layout prefix with a terminator that cannot nest.
        Regression test direction (short): Mount `a` and `a/b`, run `DROP POOL MEMBER 'a'`, assert `a/b` namespaces, manifests, and mount slot survive.

### Timing / ordering

    Medium: GC ref-object cleanup requires the pool-global catalog token to be unchanged for the whole remaining pass
        Impact: Any catalog mutation on any member (CREATE/DROP table, namespace life change) aborts the rest of that round's covered-log deletes. Reclamation of already-folded ref objects stalls under ordinary multi-tenant churn.
        Anchor: `Gc/CasGc.cpp` / `Gc::cleanupRefObjects` (`current_catalog.token != folded.catalog_cut->token` then `return false`)
        Trigger: Leader is in ref-cleanup while any other server publishes a catalog CAS.
        Why defect: The safety argument only needs the target row/life and the GC lease to be stable. Requiring the whole-catalog token to be still makes one unrelated write a pool-wide cleanup abort. Same class previously removed from the ref-writer path.
        Fix direction (short): Revalidate the target catalog row, life id, and `gc/state` lease only; do not compare the pool-global catalog token.
        Regression test direction (short): Fold a covered log, mutate an unrelated namespace mid-cleanup, assert the original key is still exact-deleted.

### Idempotency & duplicates

    Medium: `getStorageObjects` omits the blob payload offset, so same-type object-storage copy publishes envelope bytes as file content
        Impact: Server-side copy (`DiskObjectStorage::copyFile` when `DataSourceDescription` matches) copies the whole CAS blob, including the fixed envelope. Destination files are not the logical part bytes. Same-host BACKUP-to-S3 and MOVE to another object-storage disk with the same description take this path. Cross-type MOVE (CAS S3 → local) uses `readFile`/`prepareRead` and is safe.
        Anchor: `ContentAddressedMetadataStorage.cpp` / `ContentAddressedMetadataStorage::getStorageObjects` (`StoredObject(location.key, path, location.length)`); `DiskObjectStorage.cpp` / `DiskObjectStorage::copyFile`; `DiskObjectStorageTransaction.cpp` / `copyFileImpl`
        Trigger: `BACKUP` to an S3 disk on the same host, or `copyFile`/`MOVE PARTITION` onto another object-storage disk whose data-source description equals the CAS disk.
        Why defect: The byte-reading path applies `getBlobViewPlan`'s window; the copy path does not. There is no source-side content-address guard on the copied object.
        Fix direction (short): Return the payload window from `getStorageObjects`, or refuse server-side copy on CA and force the `prepareRead` path.
        Regression test direction (short): Copy one blob-backed part file to a second S3 disk; assert destination bytes equal the logical payload, not envelope+payload.

### Backpressure & resource limits

    Medium: `SYSTEM CAS FSCK` holds `lifecycle_mutex` for the whole scan and passes no deadline
        Impact: FORGET / GC STOP / GC START serialize behind a pool-wide LIST/GET walk with no timeout and no `KILL QUERY` hook. On a large pool this is unbounded admin unavailability. Offline `cas-fsck --timeout` exists; the SQL verb does not.
        Anchor: `ContentAddressedMetadataStorage.cpp` / `ContentAddressedMetadataStorage::runFsckNow`; `InterpreterSystemQuery.cpp` / `runContentAddressedFsck`; `Tools/CasFsck.cpp` / `runFsck` (deadline default empty)
        Trigger: `SYSTEM CAS FSCK <disk>` on a pool whose `roots/` / blob LIST exceeds minutes, concurrent with `SYSTEM CAS GC STOP` or `FORGET`.
        Why defect: The CLI path already bounds the scan. The live verb takes the outermost lifecycle lock and never installs a deadline or cancellation.
        Fix direction (short): Pass a deadline (setting or `max_execution_time`), poll cancellation between pages, and do not hold `lifecycle_mutex` across I/O.
        Regression test direction (short): Start FSCK against a large fixture; issue `KILL QUERY` / expire `max_execution_time`; assert FSCK terminates and GC STOP is admitted.

    Medium: Each GC hot scan materializes every `cas/ns/stream/` key in memory
        Impact: The GC leader's RSS grows with the pool-wide ref-object count (`scan.keys.push_back` plus the per-life indexes). Default `gc_shards=1`. A large shared pool can OOM the elected leader and stall reclamation until remount/steal.
        Anchor: `Gc/CasGc.cpp` / `Gc::enumerateRefPrefix` (`listRefPrefix` caller)
        Trigger: One pool holding millions of parts from many servers; next regular or manual GC round.
        Why defect: The listing is paged from the backend but retained as one in-memory vector for the rest of the round. There is no cap other than process memory.
        Fix direction (short): Stream keys per life / per page into the walk plan; do not keep the global key vector.
        Regression test direction (short): Inject a large synthetic listing and assert peak retained keys stay within the page budget.

### Recovery & rollback

    Medium: Offline `cas-gc-rebuild` has no mount-lease interlock against a live writer
        Impact: The tool only requires `<readonly>true</readonly>` on *its* disk open, then `acquireOrRenewLease(..., allow_steal=false)`. If `gc/state` is absent or free (live GC never elected, or a virgin-looking listing), rebuild writes a new baseline while a live server is still publishing refs. Server-side `SYSTEM CAS GC REBUILD` is serialized on the live disk and is safe.
        Anchor: `programs/disks/CommandCaGcRebuild.cpp` / `CommandCaGcRebuild::executeImpl`; `Gc/CasGc.cpp` / `Gc::rebuildBaseline`
        Trigger: Operator runs `clickhouse-disks --disk cas cas-gc-rebuild` against the same prefix a live server has mounted, while that server's scheduler has not yet committed a `gc/state` lease.
        Why defect: Read-only open prevents claiming the *mount* slot; it does not prove no live writer exists. Rebuild is a disaster-recovery write of `gc/state` and hold-carry.
        Fix direction (short): Refuse rebuild unless every mount slot is terminated/fenced or the operator passes an explicit live-pool override.
        Regression test direction (short): Live writable mount + offline readonly rebuild on an empty `gc/state`; assert refusal.

    Low: Namespace janitor rewinds its cursor to empty on any LIST error
        Impact: Dead-life stream/state debris is scanned from the start of the prefix after a transient LIST failure. Reclamation is delayed, not lost; fsck still counts the debris.
        Anchor: `Gc/CasNamespaceJanitor.cpp` / `NamespaceJanitor::runOnePage` (catch around `backend.list` writes empty `GcMaintenanceState`)
        Trigger: Object-store LIST of `cas/ns/` returns a retryable error mid-janitor page.
        Why defect: A transient LIST failure is treated as "forget progress" rather than "retry this cursor".
        Fix direction (short): Keep the last good cursor on LIST failure; only reset on a decoded corrupt maintenance object.
        Regression test direction (short): Fail one LIST after a non-empty cursor; assert the next page resumes at that cursor.

### Configuration & version skew

    Medium: `ContentAddressedMetadataStorage` does not implement `applyNewSettings`, so `SYSTEM RELOAD CONFIG` never changes CAS settings
        Impact: After a rolling config reload, nodes disagree on `cas_gc_enabled`, `cas_gc_interval_sec`, cache budgets, and similar live knobs while XML already shows the new values. A disk removed from config keeps renewing its mount lease until process restart. Mixed in-process policy across a replica set during the reload window.
        Anchor: `IMetadataStorage.h` / `IMetadataStorage::applyNewSettings` (default empty); `DiskObjectStorage.cpp` / `DiskObjectStorage::applyNewSettings` (calls it); no override on `ContentAddressedMetadataStorage`
        Trigger: Change `cas_gc_enabled` or `cas_gc_interval_sec` and run `SYSTEM RELOAD CONFIG` on a subset of replicas.
        Why defect: The disk layer advertises live reload; the CAS metadata object ignores it with no log line.
        Fix direction (short): Override `applyNewSettings` for the live-safe subset and log ignored/restart-required keys; stop the keeper when the disk disappears from config.
        Regression test direction (short): Toggle `cas_gc_interval_sec` via reload; assert the scheduler period changes (or a loud "restart required" is logged).

### Network / transport

    Low: Recovery, FSCK, and GC admin waits ignore query cancellation
        Impact: `KILL QUERY` / `max_execution_time` do not interrupt `SYSTEM CAS FSCK`, `GC RUN`, `GC REBUILD`, or in-flight ref-table recovery. Each inner object-store call is still budgeted (~90s / 16 attempts, recovery 120s), so the hang is long but finite per attempt; summed work has no cooperative abort.
        Anchor: `Pool/CasRefLedger.cpp` / recovery wait (`recovery_retry_budget_ms`); `ContentAddressedMetadataStorage.cpp` / `runFsckNow`, `runGarbageCollectionRoundNow` (no `CurrentThread` cancel checks)
        Trigger: Operator kills a stuck `SYSTEM CAS GC RUN` or `FSCK` on a large pool.
        Why defect: The request controller bounds transport; the admin/recovery loops never observe the query cancel flag.
        Fix direction (short): Check `isCancelled` / deadline between pages and between recovery attempts.
        Regression test direction (short): Start FSCK or recovery; `KILL QUERY`; assert the verb returns a cancellation error before the full budget.

### Security / trust across nodes

No confirmed distributed-systems defects in reviewed scope. Intra-pool trust is the bucket credential (no peer authentication). `SYSTEM CAS *` is gated by `GLOBAL` privileges. That trust boundary is a design position, not a confirmed defect.

### Observability & diagnosability

    Low: Ref-cleanup abort on catalog movement is `LOG_DEBUG` only
        Impact: Operators watching `pending_reclaim` / `system.cas_gc_log` see a successful or deferred round that deleted fewer covered logs than expected, with no Finish-level reason. Cross-node catalog churn is indistinguishable from a healthy cheap round.
        Anchor: `Gc/CasGc.cpp` / `Gc::cleanupRefObjects` (`LOG_DEBUG` "...catalog observation/life moved")
        Trigger: Cleanup abort from the catalog-token check above, default log level.
        Why defect: A pool-wide liveness failure is recorded only at DEBUG and is not a `cas_gc_log` anomaly.
        Fix direction (short): Count and emit a `GcAnomaly` / Finish metric when cleanup stops for revalidation.
        Regression test direction (short): Force a catalog-token abort; assert a `system.cas_gc_log` / `system.cas_log` row names the stop.
