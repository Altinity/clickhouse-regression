# CAS audit re-run — consolidated NEW findings

Findings that were not in the original catalog, grouped by audit source. 70 items total across 22 audits (16 audits reported no new findings and are omitted).

---

## ad1-hash-determinism

- **NEW-AD1-1 (Low)** — `blob_hash_allow_new` semantics are dedup-fracturing by design. Anchor: `Pool/CasPoolMeta.cpp:75-101`. An operator flipping `<blob_hash_allow_new>1</blob_hash_allow_new>` and reopening with a different algo CAS-unions the new algo into `algos_used`, but from that point new writes and old writes of byte-identical content live at different keys (`blobs/ch128/S/<hex>` vs `blobs/sha256/S/<hex>`, per `CasLayout.cpp:36`). Intended safety behavior (never overwrite) but the dedup ratio degrades permanently for affected content, with no operator warning — a silent dedup fork event visible only via `system.parts.bytes_on_disk` vs physical bytes. Deserves a doc/warn.
- **NEW-AD1-2 (Info)** — `payload_digest` is hardcoded to CityHash128 regardless of pool algo. Anchor: `Formats/CasPartManifestFormat.cpp:306-317` (`computePayloadDigest` calls `CityHash_v1_0_2::CityHash128`). By comment (`CasPartManifestFormat.h:95-100`) `payload_digest` is integrity/debug only — "never a key, never dedup, never in-degree" — so not a correctness issue, but a sha256-configured pool still has one internal integrity check (manifest self-digest) that is non-cryptographic. Scope caveat when reasoning "sha256 pool ⇒ all CAS hashes are crypto".
- **NEW-AD1-3 (Info)** — CAS-025 fix incidentally lands here. `Formats/CasPartManifestFormat.cpp:293-301` now re-computes `payload_digest` on `decodePartManifest` and throws `CORRUPTED_DATA` on mismatch. Original AD1 audit predates this; belongs to `bc4-protobuf-decode` / integrity family.

## ad2-deletion-erasure

- **NEW-ad2-1 (High for compliance)** — `isBucketVersioningEnabled()` unknown → mount proceeds. Anchor: `Backend/CasObjectStorageBackend.cpp:61-75`. On a bucket where `GetBucketVersioning` errors (permissions denied) or the backend has no answer, CAS logs a WARNING and mounts. If versioning is in fact ON, every future `deleteExact` becomes a delete-marker (`Gc/CasGc.cpp:519`) and reclaim silently stops. For a regulated deployment the correct default is fail-closed on "unknown", not "assume off".
- **NEW-ad2-2 (Med)** — versioning precondition is GCS-only; S3 versioning / object-lock / CRR / soft-delete not checked. Anchor: `Backend/CasObjectStorageBackend.cpp:57-58`. Mount CAS over an S3 bucket with versioning, MFA-delete, object-lock retention, lifecycle rules that transition-to-Glacier before expiring, or CRR to a bucket CAS never deletes — `checkPoolPreconditions` returns immediately without touching any of these. The GC-side "delete marker created" log warning (`Gc/CasGc.cpp:519`) is the only after-the-fact signal.
- **NEW-ad2-3 (Med)** — no post-`deleteExact` verification anywhere in the pipeline. Anchor: `Backend/CasBackend.h:102-132` (`DeleteOutcome`); no HEAD-after-DELETE around `deleteExact` sites (`Tools/CasDecommission.cpp:57,81`). Any object-store that acknowledges DELETE but retains the object (soft-delete window, replicated-copy retention) — CAS marks the blob reclaimed and drops it from `blobIndegree`; no later fsck notices the survivor because the ref side is gone. Compliance-grade "prove erased" cannot be assembled from the outcomes CAS records.
- **NEW-ad2-4 (Med)** — `SYSTEM CONTENT ADDRESSED FORGET` explicitly documents "erasure NOT verified". Anchor: `Pool/CasPool.cpp:135,328-332,755,966`; `ContentAddressedMetadataStorage.cpp:926-929,1046,1140-1160`. The operator's only advertised "make this pool go away" verb is spec'd, in the code itself, as a non-erasure assertion. Reinforces ERASE-1/ERASE-2/ERASE-5 as a contractual gap.
- **NEW-ad2-5 (Low)** — `gc_snap_generations_to_keep` retention floor is uncapped by wall-clock. Anchor: `Pool/CasPool.h:79-84`, `Gc/CasGc.cpp:762,2319`. A CAS pool with very-slow GC rounds retains the last N snap generations even if each generation is weeks old; metadata about reclaimed subjects (ERASE-4) can therefore live much longer than "3 rounds" implies.

## ad3-day2-dr-runbook

- **NEW-ad3-1 (Low)** — SQL fsck cannot bound its runtime. `Cas::runFsck` accepts a `deadline` and a `partial_on_deadline` flag (`CasFsck.h:148-150`), but `runContentAddressedFsck` in `InterpreterSystemQuery.cpp:2524-2551` never plumbs the query-level `max_execution_time` / an explicit `DEADLINE '...'` clause into it. An operator running `SYSTEM CONTENT ADDRESSED FSCK` against a large / slow pool has no way to say "give me what you have after 10 min"; the scan runs to completion or throws `TIMEOUT_EXCEEDED` from `checkDeadline` (`CasFsck.cpp:43-48`). Anchor: `InterpreterSystemQuery.cpp:2537` (`runFsckNow(false)` — no deadline).
- **NEW-ad3-2 (Low)** — `SYSTEM CONTENT ADDRESSED GC STOP` truthfully-but-misleadingly reports `is_leader`. Comment at `InterpreterSystemQuery.cpp:1018-1023` explains that after GC is stopped, an explicit `GC RUN` can still transiently set `is_leader=1` on the disk — `system.content_addressed_mounts.is_leader` will show that until a peer steals the lease. Documented and intentional but a Day-2 footgun: dashboards keyed on `is_leader AND NOT gc_running` see a phantom leader window during operator-initiated GC RUNs after a STOP.
- **NEW-ad3-3 (Low)** — `SYSTEM CONTENT ADDRESSED FORGET` explicitly does not verify erasure. `InterpreterSystemQuery.cpp:2570-2575` — the log line spells out "erasure NOT verified. The disk stays registered and answers store-class access with a typed error". Combined with CAS-093 (fsck cannot repair) and CAS-084 (MPU orphans), a `FORGET` on a disk with in-flight writes / orphaned MPUs leaves cleanup entirely to whatever bucket lifecycle rule the operator remembered.
- **NEW-ad3-4 (Info)** — `Nullable` peer-row columns in `content_addressed_mounts` are a good pattern to keep. `StorageSystemContentAddressedMounts.cpp:194-210` deliberately writes `NULL` for `is_leader` / `pending_reclaim` / `last_success_age_seconds` / `wedged_namespace_count` on rows describing other servers' mounts. Prevents the "peer B is GC leader" misread; worth codifying for future per-disk/per-node CAS views (relates to CAS-101 quirks).

## ad4-migration

- **NEW-MIG-1 (Med)** — CAS-041 explicit sub-case: CAS → CAS same-pool MOVE does NOT relink; it byte-copies through streaming reads+writes. Anchor: `src/Storages/MergeTree/MergeTreePartsMover.cpp:223-282` (no `getPoolUUID` / pool-identity branch); `src/Storages/MergeTree/DataPartStorageOnDiskBase.cpp:735-758` (CA-aware `clonePart` runs `copyDirectoryContentIntoTransaction` — streamed read from src + streamed write to dst, not a manifest-level relink). Trigger: `ALTER TABLE ... MOVE PARTITION ... TO DISK d2` where both `d1`/`d2` are CAS disks sharing the same `pool_uuid`. The wire-protocol fetch path DOES gate on `receiver_pool_uuid == sender.getPoolUUID()` and relink instead of byte-fetching — the equivalent optimization is missing on the local cross-disk MOVE path. Same-pool CAS→CAS MOVE re-uploads every blob body (dedups on landing via HEAD-first, but source disk fully read and per-blob HEAD × N blobs).
- **NEW-MIG-2 (Med)** — CAS-210 confirmed: HEAD-first "dedup on landing" trusts backend object identity by NAME only; no body re-hash verify. Anchor: `Pool/CasPartWriteTxn.cpp:189-212`. On a HEAD hit, the writer calls `observeAndAdmit(ObjectKind::Blob, logical_ref, key, hr)` and admits the existing object without a body GET or hash re-verify. If the existing S3 object under `key` was silently mutated (LIFE-1/LIFE-2/LIFE-5) or was written by a buggy earlier build under the same key but different bytes, the new writer will adopt the corrupt object without ever reading it. INV-NO-LOSS is respected (a ref exists), but the ref points at bytes the writer never validated. The byte COUNT is verified against `source.size`; the byte CONTENT is not.
- **NEW-MIG-3 (Med)** — provenance envelope field is present but NOT driven by the operation kind; every fresh CAS write hardcodes `ProvenanceOp::Insert`. Anchor: `ContentAddressedTransaction.cpp:148-155` (`.op = Cas::ProvenanceOp::Insert`). Every part-write transaction is opened with `op = Insert`, regardless of INSERT SELECT (migration), merge output, mutation output, MOVE-landing, RESTORE-landing. Only `Insert`/`Other`/`Attach` are ever emitted from production; `Merge`/`Mutation`/`Repack` are defined but unused. Diagnostic/attestation gap directly relevant to the migration audit (was the point of adding the enum).
- **NEW-MIG-4 (Low)** — off-CAS MOVE reads never re-verify blob against manifest/BLAKE hash — INT-1 exposure at migration boundary is symmetric with NEW-MIG-2. Anchor: `DataPartStorageOnDiskBase.cpp:707-710` streamed copy loop, plus the CAS backend's plain ranged GET path (no verify-after-read hook). Strengthens MIG-6: corruption admitted at write time (NEW-MIG-2) propagates unchecked at off-CAS migration read time. MergeTree-level `checksums.txt`/`CHECK TABLE` still catch it if the operator opts in.

## ad5-resource-exhaustion

- **NEW-ad5-1 (Med)** — the manifest write path is hard fail-closed only; no smoothing at all near the caps. `Pool/CasPartWriteTxn.cpp:824-872` enforces `kMaxManifestEntries = 1_048_576`, `kMaxManifestInlineBytesTotal = 16 MiB`, `kMaxLargestInlineEntryBytes = 1 MiB`, `kMaxManifestEncodedBytes = 256 MiB` as unconditional `LIMIT_EXCEEDED` throws. Original AD-5 recommended a governor + surfaced distance-to-hard-limit metric so an operator could see the wedge coming; current design has neither the ≤ 1 s soft-limit backpressure nor a "distance-to-cap" metric. Under sustained churn, the first sign of trouble is a failed write, not a warned-and-throttled one.
- **NEW-ad5-2 (Low)** — `enforceRefTableCacheBudget` LRU-evicts a namespace's cached state; a hot table churning enough to force re-hydration under memory pressure pays repeated recovery cost. `Pool/CasRefLedger.cpp:762-810` walks all cached tables and evicts LRU non-`keep_ns` entries until total is ≤ `ref_table_cache_bytes` (default 256 MiB, `Pool/CasPool.h:204`). At extreme multi-tenancy (many active namespaces, each with large committed / owned_manifests state), this can become a re-recovery hot loop.
- **NEW-ad5-3 (Low)** — `RefLog` / `RefSnapshot` seal-decode ceilings are 64 MiB decompressed and enforced at decode, but the encode-side complete-table admission uses the same 64 MiB budget with only `kRefAdmissionSafetyMargin` headroom — essentially zero real slack. `Formats/CasFormat.cpp:98-99` + `Formats/CasRefSnapshotFormat.h:67` + `Pool/CasRefLedger.cpp:572-577`. A namespace with a very long name plus a snapshot right at the budget can be admissible on the encode side yet fail at decode on the next mount if any per-field overhead grew after encode.

Anchor: `Backend/CasObjectStorageBackend.cpp:69-74`. Suggested hardening: promote to `LOG_ERROR` plus surface in `system.content_addressed_mounts`. Narrows CAS-011.

## ad7-protocol-skew

- **NEW-ad7-1 (Info)** — `assertEOF` after `readStringBinary(sender_manifest_bytes)` will hard-fail any future v2-with-trailer sender talking to this exact v2 receiver. Anchor: `DataPartsExchange.cpp:936-937`. Not a bug — the intended forward-incompat behavior (SKEW-1 hardening's inverse: any future framing addition MUST bump the cookie). Worth documenting in wire-contract text alongside `CA_RELINK_COOKIE_VALUE`.
- **NEW-ad7-2 (Info)** — Cookie-value gate happens BEFORE the pool-uuid re-check, but AFTER `ca_relink` cookie parse — an empty cookie value on the wire is silently treated as "no relink" rather than as a malformed offer. Anchor: `DataPartsExchange.cpp:889-890`. Safe fallback direction, but obscures a diagnosable sender bug.
- **NEW-ad7-3 (Info)** — `locate()` does not read the envelope's own `header_len` before ranging — soft coupling to pool_meta's `blob_header_len` invariant. Anchor: `Pool/CasManifestReader.cpp:144-168`. Any future code path that permits an envelope's `header_len` to disagree with `PoolMeta::blob_header_len` would silently misread payload offsets on the ranged path. Recommendation: assert `header.header_len == meta.blob_header_len` where a full envelope read already happens.

## bc1-offset-overflow

- **NEW-bc1-1 (Low)** — `decodeEnvelopeHeader` discards `object_size` but the payload extent still depends on `object_size >= h.header_len`, which is **not checked here**. Anchor: `Formats/CasBlobEnvelopeFormat.cpp:162` + `CasBlobEnvelopeFormat.h:88-95`. A corrupt/truncated object whose real `object_size < h.header_len` yields a size_t-underflow when a caller computes `object_size - header_len`. Invariant lives in a comment rather than a local check — mild regression in "local guard" hygiene compared to the old `header_len + logical_size == object_size` explicit assertion.
- **NEW-bc1-2 (Info)** — `getBlobViewPlan`'s `StoredObject(..., location.offset + location.length)` and `readBlobPayload`'s identical expression are duplicated. Anchor: `ContentAddressedMetadataStorage.cpp:1915` and `:1930`. DRY hygiene note — factor `location.readEnd()` on `BlobLocation` with a single overflow-guarded add.

## bc2-writebuffer-spill

- **NEW-BC2-7 (Low)** — `SCOPE_EXIT`-only cleanup covers throw but not a survivor if `stageBlobPartFile` succeeds and a later transaction step throws (inline-overflow branch). Anchor: `ContentAddressedTransaction.cpp:952–972`. The file has no fsync either (`WriteBufferFromFile tmp(...); tmp.finalize()` — implied). If the same BC2-2 page-cache-loss hazard hits the inline-overflow blob (rare — trigger is > `INLINE_CAP` "inline-candidate"), the same silent key-vs-bytes divergence applies.
- **NEW-BC2-8 (Low)** — envelope header pre-write is not covered by the streaming-size sanity check in S3 staging. Anchor: `ContentAddressedTransaction.cpp:1793–1794` and `Pool/CasPartWriteTxn.cpp:594–602`. The buffer emits `envelope_header` directly to the sink (bypassing `hashing`) BEFORE the payload starts; if the caller-supplied sink accepts the header but silently short-writes it, the staging object holds a truncated header + full payload; `promoteStaged` copies verbatim, and decode-time header validation fails at read time. Defense-in-depth: Local-mode has `written == source.size` at `CasPartWriteTxn.cpp:600` for the payload; S3-staging header pre-write has no equivalent guard.
- **NEW-BC2-9 (Info)** — inline-overflow bounded but still holds full bytes in memory before spill. Anchor: `ContentAddressedTransaction.cpp:920–971`. Same shape as BC2-6 in the original audit, retained. A caller misrouting a large file to the inline path still pays the full in-memory cost before the streaming spill.

## bc7-blocking-io-locks

- **NEW-BC7-1 (Med)** — Asymmetric fix: replicated write paths use the `renameParts()` off-lock publish, but plain-MergeTree paths (`MergeTreeSink.cpp:379`, `MutatePlainMergeTreeTask.cpp:134`, `MergePlainMergeTreeTask.cpp:160`) still publish under `DataPartsLock`. Plain MergeTree over CAS therefore keeps the full BC7-1 stall behavior. The blocking `FIXME` at `MergeTreeSink.cpp:369-378` states the covered-part-vs-merge-selection race prevents flipping `rename_in_transaction` to `true` without a deeper redesign.

A future refactor that populates `precommitted_parts` without going through `preparePartForCommit`'s `rename_in_transaction=true` branch silently regresses back under `DataPartsLock`. No assertion prevents it.

## codeonly-line

- **NEW-codeonly-line-1 (Low)** — Non-cryptographic checksum still trusted on run objects, now under `CityHash128`-of-object-body — `Formats/CasRecordStreamFormat.cpp:210-219` (`sourceEdgeRunChecksum`). The change from CRC32C to chained CityHash128 does not close the "forgeable, pool-participant can plant a valid run" class; combined with CAS-004 the trust boundary is unchanged. A `DBMS_DEFAULT_HASHING_BLOCK_SIZE` change now silently forks *two* independent hash chains, not one.
- **NEW-codeonly-line-2 (Info)** — Envelope pad-zone now enforces "must be ASCII space up to '\n'" — `CasBlobEnvelopeFormat.cpp:230-248`. Reads any non-space byte as `CORRUPTED_DATA`. Real improvement over the old envelope; closes the smuggling side of the old `ENV-3` finding.
- **NEW-codeonly-line-3 (Low)** — `PartWriteTxn::adoptEvidence` records the sender-supplied `entry.blob_size` in `deps[entry.ref]` and then verifies only that a blob exists in `promote`. Same net gap as MW-1: `CAS-025`'s `payload_digest` verifies canonical encoding but the receiver still adopts sender-supplied `blob_size` without cross-checking against the pool's canonical blob envelope.
- **NEW-codeonly-line-4 (Info)** — `checkNamespace` is now also called on operator-supplied `server_root_id`-derived subpaths via a wide surface (`refsNamespacePrefix`, `manifestNamespacePrefix`, `namespaceFileKey`, `namespaceFilesPrefix`). Missing `.`/`..` guard (LAY-1) is unchanged in scope, but the number of call sites depending on it silently accepting benign namespaces has grown; fixing LAY-1 has correspondingly larger safety return.

## datatype-agnosticism

- **NEW-datatype-agnosticism-1 (Info)** — original audit's Layer 1 quote used `UInt128 blob_hash{}`. In current code the hash + algorithm are packed into a single `BlobRef ref` (`Formats/CasPartManifestFormat.h:54`), and `blobKey` renders the algo as its own key segment (`CasLayout.cpp:36`). Wire-format refinement (multi-algorithm-per-pool support), not a data-type coupling.
- **NEW-datatype-agnosticism-2 (Info)** — original audit's edge-case table noted mutable per-part files (`uuid.txt`/`txn_version.txt`/`metadata_version.txt`) were kept out of the content manifest. Current code has removed that special case (`ContentAddressedTransaction.cpp:844-850`): all three names fall through to the ordinary content path. Strengthens agnosticism — one fewer name-based branch.
- **NEW-datatype-agnosticism-3 (Info)** — the only place CAS inspects a file's name to alter behavior is `Cas::partFileMustStayBlob` (`ContentAddressedTransaction.cpp:65-73`) which handles `primary.idx`/`.bin`/`.mrk*`/`.cmrk*`. Structural MergeTree-file-shape predicate applied uniformly to every column type — not a type dependency. Called out to preempt future reviewers reading the suffix list as one.

## jepsen-anomaly

- **NEW-jepsen-1 (Med — observability/operability)** — Post-write fence-loss surfaces as `Unresolved`, never `Committed`; but the durable object may exist and be visible to other mounts. Anchor: `Backend/CasRequestControl.cpp:361-365, 421-425, 487-489, 515-517, 568-570, 596-598`. A paused / superseded writer whose PUT lands after `fence_ok` starts returning false — local return is `CasWriteOutcome::Unresolved` + `ProfileEvents::CasConditionalWriteFenceLostPostWrite` bump, but the OBJECT is durable on S3 and visible to any future reader that shares the key. Silently indistinguishable from CAS-002's zombie-write outcome on the storage plane. Recommended: on FenceLostPostWrite, log key+body-hash; consider best-effort DELETE against the exact token.
- **NEW-jepsen-2 (Low — soft-vs-hard fence)** — `fenceGeneration` admission covers the durable-effect blob finalize path only for `ContentAddressedTransaction::writeFile`; the ref-append lane relies on `fence_ok_fn` (boolean) rather than a captured generation token. Anchor: `Pool/CasPool.h:328-337`; `CasRefLedger.cpp:145-165`. A rapid trip-latch → arm cycle between pre-check and S3 response would flip `fence_ok_fn` back to true — the post-check would incorrectly succeed under the wrong incarnation.
- **NEW-jepsen-3 (Med-High)** — X1/R1 reader pin gap surface is unchanged; the refactor added no reader-side coupling to GC's ack floor. Anchor: `Pool/CasPool.h:289-306`; reader path `ContentAddressedMetadataStorage.cpp:1886-1933` never touches `renewWatermarkOnce` / `minActive`. Any deferred blob GET on a shared/cross-node read path (RESTORE from snapshot, distributed SELECT, `FETCH` copy) is exposed to a concurrent GC delete round. Extending it with a "reader min-manifest-ref pin" folded into the union used by `graduateForDelete` is a clean fix but was not made.

## read-protocol

- **NEW-read-1 (Med, liveness)** — `readManifestShared` HEAD-GET race window amplifies dangle. Anchor `Pool/CasManifestReader.cpp:65-90`. HEAD at l.65 and GET at l.87 are separate backend round-trips. A GC that deletes the manifest object between them surfaces as `"manifest at {} vanished between head and get — INV-NO-DANGLE"` (`FILE_DOESNT_EXIST`). Fail-loud liveness, not correctness, but a same-manifest instance of the CAS-001 class applied to manifests.
- **NEW-read-2 (Low, coverage)** — Retained-view age policy uses wall-clock `now_ms_fn()` (`PartFolderAccess.cpp:203`) subtracted from `cached->validatedAtMs()`. On backward wall-clock movement (NTP step) the freshness gate can either extend indefinitely (past > now) or refuse every cached view. Same J3 clock-skew class as CAS-030 but on a purely read-serving cache.
- **NEW-read-3 (Info)** — `CachedPartFolderAccess::buildView` single-flight drops leader exceptions onto every follower (`l.301: promise.set_exception`). One HEAD failure fans out to N `FILE_DOESNT_EXIST` errors for N coalesced readers. Correct semantically but distinguishes coalesced from independent readers in error budgets / retry storms.

## security

- **NEW-security-1 (Med — default-hardening)** — `BlobHashAlgo` default is `CityHash128`. Anchor: `Primitives/CasBlobDigest.h:207-214` (`BlobRef { BlobHashAlgo algo = BlobHashAlgo::CityHash128; ... }`); `parseBlobHashAlgo` (`CasBlobDigest.cpp:33-45`) allows `cityhash128 | xxh3-128 | sha256` but does not privilege `sha256`. A pool created without an explicit `blob_hash = sha256` disk-config value inherits the non-crypto default. In a multi-trust-domain pool, this reverts CAS-003 to its original posture. Recommendation: when the pool spans trust domains, require an explicit choice, warn on `cityhash128`, document `sha256` as recommended default.
- **NEW-security-2 (Low — clean-shutdown)** — `Xxh3128BlobHashingWriteBuffer::finalizeImpl` is not overridden; `getHashHex` calls `next()` but skips `finalize()`, and the class also lacks a `cancelImpl`. Anchor: `Primitives/CasBlobHashingWriteBuffer.cpp:96-134`. Compare to `CityHash128BlobHashingWriteBuffer` (`:78-87`) which overrides both. A mid-upload exception on the XXH3 path can leave the underlying sink dangling with data. Recommendation: mirror the overrides across all three subclasses.
- **NEW-security-3 (Low — defense in depth)** — `_pool_meta` / `_manifests` / `_files` reserved-segment gate does not include the newer reserved prefixes in the `roots/` and `blobs/` trees. Anchor: `Formats/CasLayout.cpp:274-279`. `roots/`, `blobs/`, `cas/refs/`, `cas/manifests/`, `gc/`, `gc/server-roots/` now carry reserved subtrees; `checkNamespace` only rejects two literal segment names. Recommendation: enumerate reserved segments from a single registry in `Formats/README.md` and drive `checkNamespace` from it.
- **NEW-security-4 (Low)** — `mountpointObjectKey` and `checkNamespace` accept single-character segments `.` and `..` (sub-finding of CAS-074, called out separately for the mountpoint path). Anchor: `CasLayout.h:229-235`. A caller passing `srv1/../gc/state` yields `<prefix>/roots/srv1/../gc/state` — safe on an object store (distinct literal key) but traverses into the control plane on `LocalObjectStorage` or any future path-normalizing wrapper. Recommendation: add the same `..`/`.` per-segment scan that `namespaceFileKey` (`CasLayout.h:182-184`) already does.

## tier3

- **NEW-tier3-1 (Low, feature-gap-with-safety-note)** — `moveFile` on committed non-part files throws `LOGICAL_ERROR` when the source is not staged in this transaction. Anchor: `ContentAddressedTransaction.cpp:1488`. Any code path that reaches `moveFile` on a committed part-file rename (e.g. a future MergeTree change that reintroduces the `txn_version.txt` `.tmp` + `replaceFile` rename dance) — comment (1483-1487) documents it as "no live caller … retained only as a fail-loud guard". Correctness-safe but coupled to a MergeTree invariant CAS does not enforce; a future MergeTree refactor could regress silently.
- **NEW-tier3-2 (Low, robustness)** — cross-namespace `moveDirectory` (RENAME TABLE) is documented as best-effort, non-atomic, idempotent-on-retry but has no in-call compensation. Anchor: `ContentAddressedTransaction.cpp:1215-1248`. Server crash mid-loop during a `RENAME TABLE` that spans a CAS pool ⇒ table is "SPLIT across namespaces" until manually re-driven. Same failure mode as DUR1 partial-commit class, at RENAME-TABLE granularity — not called out in original Tier3/Tier2 sections.
- **NEW-tier3-3 (Info)** — Same-pool same-disk `moveDirectory` for part-dirs is a pure metadata `republishRef` (`ContentAddressedTransaction.cpp:1370`), i.e. genuinely O(1) copy-by-reference. Original audit did not enumerate this as a positive property; worth calling out that same-disk `MOVE PARTITION TO TABLE` is already relink-free on CAS today. Bounds the gap in TIER-1 (CAS-041) precisely to the cross-disk case.

## tier4

- **NEW-tier4-1 (Low, test-coverage)** — FETCH-to-detached relink correctness has code but no dedicated integration test. `ALTER TABLE ... FETCH PARTITION ... FROM ...` on CAS (routes through `to_detached=true`) needs an integration test asserting that the received part lands as a relinked `detached/<name>` ref, not as a byte re-upload. Anchor for fix: `DataPartsExchange.cpp:697-704, 944` + `ContentAddressedExchange.h:50, 206-208`. No test in `tests/integration/test_cas_*` currently pins B66b.
- **NEW-tier4-2 (Low, test-coverage)** — RENAME TABLE / cross-engine table move on CAS is best-effort non-atomic and the "SPLIT across namespaces" recovery path is idempotent by construction, but no integration test injects a fault between the `republishRef` loop and `dropNamespace` and asserts idempotent re-drive. EXCHANGE TABLES composes two such halves; a dedicated fault-injection test would catch a future refactor that accidentally loses idempotency.
- **NEW-tier4-3 (Low, observability)** — a `CasBlobAdoptTrusted` ProfileEvent (`src/Common/ProfileEvents.cpp:900`) partially closes the original OBS-3 gap (relink hit-rate is measurable at the "adoption" level), but there is still no counter distinguishing a **relink fetch** from a **byte fetch** in the replication log (`system.replicated_fetches` bytes-transferred remains the only signal). Narrows OBS-3 from "no visibility" to "no per-fetch flag."

## upgrade-compat

- **NEW-upgrade-compat-1 (Med)** — `changePoints()` history stayed frozen at `{{1,1}}` across two `G_BUILD` bumps. `Formats/CasFormat.cpp:22, 26-48`. `G_BUILD` advanced from 1 to 3, but no class received a class-specific change-point array; every class still dispatches to `BASELINE = {{1, 1}}`. The `README.md:44-51` upgrade contract explicitly says "Breaking change = `v` bump + `changePoints` + write-down-to-floor" and the two `v` bumps that happened were treated as breaking (backward floor raised to 3), but the `changePoints` half of the contract was not exercised. A future operator cannot inspect format history to know which generations were additive vs breaking.
- **NEW-upgrade-compat-2 (Low)** — backward pool-meta floor is a hard `< 3` gate, no operator override. `Formats/CasPoolMetaFormat.cpp:109-113` throws with message "CAS is pre-release — recreate the pool." Correct fail-closed pre-release, but a raw throw with no operator escape hatch and no runbook link. Any test pool minted by an earlier CAS branch cannot be reopened by this build even in read-only observe mode. Post-GA this must become a versioned upgrade path.
- **NEW-upgrade-compat-3 (Low)** — tolerant-key silent-drop has no per-generation "critical additive" mechanism. `Formats/CasTextFormat.cpp:245-256`. The `!`-prefix "critical key" convention (line 249-251) is the only way to make an unknown key fail closed; no way to add a new tolerant additive key that is "best-effort forever after floor-raise N". Makes the CAS-027-analog residual window permanent within a generation.
- **NEW-upgrade-compat-4 (Info)** — pool-meta admission ratchets `min_reader_generation` irreversibly on any new-algo union. `CasPoolMeta.cpp:75-102` (`admitOrValidate`) — line 88: `next.min_reader_generation = G_BUILD;`. Correct (once a schema-3-bearing algo is present, older readers cannot decode the settlement key), but the ratchet fires on any new-algo admission regardless of whether the admitted algo requires schema-3 semantics. Fine as over-fence today; revisit if a `BlobHashAlgo` is ever added that is deliberately gen-1-compatible.
- **NEW-upgrade-compat-5 (Info)** — no LE-only build assertion. No occurrence of `std::endian::native` / `__BYTE_ORDER__` / `static_assert` guarding LE-only in `MetadataStorages/ContentAddressed/**`. Explicit-BE wire codec covers CAS's own bytes, but the underlying `CityHash128` implementation is not audited BE-safe. Cheap one-liner recommendation.

## write-protocol

- **NEW-write-1 (Low, LEAK/OBSERV)** — `CaContentWriteBuffer::finalizeImpl` sets `temp_ownership_transferred = true` (line 1845) even after `on_finalized` throws in the tail of that lambda, because the flag is set after the callback. On S3-staging mode a callback throw would leave `temp_ownership_transferred = false`; `~CaContentWriteBuffer()` then calls `cancel()` → `cancelImpl` (line 1849) — and for `is_s3_staging=true` the destructor deliberately does not delete the remote staging object. So a fresh mount's staging-key becomes an orphan sweep target rather than being reclaimed on the failing txn. Anchor: `ContentAddressedTransaction.cpp:1842–1846` + `165–207`.
- **NEW-write-2 (Low, CORRECTNESS/COMPAT)** — `CaContentWriteBuffer::finalizeImpl` reports the payload size via `count()` (line 1822), which is the byte count of what THIS buffer forwarded to `hashing`. In S3-staging mode the envelope header is written directly to `sink` (line 1794) bypassing `hashing`. Correct by design, but the reported `size` returned via `on_finalized(hash_hex, size, temp_path)` is the payload-only size — `stageBlobPartFile` then persists as `entry.blob_size`. Downstream `tryReadFileInFlight` for S3 staging builds a `ReadBufferFromFileView` windowed to `[header_len, header_len+size)` which requires `header_len` from `poolMeta().blob_header_len`. If a mid-stream mount rotates `blob_header_len`, in-flight read of a pending blob would read from the wrong offset. Not currently exploitable but chains via CAS-024/CAS-066.
- **NEW-write-3 (Low, LIVENESS/PERF)** — `ContentAddressedTransaction::moveDirectory`'s RENAME-TABLE branch (`:1231–1249`) does `for (const auto & [ref, _] : store->listRefs(from_ns))` and calls `republishRef(...)` per ref, then `putNamespaceFile` per verbatim file, then `dropNamespace(from_ns)`. There is no bounded budget on this loop and no chunking: a table with millions of parts stalls the entire user query for the whole loop, holding the disk transaction open. Chain with CAS-006 (S3 latency under DataPartsLock) and CAS-057 (LIST cost) for a full outage shape on RENAME TABLE of a very large table.
